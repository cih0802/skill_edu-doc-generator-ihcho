# CREATE 모드 — 신규 교육자료 생성

## When to Load

라우터(`SKILL.md`) 모드 판정 결과가 **CREATE** 일 때. `GOAL` 이 확보된 상태여야 한다.

## Prerequisites

- 모드 판별 완료
- `GOAL` 확보 (없으면 라우터에서 질문했어야 함)

> **참조 경로**: 아래 `../references/...` 는 스킬 루트의 `references/` 폴더다.
> 이 파일이 하위 폴더에 있으므로 상위 경로로 표기한다.

---

## Workflow

> **이 장이 정하는 것** — 목표 하나로 문서 세트를 만들어 내는 순서.
> 계정 적합성 확인 → 초안 → 비판적 검토 → 실습 문서 → 정리 문서 → 검증 → 인덱스 → 등록.

### STEP C0. 목표 확정, 번호 배정, 폴더 준비
1. `GOAL`을 확인하고, 모호하면 **질문 1개로만** 명확화한다.
2. `TOPIC_SLUG` 를 결정한다 (영문 소문자 + 하이픈).
3. **카탈로그에서 번호를 배정한다.**
   ```bash
   cat "/workspace/00_교육자료_카탈로그.md"
   ```
   - 표에서 가장 큰 `NN` 을 찾아 **`NN + 1`** 을 배정한다
   - **빈 번호를 재사용하지 않는다** (폐기된 자료의 번호도 비워 둔다)
   - 카탈로그가 없으면 `EDU-01` 부터 시작하고 카탈로그를 새로 만든다
4. **대상 폴더가 이미 존재하는지 확인한다.** 같은 주제가 다른 번호로 있을 수 있으므로
   번호가 아니라 **slug 로** 찾는다.
   ```bash
   ls -d /workspace/EDU-*_<TOPIC_SLUG>/ 2>/dev/null
   ```
   결과가 있으면 **⚠️ STOP** — 라우터(`SKILL.md`)의 ⓐ 질문으로 돌아간다.
5. `/workspace/EDU-<NN>_<TOPIC_SLUG>/` 를 생성한다.
6. **카탈로그에 행을 추가한다.** 이 시점에는 검증 상태를 `⏳ 진행 중` 으로 둔다.

   | 열 | 값 |
   |----|-----|
   | 번호 | `EDU-<NN>` |
   | 한글 제목 | 사람이 읽는 제목 |
   | 폴더 | `EDU-<NN>_<TOPIC_SLUG>/` |
   | 분야 태그 | **해당하는 것 전부.** 하나만 고르지 않는다 |
   | 규격 / 실행 검증 | `⏳ 진행 중` |

**⚠️ STOP**: `GOAL` / `TOPIC_SLUG` / 예상 문서 구성을 제시하고 승인받는다.

주제에 따라 실습 구성이 갈리는 선택지(소스 시스템, 배포 방식 등)가 있으면
이 시점에 **하나만** 질문해 확정한다. 문서 전체 구조가 여기서 결정된다.

### STEP C1. 계정 적합성 사전 확인

문서를 쓰기 **전에** 이 계정에서 실습이 가능한지 확인한다.
불가능한 실습의 문서를 쓰는 것은 낭비이며, 검토 단계(C3)까지 가서 발견하면 되돌리는 비용이 크다.

```sql
SELECT CURRENT_ACCOUNT(), CURRENT_REGION(), CURRENT_ROLE(),
       CURRENT_USER(), CURRENT_VERSION();
```

주제 관련 기능의 활성화 여부를 실제 SQL로 확인한다
(예: `SHOW <FEATURE> ...`, `SHOW PARAMETERS LIKE '...' IN ACCOUNT`).
최신 문법과 제약은 `cortex search docs "<주제>"` 로 확인한다.

**⚠️ STOP**: 계정 제약으로 실습 자체가 불가하면 진행 전에 알리고 대안을 제시한다.

### STEP C2. 교육자료 초안 작성 (`01_교육자료_정리본.md`)

**Load** `../references/20_teardown-registry.md` — 객체 대장과 명명 규칙 작성에 필요하다.
포함해야 할 내용:
- 학습 목표 및 완료 시 달성 상태
- 사전 준비물 / 필요 권한 / 필요 리소스
- 아키텍처 개요 (텍스트 다이어그램 허용)
- 핵심 개념 설명
- **객체 대장** — `../references/20_teardown-registry.md` 의 "객체 대장" 절
- **명명 규칙** — `../references/20_teardown-registry.md` 의 "명명 규칙" 절
- 전체 실습 단계 요약 (문서 번호와 매핑, `98_` 정리 문서 포함)
- 예상 소요 시간
- **비용 주의 — 지속 과금 객체와 정리 필요성**
- 트러블슈팅 참고 사항

### STEP C3. 비판적 검토 및 업데이트 (생략 금지)

**Load** `../references/30_quality-bar.md` — 검토 기준.

**Load** `../references/11_verification.md` — 근거 우선순위와 실행 vs 컴파일 판단.
`../references/30_quality-bar.md` 를 기준으로 초안을 스스로 검토한다. 근거는 `../references/11_verification.md` 를 따른다.

검토 결과를 `01_` 문서에 반영하고, 발견한 문제와 조치를 문서 하단
`## 검토 이력` 의 `### 1차 (생성 시)` 로 기록한다.

이 이력은 이후 IMPROVE 모드가 중복 지적을 피하는 근거가 되므로,
**미검증 항목과 그 이유를 반드시 남긴다.**

### STEP C4. 실습 문서 생성 (`02_` ~ `89_`)

**Load** `../references/10_output-contract.md` (아직 로드하지 않았다면) — 분리 규칙, 메타 주석, SQL 작성 원칙.
- 문서 분리 규칙 적용 — `../references/10_output-contract.md`
- 모든 파일에 메타 주석 블록 포함 — `../references/10_output-contract.md`
- **`02_` 시작부에 사전 스냅샷 배치** — `../references/20_teardown-registry.md` 의 "사전 스냅샷" 절 — 실측값을 전사하지 않고 빈 기록 서식으로 둔다
- SQL 문서 작성 원칙 적용 — `../references/10_output-contract.md` 의 "SQL 문서 작성 원칙" 절
- 계정 레벨 객체에 `CREATE OR REPLACE` 를 쓰지 않는다
- 주제가 요구하면 부수 문서(`90_`~`94_`)와 왕복 검증 문서(`95_`/`96_`)를 추가한다 — 선택

### STEP C5. 정리 문서 생성 (`98_리소스정리.sql`) — 생략 금지

**Load** `../references/21_teardown-execution.md` — `98_` 9개 필수 구성과 안전장치.
- `../references/21_teardown-execution.md` 의 "필수 구성" 절 9개 요소를 모두 포함
- `01_` 객체 대장과 **1:1 대조**
- `../references/21_teardown-execution.md` 의 "안전장치" 절 적용
- 외부 정리가 분량이 크면 별도 `.md` 로 분리 (예: `97_외부리소스_정리.md`)

**⚠️ 자체 검증**: `01_` 객체 대장 항목 수와 `98_` 삭제 대상 수를 세어
**1:1 일치**를 확인한다. 불일치하면 어느 쪽이 누락인지 판단해 수정한다.

### STEP C6. 쿼리 검증 및 실습 완주 (생략 금지)

**(1) 구문 검증.** `../references/11_verification.md` 에 따라 **모든 SQL을 컴파일 검증**하고, 실패는 **수정 후 재검증**한다.

**(2) 🔴 실습 완주.** 컴파일만으로 끝내지 않는다. `../references/30_quality-bar.md` 의 "완주 검증" 절에 따라
`02_` → 마지막 단계 → `98_` 정리 → 사전 스냅샷 대조까지 **실제로 실행**한다.
비용은 사전 허가되었으므로 비용을 이유로 건너뛰지 않는다.
완주에 실습 데이터가 필요하면 직접 만들고, 완주 후 삭제한다.

**(3) 표기.** 실행으로 확인한 것과 미검증 항목을 `../references/11_verification.md` 의 미검증 표기 의무에 따라 구분해 적는다.
완주하지 못한 단계는 그 이유를 함께 쓴다.

### STEP C7. 인덱스 스크립트 생성 및 실행 (`99_` → `00_`)
`99_generate_index.py` 요구사항:
- 스크립트가 위치한 폴더를 스캔
- `00_index.md` 자체는 목록에서 제외
- 파일명 접두 번호 기준 정렬 (빈 번호 허용)
- 최상단 메타 주석(`/* */`, `<!-- -->`, `""" """`) 파싱 → `title`, `step`, `type`, `summary`, `requires`, `next` 추출
- 메타 주석 없으면 `summary: (요약 없음)` 처리 + **경고 출력**
- 마크다운 표 + 실습 진행 순서 + 의존 관계를 `00_index.md` 에 기록
- **재실행 시 항상 덮어쓰기(멱등)**

작성 후 실제로 실행한다.

```bash
cd /workspace/EDU-<NN>_<TOPIC_SLUG> && python3 99_generate_index.py
```

경고가 출력되면 원인(메타 주석 누락 등)을 해결한 뒤 재실행한다.
**멱등성을 확인한다** — 2회 실행 결과가 동일해야 한다.

### STEP C8. 카탈로그 갱신 및 최종 보고

**먼저 카탈로그(`/workspace/00_교육자료_카탈로그.md`) 의 해당 행을 갱신한다.** `⏳ 진행 중` 을 실제 결과로 바꾼다.

- **문서 수** — 최종 개수
- **규격** — `✅` 또는 `❌ 미준수`(무엇이 없는지 함께)
- **실행 검증** — `✅ 완주` / `⚠️ 부분(무엇까지)` / `❌ 미실행(이유)`
- **분야 태그** — 실제로 다룬 내용에 맞게 보정 (작성 중 범위가 바뀌었을 수 있다)
- 미해결 항목이 있으면 카탈로그의 "현재 미해결 항목" 절에 추가

그다음 보고한다.

- 생성된 폴더 경로와 문서 개수
- **실습 완주 여부** — 완주했다면 학습 목표별 달성 근거, 못 했다면 어느 단계에서 왜 멈췄는지
- **실행으로 발견해 정정한 결함** (있다면)
- **검증된 항목 / 미검증 항목** (숨기지 않는다)
- **정리·대조 결과** — 잔여물 0 확인 여부
- 실습 시작 방법 (`00_index.md` 부터)

**⚠️ STOP**: 최종 리뷰.

## 공통 금지 사항 — 실행 시점

라우터의 라우팅 단계 금지 사항에 더한다.

**B. 검증 근거 — 이것을 근거로 삼지 않는다**
- **검증 단계를 생략하지 않는다**
- **모델 기억을 근거로 정확성을 주장하지 않는다**
- **검증하지 않은 구문을 검증된 것처럼 서술하지 않는다**
- **프로시저·태스크의 "성공 응답"을 검증 근거로 삼지 않는다** — 반환 메시지와 `STATE = SUCCEEDED` 는 `EXCEPTION` 핸들러에 삼켜진 실패를 가릴 수 있다. **결과 상태를 별도 쿼리로 단정한다**
- **`98_` 을 1회 실행해 성공한 것을 재실행 안전성의 근거로 삼지 않는다** — 정리 문서는 두 번 실행해 검증한다. `IF EXISTS` 는 **상위 데이터베이스·스키마 부재를 막아주지 않는다**
- **컴파일 검증만으로 완료를 보고하지 않는다** — 실습 완주(실행 → 결과 확인 → 정리 → 대조)까지
  수행하고, 못 한 부분은 이유와 함께 밝힌다 (품질 기준의 "완주 검증" 절)
- **실습 데이터가 없다는 이유로 완주를 건너뛰지 않는다** — 필요한 데이터는 직접 만든다
- **비용을 이유로 실행 검증을 생략하지 않는다** — 컴퓨트·서버리스·토큰·스토리지 비용은
  사용자가 사전 허가했다(검증 규율의 "실행 승인" 절). 단 **로그인 경로 변경·자격증명 발급·
  기존 사용자/역할 변경·계정 파라미터 변경·외부 시스템 변경**은 비용 허가와 별개로 확인받는다
- **`DROP` 워크플로를 추측해 기술하지 않는다** — 공식 문서로 확인한다
- **차단 지점(하드 블로커)을 추정으로 기술하지 않는다** — 순서대로 실행해 **처음 막히는 지점**을 실측으로 확정하고 오류 원문을 인용한다. 도달 한계까지 간 것을 "완주" 라고 부르지 않는다
**C. 서술 정직성 — 아는 것보다 크게 말하지 않는다**
- **측정하지 않은 성능·비용·효과 수치를 제시하지 않는다** — 레이턴시, 처리량, 절감률, 방어율, ROI
- **"검증 완료"·"운영 배포 가능" 류의 총괄 합격 선언을 쓰지 않는다** — 검증은 항목 단위로만 주장한다
- **이름이 비슷한 두 제품 기능을 확인 없이 동일시하지 않는다** — 성격·적용 범위를 공식 문서로 확인한다
**D. 정리·왕복 가능성 — 계정에 흔적을 남기지 않는다**
- **정리 문서(`98_`) 없이 완료로 보고하지 않는다**
- **실행 검증을 했다면 `98_` 정리와 스냅샷 대조까지 완결한다** — 비용 허가는 잔여물을 남길 허가가 아니다
- **객체 대장에 없는 객체를 실습에서 생성하지 않는다**
- **객체 추출을 `.sql` 파일로 한정하지 않는다** — `.md` 코드블록의 `CREATE`/`ALTER … SET` 도 대장 대상이다
- **정적 검색 결과만으로 객체 대장을 완성하지 않는다** — 프로시저·태스크가 **실행 중 만드는 객체**는 `grep` 에 걸리지 않는다. 계정 레벨이면 `DROP DATABASE` 로도 사라지지 않으므로 `(간접)` 으로 등재하고 `98_` 에 패턴 검색 절차를 둔다
- **사용자가 명시하지 않은 기존 Snowflake 객체를 재사용하거나 변경하지 않는다.** 제품 요구사항 때문에 불가피하게 변경해야 한다면 그것을 **대장 (b) 속성 변경 행으로 등재하고 "속성 변경(Mutation)" 절의 3단계(사전 값 기록 → 변경 지점 경고 → `98_` 원복)를 모두 수행한다.** 등재 없이 변경하는 것을 금지한다
- **`DROP` 만으로 원복되지 않는 변경을 정리 완료로 보고하지 않는다**
- **계정 기본 객체(`COMPUTE_WH`, `SNOWFLAKE`, 시스템 Role, `PUBLIC` 등)를 삭제하는 구문을 생성하지 않는다**
- **`CREATE OR REPLACE` 를 재실행 안전성의 근거로 삼지 않는다.** 계정 레벨 객체(DB/WH/Role)에는 쓰지 않는다
- **스냅샷·환경 상태의 실측값을 문서에 전사하지 않는다** — 쿼리와 빈 기록 서식을 제공한다
**E. 보안·자격증명**
- **발급한 자격증명 값을 대화·문서에 출력하지 않는다**
- **동적 SQL 의 식별자 자리를 검증 없이 문자열 결합하지 않는다** — 식별자는 바인드할 수 없으므로 패턴 검사로 방어한다. 주입 가능한 패턴을 예시로 남기지 않는다
**F. 문서 구조·번호·카탈로그**
- `00_index.md` 를 손으로 작성하지 않는다
- 폴더 밖에 파일을 흩뿌리지 않는다 (예외: 워크스페이스 카탈로그 `/workspace/00_교육자료_카탈로그.md`)
- `95_`, `96_`, `98_`, `99_` 를 다른 용도로 쓰지 않는다 (예약 번호)
- 계획·분석·진행 상황 문서를 별도 파일로 만들지 않는다 (분석은 대화와 `01_` 검토 이력에 남긴다).
  단 `90_`~`94_` 의 **부수 문서**(개념 심화, 실무 핸드오프, 운영 런북)는 허용한다 — 문서 번호 규칙 참고
- **이미 배정된 `EDU-<NN>` 번호를 바꾸지 않는다.** 폐기된 번호도 재사용하지 않는다
- **번호에 분야·난이도·수강 순서를 인코딩하지 않는다**
- **분야 태그를 하나만 달지 않는다** — 해당하는 것 전부 단다. 한 자료가 여러 분야에 걸치는 것이 정상이다
- **카탈로그에 등록하지 않고 완료로 보고하지 않는다** — 번호·제목·폴더·분야 태그·검증 상태
**G. 작업 환경**
- **`>>` 로 문서에 내용을 덧붙이지 않는다** — 이 스테이지 파일시스템에서 **조용히 실패**한다. 전체를 다시 쓰고, 쓴 뒤 **내용으로** 확인한다

## CREATE 전용 금지 사항

- **기존 폴더를 확인 없이 덮어쓰지 않는다**
- 문서 번호를 중복하지 않는다
- 필수 문서(`01_`, `98_`, `99_`)를 빼놓고 마무리하지 않는다
- **계정 적합성 확인(STEP C1) 없이 문서를 쓰지 않는다** — 불가능한 실습의 문서는 낭비다
