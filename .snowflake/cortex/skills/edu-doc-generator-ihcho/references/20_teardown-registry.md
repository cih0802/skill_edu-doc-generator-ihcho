# 정리 준비 — 객체 대장과 사전 스냅샷

> **이 장이 정하는 것** — 실습이 만든 것을 빠짐없이 되돌리는 방법.
> 객체 대장(정리의 계약서) · 사전 스냅샷 · `98_` 9개 필수 구성 · 재실행 안전성.

> **원칙: 실습은 계정에 흔적을 남기지 않는다.**
> 실습 전 상태와 정리 후 상태가 동일해야 한다. 이를 **왕복 가능성(round-trip)** 이라 부른다.
> 정리 절차는 부가 기능이 아니라 **산출물의 필수 구성 요소**다.

---

## 1. 객체 대장(Object Registry) — `01_` 문서에 필수 포함

실습에서 **생성하는 모든 것**을 표로 명시한다.
여기에 없는 객체를 만들면 안 되고, 여기 있는 모든 객체는 `98_` 에서 삭제되어야 한다.
**이 표가 정리 절차의 계약서다.**

| 종류 | 이름 | 스코프 | 생성 문서 | 정리 방법 | 비용 발생 |
|------|------|--------|-----------|-----------|-----------|
| Role | `LAB_ADMIN_RL` | 계정 | `02_` | `DROP ROLE` | 없음 |
| Database | `LAB_DB` | 계정 | `02_` | `DROP DATABASE` | 스토리지 |
| Warehouse | `LAB_WH` | 계정 | `02_` | `DROP WAREHOUSE` | **컴퓨트** |
| Integration | `LAB_EAI` | 계정 | `04_` | `DROP INTEGRATION` | 없음 |
| Secret | `LAB_DB.SCH.LAB_SECRET` | 스키마 | `04_` | `DROP SECRET` | 없음 |
| (외부) | 복제 슬롯 `lab_slot` | 소스 DB | `03_` | `pg_drop_replication_slot()` | **소스 디스크** |

#### 스코프 열이 중요한 이유

**계정 레벨 객체**(Role, Database, Warehouse, Integration, Compute Pool, Share,
Network Policy, Openflow Deployment 등)는 삭제를 놓치면 계정에 영구히 남는다.
**스키마 레벨 객체**는 상위 DB를 지우면 함께 사라지므로 위험이 낮다.

#### 외부 리소스도 대장에 포함한다

Snowflake 밖에서 만든 것(복제 슬롯, 웹훅, IAM 역할, 방화벽 규칙, 소스 DB 설정 변경)도
같은 표에 넣는다. 누락되면 사용자 환경에 문제가 남는다.

#### 대장은 세 부분으로 나눈다

대장을 하나의 표로 만들면 성격이 다른 항목이 섞여 정리가 누락된다.
다음 세 부분으로 나눠 작성한다.

| 부분 | 대상 | 정리 동작 |
|------|------|-----------|
| **(a) 신규 생성 Snowflake 객체** | 실습이 만든 것 | `DROP` |
| **(b) 기존 객체의 속성 변경** | 실습이 **바꾼** 것 | **원복** (아래 "속성 변경(Mutation)" 절) |
| **(c) 외부 리소스** | Snowflake 밖 | 삭제 또는 설정 원복 |

#### 🔴 간접 생성 객체 — `grep` 으로는 절대 찾을 수 없다

**대장 누락의 가장 위험한 유형이다.** 지금까지의 객체 추출은 문서에 적힌
`CREATE` 구문을 찾는 방식이다. 그런데 **프로시저·태스크·UDF 가 실행 중에 만드는
객체**는 문서에 `CREATE` 구문으로 존재하지 않는다. 동적 SQL 문자열 안에 있거나
런타임에 조립되므로 정적 검색으로 보이지 않는다.

| 유형 | 예시 | 왜 위험한가 |
|------|------|-------------|
| 프로시저가 만드는 사용자 | `EXECUTE IMMEDIATE 'CREATE USER ' \|\| :v_id` | **계정 레벨**이라 `DROP DATABASE` 로 사라지지 않는다 |
| 프로시저가 만드는 Role·Grant | 동적 `GRANT ROLE` | 권한이 계정에 잔존한다 |
| 태스크가 적재하는 대상 테이블 | 파이프라인이 자동 생성하는 대상 | 상위 DB 안이면 위험은 낮다 |
| 외부 시스템이 역방향 생성 | SCIM 프로비저닝이 만드는 사용자 | Snowflake 밖 트리거로 생성된다 |

> 실측 사례: 인사 동기화 프로시저가 사번당 `CREATE USER` 를 발행해 계정에
> 사용자 5명을 만들었다. 문서의 `CREATE` 구문에는 없으므로 대장에서 빠졌고,
> `DROP DATABASE` 로도 사라지지 않아 **계정 레벨 잔여물**이 되었다.

**필수 조치.**

1. 대장 (a) 에 **`(간접)` 표시와 "생성 문서" 대신 "누가 만드는가"** 를 적는다
   ```
   | **User (간접)** | `EMP_F***` | 계정 | `06_` 프로시저가 실행 중 생성 | `DROP USER` |
   ```
2. **이름이 가변적이면 패턴으로 등재**하고, `98_` 에 **패턴 검색 + 개별 삭제** 절차를 둔다
   ```sql
   -- 프로시저가 만든 사용자를 먼저 찾는다 (입력 데이터에 따라 개수가 다르다)
   SHOW USERS LIKE 'EMP_F%';
   --   남은 사용자: ______  (없어야 합니다)
   ```
3. 알려진 이름은 개별 `DROP` 을 넣고, **"입력을 바꿨다면 더 있을 수 있다"** 를 경고한다

**찾는 방법.** 정적 검색으로는 안 되므로 아래를 병행한다.

```bash
# 동적 SQL 조립 지점을 찾는다 — 여기서 만들어지는 객체를 사람이 읽어 판단한다
grep -rnE "EXECUTE IMMEDIATE|IDENTIFIER\(|\|\| *'" "$F"
```

그리고 **실습을 완주한 뒤 계정을 접두사로 훑는다.** 이것이 가장 확실하다
(품질 기준의 "완주 검증" 절).

#### 속성 변경(Mutation) — 삭제가 아니라 **원복** 대상

> **가장 놓치기 쉬운 결함이다.** 사전 스냅샷 절의 "기존 객체를 재사용하지 않는다" 원칙에도
> 불가피한 예외가 생긴다. 제품이 요구하는 계정·사용자·파라미터 설정 변경은
> 새 객체를 만들 수 없으므로 **기존 객체를 바꿔야만** 한다.
> 이런 항목은 `DROP` 으로 되돌아가지 않으므로 별도로 관리한다.

전형적인 예:

| 유형 | 예시 | 왜 불가피한가 |
|------|------|---------------|
| 사용자 속성 | `ALTER USER … SET DEFAULT_SECONDARY_ROLES`, `SET DEFAULT_ROLE` | 제품이 특정 Role 평가 방식을 요구 |
| 계정 파라미터 | `ALTER ACCOUNT SET …` | 기능 활성화에 필요 |
| 기존 객체 연결 | `ALTER <상위객체> SET EVENT_TABLE / EXTERNAL_ACCESS_INTEGRATIONS` | 상위 객체가 실습 대상이면 원복 필요 |
| 외부 시스템 설정 | `wal_level`, `binlog_format`, 방화벽 규칙 | 소스 시스템 재설정 |

**필수 3단계.** 하나라도 빠지면 왕복 가능성이 깨진다.

1. **`02_` 사전 스냅샷에서 실습 전 값을 기록한다** — 기록 서식을 함께 제공한다.
   무엇으로 되돌릴지 모르면 원복이 불가능하다.
   ```sql
   -- 🔴 실습 전 값 기록 — 이 값 없이는 원복할 수 없습니다
   DESCRIBE USER IDENTIFIER($my_user);
   -- 실습 전 DEFAULT_SECONDARY_ROLES = ______________
   ```
2. **변경 지점에 🔴 경고를 붙인다** — "이것은 신규 생성이 아니라 기존 객체 변경이며
   `DROP` 으로 되돌아가지 않는다"는 사실을 그 자리에서 알린다.
3. **`98_` 에 원복 절을 둔다** — 실습 전 값에 따라 **분기**한다.
   원복 구문은 `UNSET`(기본값 복귀)과 `SET <원래 값>`이 다르므로 공식 문서로 확인한다.

```sql
-- 경우 1) 실습 전에도 이미 그 값이었다 → 할 일 없음
-- 경우 2) 실습 전이 미설정/NULL 이었다  → ALTER USER … UNSET <속성>;
-- 경우 3) 실습 전이 명시적 다른 값이었다 → ALTER USER … SET <속성> = <원래 값>;
```

> 💡 **제품 기본값이 이미 그 값이면 변경 자체가 불필요하다.** 변경 구문을 넣기 전에
> 해당 속성의 현재 기본값을 확인하고, 기본값과 같다면 "건너뛰어도 된다"고 명시한다.
> 불필요한 변경을 만들지 않는 것이 원복보다 낫다.

## 2. 명명 규칙 — 식별 가능하게 만든다

정리 누락을 막는 가장 효과적인 수단은 **일관된 접두사**다.

- 모든 신규 객체에 공통 접두사를 붙인다: `LAB_`, `<TOPIC>_EDU_` 등
- 모든 객체의 `COMMENT` 에 공통 태그를 넣는다: `[<TOPIC_SLUG>]`
- 이렇게 하면 정리 시 `SHOW ... LIKE '<PREFIX>%'` 로 잔여물을 한 번에 찾을 수 있다

```sql
CREATE DATABASE LAB_DB COMMENT = '실습용. [openflow-cdc]';
```

## 3. 사전 스냅샷 — `02_` 문서 시작부에 필수

실습 **전** 상태를 기록해 둔다. 정리 후 이것과 대조해 원상복구를 증명한다.
기록 자체가 계정을 변경하지 않도록 **조회 전용**으로 구성한다.

```sql
-- 실습 전 상태 스냅샷 (결과를 별도로 저장하거나 캡처해 둘 것)
SHOW DATABASES;
SHOW WAREHOUSES;
SHOW ROLES;
SHOW INTEGRATIONS;
SHOW COMPUTE POOLS;
-- 주제에 따라 추가: SHOW TASKS / STREAMS / PIPES / SECRETS / NETWORK RULES ...
```

접두사 방식을 쓴다면 더 간단하게 **충돌 검사**로 대체할 수 있다.

```sql
-- 접두사가 이미 쓰이고 있지 않은지 확인 (기존 객체를 덮어쓰지 않기 위해)
SHOW DATABASES  LIKE 'LAB_%';
SHOW WAREHOUSES LIKE 'LAB_%';
SHOW ROLES      LIKE 'LAB_%';
-- 결과가 있으면 접두사를 바꾸거나 사용자에게 확인한다
```

> ⚠️ **기존 객체를 재사용하지 않는다.** 사용자가 명시적으로 지정한 경우를 제외하고,
> 실습은 항상 새 객체를 만든다. 기존 객체를 건드리면 정리로 되돌릴 수 없다.

#### 🔴 스냅샷 결과값을 문서에 전사하지 않는다

가장 흔한 실수는 스냅샷을 한 번 실행하고 **그 결과를 문서 표에 옮겨 적는 것**이다.
전사한 값은 즉시 낡는다. 실습자의 계정은 작성자의 계정이 아니다.

| 전사가 만드는 결함 | 예시 |
|-------------------|------|
| 값이 틀린다 | `AUTO_SUSPEND = 600초` 로 적었지만 실제 계정은 `300초` |
| 목록이 빠진다 | 웨어하우스 3개 중 1개만 적어 대조 기준이 무의미해진다 |
| 대조가 불가능해진다 | 실습자의 실제 상태와 문서의 값이 달라 차이의 원인을 알 수 없다 |

따라서 스냅샷 절(또는 `95_실습전_기준선.md`)은 다음 두 가지만 담는다.

1. **실행할 쿼리**
2. **빈 기록 서식** — 값은 실습자가 채운다

```sql
-- 실습 전 상태 스냅샷 — 결과를 아래 서식에 직접 기록하세요
SHOW WAREHOUSES;
--   실습 전 웨어하우스 목록: ______________________________
--   COMPUTE_WH AUTO_SUSPEND = ______ 초
```

> 작성자가 확인한 값을 남기고 싶다면 **"작성 시점의 참고값(계정마다 다름)"** 으로
> 명시하고, 대조 기준으로 쓰지 않는다.
