# 품질 기준 (Quality Bar)

> **이 장이 정하는 것** — 완성으로 볼 수 있는 최저선.
> 구조 · 내용 · 정확성(완주 검증 포함) · 정리 4개 영역과 심각도 매핑.

- **CREATE 모드**: 완료 전 자체 확인 체크리스트
- **IMPROVE 모드**: 갭 분석 기준

각 항목 앞의 표시는 **IMPROVE 모드 갭 분석 시 기본 심각도**다.
맥락에 따라 조정할 수 있으나, 조정했다면 근거를 밝힌다.

| 심각도 | 기준 |
|--------|------|
| 🔴 **치명** | 실습이 실패하거나, 계정에 잔여물이 남거나, 거짓을 사실로 서술 |
| 🟡 **중요** | 규격 위반, 필수 요소 누락, 검증 부족 |
| 🟢 **개선** | 가독성, 구성, 보강 |

## 1. 구조

- 🟡 전용 폴더 하위에만 파일이 있다
- 🟡 `00_index.md` 는 스크립트로 생성되었다 (수동 작성 아님)
- 🔴 `01_` 정리본이 존재하고 검토 이력이 있다
- 🟡 문서 번호가 오름차순·유일하다
- 🟡 예약 번호를 용도에 맞게 썼다 (`98_` 정리 / `99_` 인덱스 / `95_`·`96_` 왕복 검증)
- 🟢 부수 문서가 `90_`~`94_` 에 있고, 계획·분석 문서가 아니다
- 🟡 Snowflake 외부 작업이 `.md` 로 분리되었다
- 🟡 모든 파일에 메타 주석 블록이 있다
- 🟡 `requires` / `next` 체인이 실제 파일과 일치한다
- 🟡 `99_generate_index.py` 재실행이 정상 동작하고 멱등하다
- 🟢 인덱스 생성 시 경고가 없다

## 2. 내용

- 🔴 학습 목표가 명확하고 완료 시 달성 상태가 정의되었다
- 🔴 사전 준비물과 필요 권한이 빠짐없이 기술되었다
- 🔴 실습이 **데이터 적재 결과 검증**까지 도달한다
- 🟡 최소 권한 원칙이 적용되었다 (전용 Role/Warehouse/DB 분리)
- 🔴 시크릿이 문서에 평문으로 남지 않는다
- 🟡 재실행 안전성(멱등성)이 확보되었다 — **`CREATE OR REPLACE` 는 근거가 되지 않는다**
- 🔴 **계정 레벨 객체(DB/WH/Role)에 `CREATE OR REPLACE` 를 쓰지 않았다** (동명 사용자 자산 파괴)
- 🟡 실습 불가 조건(계정 Edition/Region/기능 미활성화 등)이 **게이트**로 앞단에 배치되었다
- 🟢 트러블슈팅 정보가 증상 기준으로 제공된다
- 🟢 예상 소요 시간이 단계별로 제시되었다

## 3. 정확성 — 사실 확인

근거 판정은 `output-contract.md` 의 검증 규율을 따른다.

- 🔴 **모든 SQL이 컴파일 검증을 통과했다** (선행 객체 부재로 컴파일 불가한 것은 미검증 표기)
- 🔴 **실습을 최소 1회 완주하고 정리·대조까지 실행했다** (아래 절)
- 🔴 문법을 공식 문서로 대조했다 (**모델 기억에 의존하지 않았다**)
- 🟡 계정 적합성(Edition, Region, Trial, 기능 활성화)을 실제 SQL로 확인했다
- 🔴 **미검증 항목이 문서와 검토 이력 두 곳에 명시되었다**
- 🟡 검증 도구의 한계로 확인 못 한 것을 그렇게 밝혔다
- 🔴 객체의 삭제·상태 전이 워크플로를 추측하지 않고 공식 문서로 확인했다
- 🔴 **측정하지 않은 정량 수치를 제시하지 않았다** (아래 절)
- 🔴 **"검증 완료" 류의 총괄 합격 선언이 없다** (미검증 항목 표기 의무)
- 🔴 **제품 기능의 성격과 적용 범위를 공식 문서로 확인했다** (아래 절)

#### 🔴 측정하지 않은 정량 수치 금지

성능·비용·효과 수치는 그럴듯할수록 위험하다. 독자는 이것을 실측치로 받아들이고
의사결정 근거로 쓴다. **측정 절차 없이 숫자를 쓰지 않는다.**

금지 대상 — 측정 절차가 없다면 하나도 쓰지 않는다.

| 범주 | 예시 표현 |
|------|-----------|
| 레이턴시 | `0.38초`, `P95 1.42초`, `밀리초 단위 처리` |
| 처리량 | `100+ QPS 지원`, `10,000건 0.45초` |
| 절감·개선률 | `운영 공수 85% 절감`, `탐색 시간 90% 단축`, `토큰 75% 절감` |
| 정확도·성공률 | `방어율 100%`, `차단 정확도 100%`, `유출 위험 0%` |
| 비용·ROI | `유휴 비용 0 크레딧`, `TCO N% 개선` |
| 토큰 수 | 단위까지 특정한 `prompt_tokens 105` 표 |

수치를 제시하려면 **세 가지를 함께 둔다.**

1. **측정 쿼리 또는 명령** — 독자가 재현할 수 있어야 한다
2. **표본 수와 측정 조건** — 웨어하우스 크기, 문서 건수, 반복 횟수
3. **측정 시점** — 값은 시간이 지나면 달라진다

그럴 수 없다면 선택지는 둘이다.

| 선택 | 표기 |
|------|------|
| 수치를 **삭제**한다 | 정성 서술로 대체 — "유휴 시 컴퓨트 비용이 발생하지 않는다" |
| 예시임을 **명시**한다 | `예시값(미측정) — 실제 값은 계정·데이터에 따라 다릅니다` |

> ⚠️ **표본 3건으로 `100%` 를 주장하지 않는다.** 관찰 결과는 관찰 결과로 쓴다 —
> "테스트한 3개 시나리오에서 모두 차단되었다".

#### 자주 나오는 정확성 결함 유형

| 유형 | 예시 | 어떻게 잡는가 |
|------|------|---------------|
| 파라미터명 오류 | 실제와 다른 옵션·컬럼 이름 사용 | 컴파일 검증 |
| 필수 권한 누락 | 동작에 필요한 권한을 빠뜨려 런타임에 실패 | 공식 문서 대조 |
| 삭제 워크플로 단순화 | 다단계 절차를 `DROP` 하나로 기술 | 공식 문서 대조 |
| 변경 가능성 오기 | 변경 불가한 속성을 변경 가능하다고, 또는 그 반대로 서술 | 공식 문서 대조 |
| 검증 범위 과장 | 검증 명령이 실제로 확인하지 못하는 것까지 확인한다고 서술 | 자체 점검 |
| **기능 혼동** | 이름이 유사한 두 제품 기능을 동일시하거나, 적용 대상을 확대 해석 | 공식 문서 대조 (아래) |
| **미측정 수치** | 성능·절감률·방어율을 측정 없이 제시 | 위 절 |
| **구·신 함수 혼용** | 신규 함수 이름에 구버전 시그니처를 적용 | 컴파일 검증 (아래) |

#### 🔴 기능 혼동 — 이름이 비슷하면 반드시 문서로 확인한다

Snowflake는 유사한 이름의 기능을 여러 계층에 둔다. **이름이 비슷하다는 이유로
같은 기능이라고 서술하면 아키텍처 설명 전체가 틀린다.** 실습은 동작하는데
설명이 거짓인 상태가 되므로 컴파일·실행 검증으로는 잡히지 않는다.

각 기능에 대해 세 가지를 문서로 확인한다.

| 확인 항목 | 왜 |
|-----------|-----|
| **무엇을 검사·처리하는가** | 입력인가 출력인가. 차단인가 필터인가 |
| **어느 호출 경로에 적용되는가** | SQL 함수 / 특정 클라이언트 / 특정 제품에만 적용될 수 있다 |
| **활성화 방법과 전제 조건** | 함수 인자 / 계정 파라미터 / Edition·Region 요건 |

> 💡 이름이 비슷한 두 기능을 하나의 "다층 방어" 그림으로 합치기 전에, **각 레이어가
> 실제로 그 위치에서 동작하는지** 문서로 확인한다. 다이어그램은 검증 대상이다.

#### 🔴 구·신 함수 혼용 — 시그니처는 이름과 함께 바뀐다

Snowflake는 함수를 새 이름으로 재출시하면서 **인자 형태를 함께 바꾸는** 경우가 많다.
모델 기억은 구버전 시그니처를 신버전 이름에 그대로 붙이는 실수를 반복한다.

- 구·신이 공존하는 함수는 **신규 이름으로 문서를 다시 확인한다**
- 인자 개수·타입·반환 타입을 모두 확인한다 (반환이 문자열인지 OBJECT인지)
- **반드시 컴파일 검증한다.** 이 유형은 컴파일에서 즉시 잡힌다

## 4. 완주와 검증 태도

> 이 절은 **어떻게 검증하는가**를 정한다. 앞 "정확성 — 사실 확인" 절과 별개로,
> 무엇을 근거로 "확인했다"고 말할 수 있는지의 문제다.

#### 🔴 완주 검증 — 컴파일은 완주를 대신하지 못한다

> **"컴파일을 통과했다"는 "실습이 된다"가 아니다.** 이 두 항목을 `또는` 으로 묶으면
> 컴파일만으로 정확성 기준이 충족되어, **한 번도 돌려보지 않은 자료를 완료로 보고**할 수 있다.
> 그래서 분리한다.

컴파일 검증이 원리상 잡지 못하는 것들이 있다.

| 유형 | 실제 사례 |
|------|-----------|
| **DDL 절 순서 오류** | `CREATE PROCEDURE ... EXECUTE AS OWNER` 뒤에 `COMMENT` → 생성 자체가 실패. 개별 구문을 컴파일해도 드러나지만, 문서를 읽기만 하면 놓친다 |
| **런타임 타입 오류** | `TO_JSON(<VARCHAR>)` → 실행 시점에 실패. 프로시저 본문은 생성 시 컴파일되지 않는다 |
| **프로시저 본문 전체** | 본문은 `CREATE` 시 검증되지 않는다. 커서 필드를 SQL 문에 직접 참조하는 오류 등이 호출 시점에야 드러난다 |
| **조용한 실패** | `EXCEPTION WHEN OTHER THEN RETURN '...'` 가 오류를 삼켜 **정상 반환처럼 보인다.** 결과 테이블이 0행인 것으로만 알 수 있다 |
| **상태·순서에 의존하는 동작** | 스트림 오프셋 전진, Task `WHEN` 조건 평가, 인덱스 동기화, 소유권에 따른 권한 |
| **세션 상태 파괴** | 정리 중 사용 중인 웨어하우스를 `DROP` → 후속 문장이 실패 |
| **정리 절차 전체** | `98_` 의 `DROP` 은 대상이 없으면 컴파일조차 불가하다. 실습을 수행한 뒤에만 검증된다 |

**완주의 정의.** 아래를 모두 실행해야 "완주"다.

1. `02_` 부터 마지막 단계 문서까지 **순서대로 실행**한다
2. 학습 목표의 **데이터 적재·동작 결과를 쿼리로 확인**한다 (생성 성공만으로는 부족하다)
3. `98_` 정리를 **실행**한다
4. 사전 스냅샷과 **대조**해 잔여물 0을 확인한다 (속성 변경 원복 포함)

**완주하지 못했다면** 그 사실과 이유를 `01_` 검토 이력과 각 문서 상단에 쓴다.
비용은 사전 허가되었으므로(검증 규율의 "실행 승인" 절) **비용은 완주하지 못한 이유가 될 수 없다.**
정당한 이유는 다음과 같은 것들이다.

- 외부 시스템·테넌트·자격증명이 필요하다 (Entra ID, 소스 DB, IdP 인증서)
- UI 조작이 필요하다 (드래그앤드롭 업로드)
- 시간 경과가 필요하다 (CRON 자연 발동, `TARGET_LAG` 증분 갱신)
- 사용자가 확인을 보류한 위험 구문이다 (로그인 경로 변경 등)

> 💡 완주에 실습 데이터가 필요하면 **직접 만든다.** 파일이 없다고 건너뛰지 않는다.
> 예: PDF 가 필요하면 생성해 스테이지에 올린 뒤(`COPY FILES` 등) 파싱까지 확인한다.
> 이때 만든 검증용 자산은 완주 후 삭제한다.

#### 🔴 "성공 응답" 은 검증 근거가 아니다 — 결과 상태를 단정한다

구문이 오류 없이 끝난 것과 **의도한 상태가 된 것**은 다르다.
아래는 모두 "성공" 으로 보이면서 실제로는 아무 일도 하지 않은 사례다.

| 겉보기 | 실제 |
|--------|------|
| `CALL` 이 `... 완료: 총 4건 처리됨` 반환 | `EXCEPTION` 핸들러가 오류를 삼켰다. 대상 테이블은 **0행** |
| 태스크 이력 `STATE = SUCCEEDED` | 프로시저 내부에서 실패했으나 핸들러가 정상 반환했다 |
| `CALL` 이 매번 같은 건수를 반환 | 스트림 오프셋이 전진하지 않아 **같은 건을 재처리**하고 있었다 |
| `CREATE USER IF NOT EXISTS` 성공 | 기존 계정이라 **아무 것도 갱신되지 않았다** (부서이동 미반영) |
| `ALTER ... SET` 성공 | 설정은 됐으나 `DESCRIBE` 출력에 그 속성이 없어 **확인 자체가 불가능**했다 |

**규칙.**

1. **반환 메시지·`STATE` 를 근거로 쓰지 않는다.** 결과를 **별도 쿼리로 단정**한다
   ```sql
   CALL MY_PROC();                       -- ← 이것은 근거가 아니다
   SELECT COUNT(*) FROM TARGET_TABLE;    -- ← 이것이 근거다
   SHOW USERS LIKE 'EMP_%';              -- ← disabled 값까지 확인한다
   ```
2. **`EXCEPTION WHEN OTHER THEN RETURN ...` 패턴을 결함으로 지적한다.**
   교육자료가 이 패턴을 쓴다면, 최소한 **실패를 감사 로그·알림으로 남기는지**
   확인하고, 남기지 않으면 조용한 실패 위험을 그 자리에 경고한다
3. **멱등성 주장에는 2회 호출 결과를 붙인다.** 1회 성공은 재실행 안전성의 근거가 아니다
   (정리 요구사항의 "재실행 안전성" 절과 같은 원칙이다)
4. **검증 표에 "관측" 열을 둔다.** "성공" 이 아니라 **무엇을 보았는지**를 적는다

> 이 원칙을 지키지 않으면 검증 상태 주석이 거짓이 된다. 실측 사례에서
> 결함 3건이 모두 "성공 응답" 을 반환하고 있었고, 자료는 그것을 근거로
> "엔드투엔드 검증 완료" 를 선언하고 있었다.

#### 🔴 도달 한계(Hard Blocker)를 실행으로 확정한다

계정 에디션·트라이얼 여부·리전·기능 활성화 상태에 따라 **어떤 실습은 끝까지 갈 수
없다.** 그 사실 자체는 결함이 아니다. **결함은 차단 지점을 추정으로 적는 것이다.**

| 흔한 오류 | 결과 |
|-----------|------|
| 문서로 읽은 제약을 게이트로 삼는다 | 실제로는 통과하는 지점에서 학습자를 멈춘다 |
| 가장 앞선 제약만 경고한다 | **진짜 벽은 뒤에 있는데 예고되지 않는다** |
| "될 것이다" 로 서술한다 | 학습자가 중간까지 진행한 뒤 막힌다 |

> 실측 사례: 자료는 "트라이얼 계정에서 `CREATE OPENFLOW DEPLOYMENT` 가 실패할 수
> 있다" 를 사전 게이트로 두었다. 실제로 실행해 보니 **성공**했고, 진짜 차단 지점은
> 세 문서 뒤의 `CREATE EXTERNAL ACCESS INTEGRATION`
> (`External access is not supported for trial accounts`) 이었다.
> 학습자를 틀린 곳에서 멈추게 하고, 정작 넘을 수 없는 벽은 예고하지 않았다.

**필수 절차.**

1. **가장 이른 하드 블로커를 실행으로 찾는다.** 순서대로 실행하다 처음 막히는 지점이
   그것이다. 문서로 추정하지 않는다
2. 막힌 **오류 원문을 그대로 인용**하고 공식 문서로 원인을 대조한다
3. `01_` 의 사전 준비물과 해당 단계 문서 **양쪽에** 그 지점을 명시한다
4. **해소 방법**을 적는다 (에디션 전환, 담당자 승인, 외부 리소스 준비 등)
5. 카탈로그의 실행 검증 열에 **"부분 완주 (도달 한계 확인)"** 으로 기록한다

**도달 한계까지 간 것은 완주 실패가 아니다.** 어디까지 되고 어디서 왜 막히는지를
실측으로 확정한 것이 산출물이다. 다만 그것을 **"완주" 라고 부르지 않는다.**

## 5. 정리 / 왕복 가능성

세부 기준은 `teardown.md` 참고.

- 🔴 `01_` 에 **객체 대장**이 있고 스코프·정리 방법·비용 발생 여부가 채워졌다
- 🔴 대장이 **(a) 신규 생성 / (b) 속성 변경 / (c) 외부 리소스** 세 부분으로 나뉘어 있다
- 🔴 **`ALTER … SET` 으로 바꾼 기존 객체 속성이 모두 대장 (b) 에 등재되었다** — `CREATE` 문만 대조하면 놓친다
- 🔴 **객체 추출을 `.sql` 이 아니라 폴더 전체(`.md` 코드블록 포함)에서 수행했다** — 설명 문서의 코드블록도 실습자는 실행한다
- 🔴 **속성 변경 항목마다 3단계가 모두 있다**: `02_` 사전 값 기록 → 변경 지점 🔴 경고 → `98_` 원복 절
- 🟡 원복 절이 실습 전 값에 따라 **분기**한다 (`UNSET` 과 `SET <원래 값>` 은 다르다)
- 🟡 제품 기본값이 이미 그 값이면 "변경을 건너뛰어도 된다"고 명시했다
- 🟡 모든 신규 객체에 **공통 접두사**와 `COMMENT` 태그가 있다
- 🟡 `02_` 시작부에 **사전 스냅샷**(또는 접두사 충돌 검사)이 있다
- 🔴 **`98_리소스정리.sql` 이 존재한다**
- 🟡 `98_` 이 9개 필수 구성 요소를 모두 포함한다
- 🔴 **객체 대장의 모든 항목이 `98_` 삭제 대상에 있다 (1:1 대조 완료)**
- 🔴 `DROP` 만으로 삭제되지 않는 객체의 실제 워크플로를 공식 문서로 확인해 반영했다
- 🔴 **외부 리소스 정리가 포함되었다** (특히 계속 누적되는 것)
- 🟡 각 단계 문서 말미에 그 단계까지의 정리 주석이 있다
- 🟡 `98_` 의 `DROP` 문이 주석 처리 상태이고 `IF EXISTS` 를 쓴다
- 🟡 정리 완료 검증 쿼리가 있고 사전 스냅샷과 대조하는 절차로 끝난다
- 🟡 **정리 완료 검증 쿼리를 실제로 실행해 봤다** — 실습 리소스가 없어도 실행 가능한 유일한 부분이다
- 🟡 검증 쿼리가 `ACCOUNT_USAGE` 뷰의 존재를 가정하지 않는다 (없는 계정이 있다)
- 🔴 계정 기본 객체를 삭제하는 구문이 없다
- 🟡 일시 중단 선택지가 제공되었다 (실습을 이어서 할 수 있도록)

#### 중복 지적 방지

`01_` 의 기존 검토 이력을 먼저 읽고, 다음은 새 결함으로 보고하지 않는다.

- 이미 "미검증"으로 정직하게 밝힌 항목
- 이미 계정 제약으로 불가함을 명시한 항목
