# IMPROVE 모드 — 기존 교육자료 개선

## When to Load

라우터(`SKILL.md`) 모드 판정 결과가 **IMPROVE** 일 때. `TARGET_FOLDER` 가 확보된 상태여야 한다.

## Prerequisites

- 모드 판별 완료
- `TARGET_FOLDER` 확보
- 규격 외 폴더인 경우: ①(규격 재구성) / ②(내용만) 확정 완료

> **참조 경로**: 아래 `../references/...` 는 스킬 루트의 `references/` 폴더다.
> 이 파일이 하위 폴더에 있으므로 상위 경로로 표기한다.

---

## Workflow

> **이 장이 정하는 것** — 기존 자료를 같은 기준으로 끌어올리는 순서.
> 인벤토리 → 전체 읽기 → 갭 분석 → **승인** → 반영 → 재검증 → 이력 누적 → 인덱스.

> **원칙: 읽고 → 진단하고 → 승인받고 → 최소 변경으로 고친다.**
> 기존 자료는 사용자의 자산이다. 임의로 뒤엎지 않는다.

### STEP I0. 인벤토리 및 범위 확정

```bash
ls -la /workspace/<TARGET_FOLDER>/
```

파일 목록, 번호, 확장자, 크기를 파악한다. `IMPROVE_SCOPE` 를 확정한다(미지정 시 `full`).

**⚠️ STOP**: 대상 폴더와 개선 범위를 제시하고 승인받는다.

### STEP I1. 전체 읽기 (생략 금지)

**Load** `../references/10_output-contract.md` — 규격 위반을 판별하려면 규격을 알아야 한다.

**대상 폴더의 모든 문서를 실제로 읽는다.** 인덱스나 파일명만 보고 판단하지 않는다.

읽는 순서:
1. `00_index.md` — 의도된 구조 파악
2. `01_*.md` — 목표, 객체 대장, 검토 이력 (기존 검토에서 이미 다룬 것을 중복 지적하지 않기 위해 필수)
3. `02_` ~ `97_` — 단계별 문서 전체
4. `98_` — 정리 문서 (없으면 그 자체가 결함)
5. `99_*.py` — 인덱스 스크립트

읽으면서 다음을 추출한다.
- 실제로 생성되는 객체 목록 (SQL에서 직접 추출 — **대장을 믿지 않는다**)
- 문서 간 `requires` / `next` 체인
- 기존 검토 이력에 기록된 이미 알려진 한계
- 미검증으로 표기된 항목

#### 분량이 많을 때

문서 수가 많거나 총 분량이 커서 전부 읽으면 이후 작업 여력이 부족해질 것 같으면,
읽기를 다음처럼 나눈다. **읽기를 건너뛰는 것은 허용하지 않는다.**

| 방법 | 언제 |
|------|------|
| 우선순위 정독 + 나머지 대상 축소 | `IMPROVE_SCOPE` 가 `full` 이 아닐 때. 범위에 해당하는 문서만 정독한다 |
| 서브에이전트에 읽기 위임 | `full` 이고 분량이 클 때. 갭 분석에 필요한 사실만 추출해 오게 한다 |
| 회차 분할 | 위 두 방법으로도 부족할 때. 사용자에게 알리고 문서 그룹을 나눠 여러 회차로 진행한다 |

객체 목록 추출은 grep 으로 보조할 수 있다. 단, **grep 결과만으로 판단하지 말고
해당 파일을 읽어 문맥(주석 처리 여부, 조건부 실행, 설명용 예시 여부)을 확인한다.**

**확장자를 제한하지 않는다.** `.md` 설명 문서의 코드블록도 실습자는 실행한다.
`.sql` 만 훑으면 그 구문이 만든 객체와 바꾼 속성이 대장에서 빠진다.
자세한 근거는 정리 요구사항의 "자체 검증 — 1:1 대조" 절 참고.

```bash
F=/workspace/<TARGET_FOLDER>/
grep -rnE "CREATE (OR REPLACE )?(IF NOT EXISTS )?(DATABASE|SCHEMA|WAREHOUSE|ROLE|TABLE|VIEW|STAGE|SECRET|NETWORK RULE|EXTERNAL ACCESS INTEGRATION|EVENT TABLE|TASK|STREAM|PIPE|COMPUTE POOL|FUNCTION|PROCEDURE|CORTEX SEARCH SERVICE)" "$F"
grep -rnE "ALTER (USER|ACCOUNT|SESSION|DATABASE|WAREHOUSE|TASK|STAGE) .*(SET|UNSET) " "$F"   # ← 속성 변경 탐지
grep -rn  "GRANT " "$F"                                                                      # ← 계정 레벨 권한 부여 탐지
```

### STEP I2. 갭 분석 (Gap Analysis)

**Load** `../references/30_quality-bar.md` — 체크리스트와 심각도 매핑.

**Load** `../references/11_verification.md` — 정확성 판정의 근거 규율.

**Load** `../references/20_teardown-registry.md` — `IMPROVE_SCOPE` 가 `full` 또는 `teardown` 일 때 — 대장 대조.

**Load** `../references/21_teardown-execution.md` — `IMPROVE_SCOPE` 가 `full` 또는 `teardown` 일 때 — `98_` 구성 점검.

`../references/30_quality-bar.md` 를 체크리스트로 삼아 **현재 상태를 항목별로 판정**한다.
`IMPROVE_SCOPE` 에 해당하는 항목만 본다.

각 결함을 아래 형식으로 정리한다.

| # | 심각도 | 분류 | 위치 | 문제 | 근거 | 조치안 |
|---|--------|------|------|------|------|--------|
| 1 | 🔴 치명 | 정확성 | `03_*.sql:45` | `DROP` 워크플로가 실제와 다름 | 공식 문서 대조 | 3단계 절차로 수정 |
| 2 | 🟡 중요 | 정리 | `01_*.md` | 객체 대장에 Integration 누락 | SQL 직접 추출 결과 | 대장 + `98_` 에 추가 |
| 3 | 🟢 개선 | 가독성 | `07_*.md` | 설정값이 본문에 산재 | — | 상단으로 집약 |

심각도 정의:

| 심각도 | 기준 |
|--------|------|
| 🔴 **치명** | 실습이 실패하거나, 계정에 잔여물이 남거나, 잘못된 정보를 사실로 서술 |
| 🟡 **중요** | 규격 위반, 누락된 필수 요소, 검증 부족 |
| 🟢 **개선** | 가독성, 구성, 보강 |

**정확성 판정은 `../references/11_verification.md` 를 따른다.** "틀린 것 같다"로 지적하지 않고, 실행·컴파일·공식 문서로 확인한 뒤 지적한다.

### STEP I3. 개선 계획 제시 및 승인

**⚠️ STOP — 이 단계는 반드시 멈춘다.**

갭 분석 표를 제시하고 다음을 함께 보고한다.
- 결함 건수 (심각도별)
- 변경될 파일 목록
- 문서 추가·삭제·번호 변경이 필요한지 (아래 "문서 추가·삭제·번호 변경 규칙" 참고)
- 예상 작업 범위

사용자가 일부만 선택할 수 있게 한다.

> "🔴 치명 2건, 🟡 중요 5건, 🟢 개선 3건을 발견했습니다. 전부 반영할까요, 아니면 치명·중요만 먼저 반영할까요?"

**승인 없이 파일을 수정하지 않는다.**

### STEP I4. 개선 적용

승인된 항목만 반영한다. 다음 규율을 지킨다.

#### 최소 변경 원칙
- **부분 편집을 우선한다.** 전체 재작성은 문서가 규격을 근본적으로 위반할 때만 한다.
- 지적하지 않은 부분은 건드리지 않는다.
- 사용자가 직접 손댄 것으로 보이는 내용(주석, 메모, 커스텀 값)은 보존한다.
- 파일 삭제는 **승인받은 경우에만** 한다.

#### 규격 정렬 (Normalization)
기존 자료가 구 규격이면 다음을 보완한다. 없는 것만 추가한다.
- 메타 주석 블록 누락 → 추가
- `01_` 에 객체 대장 없음 → **폴더 전체**(`.md` 코드블록 포함)에서 객체를 추출해 작성
- `02_` 에 사전 스냅샷 없음 → 추가
- `98_리소스정리.sql` 없음 → **신규 생성** (STEP C5와 동일 기준)
- 단계 문서 말미에 정리 주석 없음 → 추가
- `99_generate_index.py` 없음 → 신규 생성
- 검증 상태 주석 없음 → 추가. **총괄 합격 선언이 있으면 제거**한다
- 계정 레벨 객체에 `CREATE OR REPLACE` → `IF NOT EXISTS` + 충돌 검사 게이트로 전환
- 스냅샷 실측값이 전사되어 있음 → 쿼리 + 빈 기록 서식으로 교체
- 부수 문서가 번호 없이 흩어져 있음 → `90_`~`94_` 로 편입 (계획·분석 문서는 제외)

#### 정확성 수정
- 수정 근거를 반드시 확보한 뒤 고친다 (`../references/11_verification.md`)
- 고친 구문은 **재검증**한다
- 검증 못 한 것은 미검증으로 표기한다 (`../references/11_verification.md`)

### STEP I5. 재검증 및 실습 완주

수정한 SQL을 `../references/11_verification.md` 에 따라 다시 검증한다. **수정했다는 사실이 정확성을 보장하지 않는다.**

**🔴 개선 범위가 `full` 또는 `accuracy` 이면 실습을 완주한다.**
`../references/30_quality-bar.md` 의 "완주 검증" 절 기준을 따른다. 기존 자료가 "검증 완료"라고 주장하고 있어도 그것을 근거로 삼지 않는다 —
그 주장 자체가 갭 분석 대상이다.

> 실측 사례: 컴파일만 통과한 자료에서 완주 시 `CREATE PROCEDURE` 절 순서 오류로
> 프로시저가 아예 생성되지 않고, 프로시저 본문의 런타임 타입 오류와
> `EXCEPTION` 핸들러에 삼켜진 조용한 실패가 드러났다.

`requires` / `next` 체인이 실제 파일과 일치하는지 확인한다.

### STEP I6. 검토 이력 누적 기록

`01_` 문서의 `## 검토 이력` 에 **새 회차를 추가**한다. 기존 이력을 지우지 않는다.
기존 회차 수를 세어 다음 번호(`<N>`)를 정한다.

```markdown
## 검토 이력

### 1차 (생성 시)
...기존 내용 유지...

### <N>차 개선 — <날짜>
개선 범위: full

| 심각도 | 위치 | 문제 | 조치 | 검증 |
|--------|------|------|------|------|
| 🔴 | `03_*.sql` | ... | ... | 컴파일 검증 |
| 🟡 | `01_*.md` | ... | ... | — |

미반영 (사용자 판단으로 보류):
- 🟢 ...
```

### STEP I7. 인덱스 재생성

```bash
cd /workspace/<TARGET_FOLDER> && python3 99_generate_index.py
```

경고가 출력되면(메타 주석 누락 등) 해결한 뒤 재실행한다.
멱등성을 확인한다 (2회 실행 결과 동일).

### STEP I8. 카탈로그 갱신 및 최종 보고

개선으로 **규격 준수 여부나 실행 검증 상태가 바뀌었다면 카탈로그
(`/workspace/00_교육자료_카탈로그.md`) 의 해당 행을 갱신한다.** 해소된 미해결 항목은 그 절에서 지운다.
자료가 구 규칙 폴더명이면 `EDU-<NN>_<slug>` 로 정렬할지 사용자에게 확인한다.


- 반영한 결함 수 (심각도별)와 **보류한 것**
- 변경된 파일 목록
- 새로 생성한 파일
- 재검증 결과 — 검증된 것 / 여전히 미검증인 것
- **개선 후에도 남아 있는 한계** (숨기지 않는다)

**⚠️ STOP**: 최종 리뷰.

### 문서 추가·삭제·번호 변경 규칙 (STEP I4 공통)

IMPROVE 모드에서 문서 구성이 바뀔 때 적용한다.

| 상황 | 처리 |
|------|------|
| 문서 **추가** — 빈 번호가 있다 | 그 번호를 사용한다. 번호 변경 불필요 — 번호는 연속일 필요가 없다 (`../references/10_output-contract.md`) |
| 문서 **추가** — 빈 번호가 없다 | 뒤쪽 문서를 재번호. `requires`/`next` 체인과 문서 내 상호 참조를 **모두** 갱신 |
| 문서 **분할** — 한 문서가 SQL/외부 작업 혼재 | `../references/10_output-contract.md` 의 분리 규칙에 따라 분리. 원본 번호를 앞쪽에 유지하고 뒤쪽에 새 번호 부여 |
| 문서 **삭제** | **승인 필수.** 번호는 비워 둔다(재번호하지 않는다 — 외부 참조 보호) |
| 문서 **이름 변경** | 다른 문서의 `requires`/`next` 와 본문 참조를 모두 갱신 |

재번호는 외부 참조(사용자 메모, 다른 문서 링크)를 깨뜨린다. **가능하면 피하고,
수행했다면 최종 보고에 명시한다.**

## Stopping Points

- ✋ I0: 대상 폴더와 개선 범위를 제시하고 승인받는다
- ✋ I3: 이 단계는 반드시 멈춘다
- ✋ I8: 최종 리뷰

> `✋ I3` (개선 계획 승인)은 **가장 중요한 중단점**이다. 이 승인 없이 파일을 수정하지 않는다.

## 공통 금지 사항 — 실행 시점

라우터의 라우팅 단계 금지 사항에 더한다.

**B. 검증 근거 — 이것을 근거로 삼지 않는다**
- **검증 단계를 생략하지 않는다**
- **모델 기억을 근거로 정확성을 주장하지 않는다**
- **검증하지 않은 구문을 검증된 것처럼 서술하지 않는다**
- **프로시저·태스크의 "성공 응답"을 검증 근거로 삼지 않는다** — 반환 메시지와 `STATE = SUCCEEDED` 는 `EXCEPTION` 핸들러에 삼켜진 실패를 가릴 수 있다. **결과 상태를 별도 쿼리로 단정한다**
- **`98_` 을 1회 실행해 성공한 것을 재실행 안전성의 근거로 삼지 않는다** — 정리 문서는 두 번 실행해 검증한다. `IF EXISTS` 는 **상위 데이터베이스·스키마 부재를 막아주지 않는다**
- **컴파일 검증만으로 완료를 보고하지 않는다** — 실습 완주(실행 → 결과 확인 → 정리 → 대조)까지
  수행하고, 못 한 부분은 이유와 함께 밝힌다 (품질 기준의 "완주 검증" 절)
- **실습 데이터가 없다는 이유로 완주를 건너뛰지 않는다** — 필요한 데이터는 직접 만든다
- **비용을 이유로 실행 검증을 생략하지 않는다** — 컴퓨트·서버리스·토큰·스토리지 비용은
  사용자가 사전 허가했다(검증 규율의 "실행 승인" 절). 단 **로그인 경로 변경·자격증명 발급·
  기존 사용자/역할 변경·계정 파라미터 변경·외부 시스템 변경**은 비용 허가와 별개로 확인받는다
- **`DROP` 워크플로를 추측해 기술하지 않는다** — 공식 문서로 확인한다
- **차단 지점(하드 블로커)을 추정으로 기술하지 않는다** — 순서대로 실행해 **처음 막히는 지점**을 실측으로 확정하고 오류 원문을 인용한다. 도달 한계까지 간 것을 "완주" 라고 부르지 않는다
**C. 서술 정직성 — 아는 것보다 크게 말하지 않는다**
- **측정하지 않은 성능·비용·효과 수치를 제시하지 않는다** — 레이턴시, 처리량, 절감률, 방어율, ROI
- **"검증 완료"·"운영 배포 가능" 류의 총괄 합격 선언을 쓰지 않는다** — 검증은 항목 단위로만 주장한다
- **이름이 비슷한 두 제품 기능을 확인 없이 동일시하지 않는다** — 성격·적용 범위를 공식 문서로 확인한다
**D. 정리·왕복 가능성 — 계정에 흔적을 남기지 않는다**
- **정리 문서(`98_`) 없이 완료로 보고하지 않는다**
- **실행 검증을 했다면 `98_` 정리와 스냅샷 대조까지 완결한다** — 비용 허가는 잔여물을 남길 허가가 아니다
- **객체 대장에 없는 객체를 실습에서 생성하지 않는다**
- **객체 추출을 `.sql` 파일로 한정하지 않는다** — `.md` 코드블록의 `CREATE`/`ALTER … SET` 도 대장 대상이다
- **정적 검색 결과만으로 객체 대장을 완성하지 않는다** — 프로시저·태스크가 **실행 중 만드는 객체**는 `grep` 에 걸리지 않는다. 계정 레벨이면 `DROP DATABASE` 로도 사라지지 않으므로 `(간접)` 으로 등재하고 `98_` 에 패턴 검색 절차를 둔다
- **사용자가 명시하지 않은 기존 Snowflake 객체를 재사용하거나 변경하지 않는다.** 제품 요구사항 때문에 불가피하게 변경해야 한다면 그것을 **대장 (b) 속성 변경 행으로 등재하고 "속성 변경(Mutation)" 절의 3단계(사전 값 기록 → 변경 지점 경고 → `98_` 원복)를 모두 수행한다.** 등재 없이 변경하는 것을 금지한다
- **`DROP` 만으로 원복되지 않는 변경을 정리 완료로 보고하지 않는다**
- **계정 기본 객체(`COMPUTE_WH`, `SNOWFLAKE`, 시스템 Role, `PUBLIC` 등)를 삭제하는 구문을 생성하지 않는다**
- **`CREATE OR REPLACE` 를 재실행 안전성의 근거로 삼지 않는다.** 계정 레벨 객체(DB/WH/Role)에는 쓰지 않는다
- **스냅샷·환경 상태의 실측값을 문서에 전사하지 않는다** — 쿼리와 빈 기록 서식을 제공한다
**E. 보안·자격증명**
- **발급한 자격증명 값을 대화·문서에 출력하지 않는다**
- **동적 SQL 의 식별자 자리를 검증 없이 문자열 결합하지 않는다** — 식별자는 바인드할 수 없으므로 패턴 검사로 방어한다. 주입 가능한 패턴을 예시로 남기지 않는다
**F. 문서 구조·번호·카탈로그**
- `00_index.md` 를 손으로 작성하지 않는다
- 폴더 밖에 파일을 흩뿌리지 않는다 (예외: 워크스페이스 카탈로그 `/workspace/00_교육자료_카탈로그.md`)
- `95_`, `96_`, `98_`, `99_` 를 다른 용도로 쓰지 않는다 (예약 번호)
- 계획·분석·진행 상황 문서를 별도 파일로 만들지 않는다 (분석은 대화와 `01_` 검토 이력에 남긴다).
  단 `90_`~`94_` 의 **부수 문서**(개념 심화, 실무 핸드오프, 운영 런북)는 허용한다 — 문서 번호 규칙 참고
- **이미 배정된 `EDU-<NN>` 번호를 바꾸지 않는다.** 폐기된 번호도 재사용하지 않는다
- **번호에 분야·난이도·수강 순서를 인코딩하지 않는다**
- **분야 태그를 하나만 달지 않는다** — 해당하는 것 전부 단다. 한 자료가 여러 분야에 걸치는 것이 정상이다
- **카탈로그에 등록하지 않고 완료로 보고하지 않는다** — 번호·제목·폴더·분야 태그·검증 상태
**G. 작업 환경**
- **`>>` 로 문서에 내용을 덧붙이지 않는다** — 이 스테이지 파일시스템에서 **조용히 실패**한다. 전체를 다시 쓰고, 쓴 뒤 **내용으로** 확인한다
