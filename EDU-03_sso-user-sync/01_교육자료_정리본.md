# SSO 및 사용자·권한 동기화 — 교육자료 정리본

## 1. 학습 목표

이 실습을 마치면 다음을 할 수 있습니다.

- 사무직군과 현장직군으로 **이원화된 계정 체계**를 하나의 Snowflake 계정에서 수용하는
  RBAC 구조를 설계하고 SQL 로 구성할 수 있다.
- `TYPE = SAML2` 시큐리티 인티그레이션으로 SSO 연동 지점을 만들고, 그것이
  **계정 로그인 페이지에 무엇을 바꾸는지** 설명할 수 있다.
- `TYPE = SCIM` 인티그레이션과 전용 프로비저닝 역할을 만들고,
  `SYSTEM$GENERATE_SCIM_ACCESS_TOKEN` 이 **실제 자격증명을 발급한다**는 점과
  그 취급 원칙을 설명할 수 있다.
- 인사 원장 테이블에 **Stream** 을 걸어 입사·부서이동·퇴사·삭제를 캡처할 수 있다.
- **스트림을 소비하는 DML** 로 offset 을 전진시켜야 하는 이유를 설명하고,
  그렇게 하지 않으면 태스크가 같은 건을 무한 재처리한다는 것을 실측으로 확인할 수 있다.
- 스트림 액션(`INSERT` / `DELETE` / `ISUPDATE`)의 조합을 해석해
  **상태 변경 퇴사와 하드 삭제 퇴사를 모두** 오프보딩 처리할 수 있다.
- `TYPE = EXTERNAL_OAUTH` 로 모바일 백엔드 연동 지점을 만들 수 있다.
- 실습이 만든 **계정 레벨 객체와 보안 상태를 전부 원복**할 수 있다.

### 완료 시 달성 상태

```
[사무직 / Entra ID]                          [현장직 / 사내 인사 DB]
   SAML2 SSO ──┐                                HR_EMPLOYEE_MASTER
   SCIM 프로비저닝 ─┤                                    │ (CDC)
                 ▼                                      ▼
          ┌──────────────────────────────────────────────────────┐
          │                    Snowflake 계정                     │
          │   KSM_ENTERPRISE_DB (BRONZE/SILVER/GOLD/            │
          │                      SERVING/OPS/SECURITY)          │
          │   HR_EMPLOYEE_STREAM → HR_STREAM_BUFFER             │
          │        → SP_SYNC_HR_EMPLOYEES                        │
          │        → CREATE/ALTER USER + GRANT ROLE              │
          │   TASK (5분) + TASK (자정 감사)                       │
          └──────────────────────────────────────────────────────┘
                                 │
                        [모바일 앱] External OAuth
```

원장에서 `UPDATE ... SET EMPLOYMENT_STATUS='RESIGNED'` 또는 `DELETE` →
다음 태스크 주기에 해당 계정이 `DISABLED = TRUE` 로 전환됩니다.

## 2. 사전 준비물

### 2.1 Snowflake 측

| 항목 | 요구사항 | 확인 방법 |
| :--- | :--- | :--- |
| 권한 | `ACCOUNTADMIN` (계정 레벨 Role/Integration/User 생성) | `SELECT CURRENT_ROLE()` |
| 접두사 여유 | `KSM_` / `AAD_` / `EMP_F` 접두사가 미사용 상태 | `95_실습전_기준선.md` 2절 |
| 서버리스 태스크 | 계정에서 서버리스 컴퓨트 사용 가능 | `07_`·`06_` 실행 시 확인 |
| 비용 승인 | 웨어하우스 + 서버리스 태스크 크레딧 | 조직 정책에 따름 |

> 🔴 **이 실습은 계정의 보안 상태를 변경합니다.** 비용과 성격이 다른 위험이므로
> 시작 전에 아래를 반드시 인지하십시오.
>
> | 변경 | 영향 |
> | :--- | :--- |
> | SAML2 인티그레이션 (`ENABLED = TRUE`) | 계정 **로그인 페이지에 SSO 버튼이 추가**됩니다. 비밀번호 로그인은 유지됩니다 |
> | `SYSTEM$GENERATE_SCIM_ACCESS_TOKEN` | `CREATE USER` / `CREATE ROLE` / `MANAGE GRANTS` 로 동작하는 **실제 베어러 토큰**이 발급됩니다 |
> | `GRANT CREATE USER` / `MANAGE GRANTS ON ACCOUNT` | 계정 사용자·권한을 조작할 수 있는 권한을 실습 역할에 위임합니다 |
> | 서버리스 태스크 2개 `RESUME` | **계정 사용자를 자동으로 `DISABLED` 시키는 태스크**가 상시 동작합니다 |
> | 동기화 프로시저 | 계정에 사용자(`EMP_F***`)를 **자동으로 생성**합니다 |
>
> 🔴 **`SSO_LOGIN_ONLY` 를 활성화하지 마십시오.** `03_` 문서에 주석 상태로
> 포함되어 있습니다. 이 실습의 인증서는 더미이므로 활성화하면 해당 사용자가
> **로그인할 수 없게 됩니다.**

### 2.2 실습 범위 밖 (미검증으로 남는 것)

| 항목 | 왜 이 실습으로 검증되지 않는가 |
| :--- | :--- |
| 실제 Entra ID SSO 로그인 왕복 | 인증서·Issuer·SSO URL 이 **더미**입니다. 인티그레이션 "생성" 만 검증됩니다 |
| 실제 JWT 로 External OAuth 인증 | RSA 공개키가 더미이며 대응 개인키가 없습니다 |
| Azure Portal SCIM 프로비저닝 동기화 | Entra ID 테넌트가 필요하며 Snowflake 외부 작업입니다 |

> ⚠️ **"인티그레이션이 생성되었다" 를 "인증이 동작한다" 로 읽지 마십시오.**
> 이전 판이 문서 제목에 `(검증 완료)` 를 붙여 이 구분을 흐렸습니다.

#### 부여되는 계정 레벨 권한

`DROP` 대상 객체는 아니지만 **계정 스코프로 위임되는 권한**이므로 함께 추적합니다.
해당 Role 을 `DROP` 하면 이 부여도 함께 사라지므로 별도 `REVOKE` 는 필요 없습니다.
다만 **무엇을 위임했는지 알지 못하면 위험을 평가할 수 없으므로** 등재합니다.

| 권한 | 부여 대상 Role | 문서 | 왜 필요한가 |
| :--- | :--- | :---: | :--- |
| `CREATE USER ON ACCOUNT` | `KSM_HR_SYNC_ADMIN` | `02_` | 동기화 프로시저가 사번별 사용자를 생성 |
| `MANAGE GRANTS ON ACCOUNT` | `KSM_HR_SYNC_ADMIN` | `02_` | 생성한 사용자에게 직군 Role 을 부여 |
| `EXECUTE TASK`, `EXECUTE MANAGED TASK ON ACCOUNT` | `KSM_HR_SYNC_ADMIN` | `02_` | 서버리스 태스크 실행 |
| `CREATE USER ON ACCOUNT` | `AAD_PROVISIONING_ROLE` | `04_` | SCIM 이 Entra ID 사용자를 프로비저닝 |
| **`CREATE ROLE ON ACCOUNT`** | `AAD_PROVISIONING_ROLE` | `04_` | SCIM 이 Entra ID 보안 그룹을 Role 로 생성 |
| `MANAGE GRANTS ON ACCOUNT` | `AAD_PROVISIONING_ROLE` | `04_` | 프로비저닝한 사용자에 Role 부여 |

> 🔴 **`CREATE ROLE ON ACCOUNT` 은 이 표에 2026-09-17 에 추가되었습니다.**
> 이전 판은 `AAD_PROVISIONING_ROLE` 객체만 대장에 두고 그 역할에 위임한
> 계정 레벨 권한을 나열하지 않았습니다. 이 권한이 있으면 **SCIM 프로비저닝이
> 계정에 Role 을 만들 수 있습니다.** 실제 Entra ID 테넌트와 연결해 실습을
> 확장했다면 `SHOW ROLES` 로 예상하지 못한 Role 이 생기지 않았는지 확인하고,
> `98_` 의 패턴 검색 절차로 정리하십시오.

#### 2-3. 🔴 실행으로 재현한 결함

**[결함 1] 스트림이 소비되지 않아 무한 재처리**

프로시저가 스트림을 **커서 `SELECT`** 로만 읽었습니다. Snowflake Stream 의 offset 은
**그 Stream 을 소비하는 DML** 안에서만 전진합니다.

| 관측 | 값 |
| :--- | :--- |
| `CALL` 1회 / 2회 반환 | 둘 다 `총 4건 처리됨` (동일) |
| 2회 후 `SYSTEM$STREAM_HAS_DATA` | `TRUE` (전진하지 않음) |
| `HR_SYNC_AUDIT_LOG` 행 수 | 4행 → **8행** (`EMP_F002` 2행 중복) |

영향: 5분 주기 태스크가 동일 건을 영구 재처리 → 서버리스 크레딧 지속 소모 +
`CREATE USER`/`ALTER USER`/`GRANT` 반복 발행 + 감사 로그 오염.

> 부수 관측: `CREATE TABLE AS SELECT ... FROM <stream>` 도 스트림을 소비합니다.
> 스키마만 복제할 의도로 `WHERE 1=0` CTAS 를 쓰면 **행은 0개인데 스트림이 비워집니다.**

**[결함 2] 자정 감사 프로시저가 항상 실패 (조용한 실패)**

`INSERT ... VALUES` 안에서 커서 레코드 필드를 직접 참조했습니다.

```sql
VALUES ('RESIGNED_VERIFICATION', :v_user_name, '... (' || r.EMP_NAME || ')', 'AUTO_DISABLED');
```

실제 오류: `SQL compilation error: invalid identifier 'R.EMP_NAME'`

`EXCEPTION WHEN OTHER THEN RETURN '...'` 핸들러가 오류를 삼켜 **정상 반환처럼
보였고**, `HR_SECURITY_AUDIT_REPORT` 는 조용히 0행으로 남았습니다.
매일 자정 태스크가 "실행 성공" 으로 기록되면서 실제로는 아무 감사도 하지 않았습니다.

**[결함 3] 인사 원장에서 `DELETE` 된 직원의 계정이 차단되지 않음**

커서가 `WHERE METADATA$ACTION = 'INSERT'` 로 필터했습니다.
순수 `DELETE` 는 스트림에 `DELETE` 액션 1행만 남기므로 무시되었습니다.

| 단계 | 관측 |
| :--- | :--- |
| `DELETE FROM HR_EMPLOYEE_MASTER WHERE EMP_ID='EMP_F003'` | 스트림 `EMP_F003 / DELETE / ISUPDATE=FALSE` 1행 |
| `CALL` 후 `SHOW USERS LIKE 'EMP_F003'` | **`disabled = false`** (활성 잔존) |

**스트림 액션 실측 (결함 3 정정 로직의 근거)**

| 원장 변경 | 스트림 결과 |
| :--- | :--- |
| `INSERT` | `INSERT` 1행 (`ISUPDATE=FALSE`) |
| `UPDATE` | `DELETE` + `INSERT` 2행 (`ISUPDATE=TRUE`) |
| `DELETE` | `DELETE` 1행 (`ISUPDATE=FALSE`) |

**[결함 4 · 🟡] 시나리오 검증이 결정적이지 않다**

Step 5 가 5분 주기 태스크를 `RESUME` 한 상태에서 Step 7 이 같은 스트림을 수동
`CALL` 했습니다. 시나리오를 결정적으로 검증하려면 **Step 7 전에 `SUSPEND`** 해야 합니다.

#### 4-0. `98_` 실행 검증에서 추가로 발견한 결함 (12번째)

| ⚠️ | `06_` 핸들러 (한계) | `EXCEPTION WHEN OTHER` 가 **`DECLARE` 절 커서의 테이블 부재를 잡지 못한다.** 이름 해석이 `BEGIN` 보다 먼저 일어난다 | 정정 대상이 아니라 한계이므로 문서에 명시. 태스크 운영 시 감사 테이블만 보지 말고 `TASK_HISTORY.ERROR_MESSAGE` 도 확인하도록 안내 | **실제 실행** — 원본 테이블 이름 변경 후 CALL → 컴파일 오류가 그대로 올라오고 감사 테이블 FAILED **0행** |

> 📌 `:SQLERRM` 결함은 2차 회차의 [결함 2](`r.EMP_NAME` 콜론 누락)와 **같은 뿌리**다.
> 그때 커서 필드는 고쳤지만 같은 규칙이 적용되는 `SQLERRM` 을 놓쳤다.
> 그리고 이 결함은 **정상 경로 실행으로는 절대 드러나지 않는다** — 예외를
> 의도적으로 일으켜 핸들러를 실행해야 보인다.

#### 도메인 스킬 대조 결과

`CREATE SECURITY INTEGRATION` 3종의 파라미터명은 공식 문서와 일치했다
(`TYPE = SAML2` / `SCIM` + `SCIM_CLIENT` + `RUN_AS_ROLE` / `EXTERNAL_OAUTH` 계열).
정정한 것은 파라미터 **값 선택**(`ANY_ROLE_MODE`)이며 문법 오류는 없었다.
SCIM 토큰 취급(값 미출력, `LENGTH()` 만 확인, 쿼리 이력 경고)도 규격을 충족했다.

미반영: 없음 (승인된 6건 + 실행 중 발견 2건 전부 반영)

**여전히 미검증인 항목** — 전부 Snowflake 외부 요건이며 자료 결함이 아니다.
