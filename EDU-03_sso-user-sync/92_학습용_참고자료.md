# [학습용 참고자료] Snowflake SSO, SCIM, 데이터 파이프라인 및 모바일 인증 핵심 개념

본 문서는 **Snowflake 하이브리드 계정 연동 및 자동 프로비저닝 가이드**를 깊이 있게 이해하고 실무에 적용하기 위해 필요한 핵심 기술 표준과 Snowflake 플랫폼의 보안/파이프라인 메커니즘을 정리한 학습용 참고자료입니다.

---

## 1. SSO(Single Sign-On) 및 SAML 2.0 동작 원리

### 1.1 SSO(Single Sign-On)란?
사용자가 한 번의 로그인(인증)으로 여러 독립된 소프트웨어 시스템이나 클라우드 서비스에 재인증 없이 접근할 수 있도록 해주는 중앙 집중식 인증 기술입니다.

### 1.2 SAML 2.0 (Security Assertion Markup Language)
기업 환경에서 가장 널리 사용되는 XML 기반의 개방형 표준 인증 프로토콜입니다.

```
[사용자 브라우저]
       │ 1. Snowflake 접속 (로그인 요청)
       ▼
┌──────────────────┐  2. SAML Request (리다이렉트)   ┌──────────────────┐
│ Service Provider │ ──────────────────────────────▶ │ Identity Provider│
│  (Snowflake)     │                                 │ (Entra ID / Okta)│
│                  │  4. SAML Assertion 토큰 제출     │                  │
│                  │ ◀────────────────────────────── │ (2FA/MFA 사내인증)│
└──────────────────┘  (X.509 인증서 서명 검증)         └──────────────────┘
```

* **주요 구성 요소:**
  * **IdP (Identity Provider, 신원 제공자):** 사용자의 신원을 인증하고 증명서를 발급하는 주체 (예: Microsoft Entra ID, Okta, PingFederate 등).
  * **SP (Service Provider, 서비스 제공자):** IdP의 인증 결과를 신뢰하고 서비스를 제공하는 주체 (예: Snowflake).
  * **SAML Assertion (어설션):** IdP가 사용자의 신원(이메일, 사번, 이름 등)과 인증 성공 사실을 암호화하여 서명한 XML 토큰.
  * **X.509 인증서:** IdP가 발행한 SAML Assertion이 위조되지 않았음을 Snowflake(SP)가 공개키 기반으로 검증하기 위한 암호화 인증서.
* **SP-Initiated vs IdP-Initiated SSO:**
  * **SP-Initiated:** 사용자가 Snowflake URL(`https://<account>.snowflakecomputing.com`)에 직접 접근하여 사내 로그인 버튼을 누르면 Entra ID 로그인 창으로 이동하는 방식 (본 실습의 표준).
  * **IdP-Initiated:** 사용자가 Microsoft 365 포털(MyApps)에서 Snowflake 아이콘을 클릭하여 접속하는 방식.

## 2. SCIM 2.0 (사용자/그룹 자동 프로비저닝)

### 2.1 SCIM (System for Cross-domain Identity Management)이란?
클라우드 서비스 간에 **사용자 계정 생성, 수정, 삭제(비활성화), 그룹/역할 할당**을 표준화된 REST API로 자동화하기 위한 IETF 개방형 표준 규격입니다.

### 2.2 SSO와 SCIM의 결정적 차이
| 구분 | SAML 2.0 (SSO) | SCIM 2.0 (프로비저닝) |
| :--- | :--- | :--- |
| **목적** | **인증 (Authentication)**: 사용자가 본인이 맞는지 확인 | **신원 관리 (Identity Lifecycle)**: 계정 및 권한 동기화 |
| **동작 시점** | 사용자가 **로그인을 시도하는 순간** 동작 | 사내 인사/Entra ID에서 **사용자 정보가 변경되는 즉시** 백그라운드 푸시 |
| **퇴사자 처리** | 로그인을 시도하지 않으면 Snowflake는 퇴사 여부를 모름 | 퇴사 처리 즉시 Entra ID가 Snowflake 계정을 `DISABLED=true`로 변경 |

### 2.3 Snowflake에서의 SCIM 동작 방식
1. Snowflake에서 `TYPE = SCIM`인 `SECURITY INTEGRATION`을 생성하고 Bearer Token을 발급받습니다.
2. Entra ID에 테넌트 URL과 토큰을 등록하면, Entra ID가 사용자/그룹 변동 시 Snowflake의 `/scim/v2/Users`, `/scim/v2/Groups` 엔드포인트를 호출하여 `CREATE USER`, `ALTER USER`, `GRANT ROLE`을 자동으로 수행합니다.

## 3. Snowflake 보안 객체: Security Integration

`SECURITY INTEGRATION`은 Snowflake와 외부 인증/보안 시스템 간의 통신 신뢰 관계(Trust Relationship)를 정의하는 Snowflake 최상위 보안 관리 객체입니다.

```sql
-- Snowflake가 지원하는 주요 보안 인티그레이션 유형
1. TYPE = SAML2          -- 기업 IdP와의 SSO 로그인 연동
2. TYPE = SCIM           -- Entra ID / Okta와의 계정/역할 자동 프로비저닝
3. TYPE = EXTERNAL_OAUTH -- 사내 API Gateway, 모바일 앱 백엔드와의 OAuth 토큰 검증
4. TYPE = OAUTH          -- BI 도구(Tableau, PowerBI) 및 커넥터 연동용 내장 OAuth
```

* **보안적 이점:** 데이터베이스 내부 SQL 계정 비밀번호를 외부에 노출하거나 저장할 필요 없이, 표준 토큰 기반의 무암호(Passwordless) 인증을 구현할 수 있습니다.

## 4. 사내 인사 DB 연동: CDC(Change Data Capture) 및 파이프라인

사내 현장직은 Entra ID가 없으므로, Snowflake의 **네이티브 데이터 파이프라인 3요소(Table + Stream + Task)**를 결합하여 자율 프로비저닝 엔진을 구축합니다.

```
[HR_EMPLOYEE_MASTER (원장 테이블)]
                 │
                 ▼ (신규 입사 / 부서이동 / 퇴사 발생)
       [HR_EMPLOYEE_STREAM (CDC 변경 감지)]
                 │
                 ▼ (SYSTEM$STREAM_HAS_DATA 감지 시 자동 트리거)
[TASK_SYNC_HR_TO_SNOWFLAKE_USERS (Serverless Task)]
                 │
                 ▼ (동적 DDL 실행: CREATE USER / ALTER USER / DISABLED)
     [SP_SYNC_HR_EMPLOYEES (저장 프로시저)]
```

### 4.1 Stream (변경 데이터 캡처, CDC)
* 테이블의 변경 이력(Insert, Update, Delete)을 오프셋 기반으로 추적하는 경량 객체입니다.
* `METADATA$ACTION` ('INSERT' / 'DELETE') 및 `METADATA$ISUPDATE` 메타데이터 컬럼을 제공하여 어떤 직원의 정보가 어떻게 바뀌었는지 정확히 식별합니다.

### 4.2 Stored Procedure (저장 프로시저)
* Snowflake SQL Scripting 또는 Python을 사용하여 절차적 로직(조건문, 반복문, 커서, 예외 처리)을 수행합니다.
* `EXECUTE IMMEDIATE`를 통해 동적으로 `CREATE USER`, `ALTER USER SET DISABLED=TRUE`, `GRANT ROLE` DDL을 실행합니다.

### 4.3 Task (스케줄링 엔진) & Serverless Compute
* **이벤트 기반 실행:** `WHEN SYSTEM$STREAM_HAS_DATA('스트림명')` 조건을 지정하여, 인사 데이터 변경이 있을 때만 서버리스(Serverless)로 구동되어 컴퓨팅 비용을 극소화합니다.
* **CRON 정주기 실행:** `SCHEDULE = 'USING CRON 0 0 * * * Asia/Seoul'`을 통해 매일 자정에 퇴사자 잔존 여부를 전수 검사합니다.

## 5. 모바일 앱 연동 및 AI 챗봇 API 보안 아키텍처

### 5.1 왜 모바일 앱이 Snowflake에 직접 연결하면 안 되는가?
* **보안 위험:** 모바일 앱 바이너리에 DB 접속 계정이나 비밀번호가 하드코딩될 경우 디컴파일을 통해 탈취될 위험이 있습니다.
* **커넥션 과부하:** 수천 명의 현장 작업자가 동시에 모바일 앱을 켤 경우 DB 세션 수가 급증하여 성능 저하가 발생합니다.

### 5.2 권장 아키텍처: BFF (Backend-for-Frontend) 패턴
모바일 앱은 기존 사내 모바일 API Gateway(BFF)와만 통신하고, 백엔드 서버가 안전하게 Snowflake Cortex AI API를 호출합니다.

```
┌─────────────────┐       (1) 사번 + PIN/생체인증        ┌──────────────────────┐
│  사내 모바일 앱    │ ──────────────────────────────▶ │ 모바일 BFF 백엔드 서버 │
│ (현장 작업자 UI)  │ ◀────────────────────────────── │ (API Gateway)        │
└─────────────────┘       (4) 정제된 AI 답변 반환        └──────────┬───────────┘
                                                            │ (2) RSA Key 서명 JWT /
                                                            │     External OAuth 토큰
                                                            ▼ (3) Cortex Search API 호출
                                                ┌──────────────────────────────┐
                                                │ Snowflake Cortex AI Platform │
                                                │ (설비/공정 지식 검색 & RAG)   │
                                                └──────────────────────────────┘
```

* **인증 방식 비교:**
  * **RSA Key-Pair 인증:** 모바일 백엔드 서비스 계정이 비대칭키(Private Key)로 JWT 토큰을 서명하여 Snowflake REST API를 호출 (가장 안정적이고 권장되는 방식).
  * **External OAuth:** 사내 중앙 인증 서버(Keycloak, Okta 등)가 발급한 사용자별 Access Token을 Snowflake가 직접 검증하여 작업자 개인 식별 컨텍스트를 유지하는 방식.

## 6. RBAC (역할 기반 접근 제어) 및 거버넌스 핵심 원칙

1. **최소 권한의 원칙 (Least Privilege):**
   * 현장 작업자(`KSM_FACTORY_WORKER_ROLE`)는 본인의 공장 설비 매뉴얼과 안전 지침만 조회할 수 있으며, 전사 재무/인사 데이터에는 접근 권한이 원천 차단됩니다.
2. **역할 계층 구조 (Role Hierarchy):**
   * 하위 역할의 권한이 상위 역할(`SYSADMIN`, `ACCOUNTADMIN`)로 자연스럽게 상속되도록 설계하여 권한 관리 복잡도를 낮춥니다.
3. **즉각적 오프보딩 (Immediate Offboarding):**
   * 퇴사 시 계정 삭제(`DROP USER`)보다는 `DISABLED = TRUE` 및 `PASSWORD = NULL` 처리를 통해 기존 작업 이력과 감사 로그(Audit Trail)의 참조 무결성을 보존하면서 접근을 즉시 차단하는 것이 엔터프라이즈 보안 표준입니다.
