> 📌 **이 문서는 `93.성능검증_및_성과보고서.md` 를 대체합니다.**
>
> 이전 문서는 레이턴시·처리량·절감률·ROI 수치를 제시했으나 **측정 절차가
> 문서에 없었고 근거를 재현할 수 없었습니다.** 실제로 2026-09-16 실행 검증에서는
> 자정 감사 프로시저가 **항상 실패**하고 있었으므로, 그 상태에서 산출된
> "효과" 수치는 성립할 수 없습니다.
>
> 따라서 수치 주장을 전부 제거하고 **"직접 측정하는 방법"** 으로 대체했습니다.
> 자기 환경에서 측정한 값만 근거로 쓰십시오.

> ⚠️ 이 문서의 쿼리는 **실습 리소스가 존재하는 동안에만** 결과를 냅니다.

## 1. 무엇을 관측해야 하는가

| 관측 대상 | 왜 중요한가 | 절 |
| :--- | :--- | :---: |
| 동기화 지연 (원장 변경 → 계정 반영) | 오프보딩이 늦으면 퇴사자가 접근 가능한 창이 생긴다 | 2 |
| 태스크 실행 성공률 | 실패가 조용히 누적되면 동기화가 멈춘 것을 모른다 | 3 |
| 스트림 적체 | offset 이 전진하지 않으면 같은 건을 반복 처리한다 | 4 |
| 보류·실패 건수 | 미정의 상태나 식별자 거부가 쌓이는지 | 5 |
| 서버리스 크레딧 | 5분 주기 태스크의 실제 비용 | 6 |
| 감사 커버리지 | 자정 감사가 실제로 동작했는지 | 7 |

## 2. 동기화 지연 측정

원장 변경 시각과 계정 반영 시각의 차이를 봅니다.

```sql
SELECT
    a.EMP_ID,
    a.ACTION_TYPE,
    m.LAST_UPDATED_AT              AS 원장_변경시각,
    a.EXECUTED_AT                  AS 계정_반영시각,
    TIMESTAMPDIFF('second', m.LAST_UPDATED_AT, a.EXECUTED_AT) AS 지연_초
FROM KSM_ENTERPRISE_DB.SILVER.HR_SYNC_AUDIT_LOG a
LEFT JOIN KSM_ENTERPRISE_DB.BRONZE.HR_EMPLOYEE_MASTER m
       ON m.EMP_ID = a.EMP_ID
WHERE a.STATUS = 'SUCCESS'
ORDER BY a.LOG_ID DESC
LIMIT 50;
```

| 측정 항목 | 내 환경의 값 |
| :--- | :--- |
| 지연 중앙값(초) | |
| 지연 최댓값(초) | |
| 측정 기간 | |
| 측정 건수 | |

> ⚠️ **이 값은 스케줄 주기에 지배됩니다.** 5분 주기 태스크라면 지연의 하한은
> 0초, 상한은 약 5분 + 실행 시간입니다. 하드 삭제 오프보딩도 같은 주기를 탑니다.
> 더 짧은 지연이 필요하면 주기를 줄이거나 트리거 방식을 검토하십시오
> (주기를 줄이면 크레딧이 늘어납니다 — 6절).
>
> 🔴 **`LAST_UPDATED_AT` 은 원장이 채우는 값입니다.** 소스 인사 시스템이 이 열을
> 갱신하지 않으면 이 측정은 무의미합니다. 또한 하드 삭제(`DELETE`)된 행은
> 조인 대상이 없어 `원장_변경시각` 이 `NULL` 이 됩니다.

## 3. 태스크 실행 성공률

```sql
SELECT
    NAME,
    STATE,
    COUNT(*)                                    AS 실행_수,
    MIN(SCHEDULED_TIME)                         AS 최초,
    MAX(SCHEDULED_TIME)                         AS 최근
FROM TABLE(KSM_ENTERPRISE_DB.INFORMATION_SCHEMA.TASK_HISTORY(
        SCHEDULED_TIME_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP())))
WHERE NAME IN ('TASK_SYNC_HR_TO_SNOWFLAKE_USERS', 'TASK_DAILY_MIDNIGHT_HR_AUDIT')
GROUP BY NAME, STATE
ORDER BY NAME, STATE;
```

| `STATE` | 의미 | 정상인가? |
| :--- | :--- | :--- |
| `SUCCEEDED` | 실행 완료 | ✅ |
| `SKIPPED` (`0040003`) | `WHEN` 조건이 FALSE — 스트림에 변경이 없었다 | ✅ **정상이며 바람직하다.** 컴퓨트를 쓰지 않는다 |
| `FAILED` | 실행 실패 | 🔴 조사 필요 |
| `SUSPENDED_...` | 연속 실패로 자동 중단 | 🔴 즉시 조사 |

> 📌 `SKIPPED` 비율이 높은 것은 **좋은 신호**입니다. 스트림이 정상적으로 소비되고
> 있다는 뜻입니다. 반대로 `SUCCEEDED` 가 매 주기 나타나면서 처리 건수가 0 이면
> 스트림이 소비되지 않고 있을 가능성을 의심하십시오 (4절).

> ⚠️ `TASK_HISTORY` 의 `RETURN_VALUE` 는 `NULL` 로 나옵니다. 프로시저 `RETURN` 값은
> 자동으로 실리지 않으며 `SYSTEM$SET_RETURN_VALUE` 가 필요합니다.

## 4. 스트림 적체 — 무한 재처리 조기 경보

```sql
-- 미소비 변경이 남아 있는가
SELECT SYSTEM$STREAM_HAS_DATA('KSM_ENTERPRISE_DB.BRONZE.HR_EMPLOYEE_STREAM') AS HAS_DATA;

-- 같은 사번이 반복 처리되고 있지 않은가 (무한 재처리 징후)
SELECT EMP_ID, ACTION_TYPE, COUNT(*) AS 처리_횟수
FROM KSM_ENTERPRISE_DB.SILVER.HR_SYNC_AUDIT_LOG
GROUP BY EMP_ID, ACTION_TYPE
HAVING COUNT(*) > 3
ORDER BY 처리_횟수 DESC;
```

| 관측 | 판정 |
| :--- | :--- |
| 태스크 실행 직후 `HAS_DATA = FALSE` | ✅ offset 이 정상 전진 |
| 태스크 실행 직후에도 `HAS_DATA = TRUE` 가 지속 | 🔴 스트림이 소비되지 않는다 |
| 동일 사번·동일 액션이 계속 증가 | 🔴 무한 재처리 |

> 🔴 **이것이 이 자료에서 실제로 발생했던 결함입니다.** 프로시저가 스트림을
> 커서 `SELECT` 로만 읽으면 offset 이 전진하지 않아 5분마다 같은 건을 영구
> 재처리합니다. 정정형은 버퍼 테이블에 `INSERT ... SELECT FROM <stream>` 으로
> **먼저 소비**합니다. `06_` 문서 [결함 1] 을 보십시오.

배치 단위 소비 이력은 버퍼에서 직접 확인할 수 있습니다.

```sql
SELECT BATCH_ID, COUNT(*) AS 소비_행수, MIN(CONSUMED_AT) AS 소비시각
FROM KSM_ENTERPRISE_DB.OPS.HR_STREAM_BUFFER
GROUP BY BATCH_ID ORDER BY 소비시각 DESC LIMIT 20;
```

## 5. 보류·실패 건수

```sql
SELECT ACTION_TYPE, STATUS, COUNT(*) AS 건수, MAX(EXECUTED_AT) AS 최근
FROM KSM_ENTERPRISE_DB.SILVER.HR_SYNC_AUDIT_LOG
GROUP BY ACTION_TYPE, STATUS
ORDER BY 건수 DESC;
```

| `ACTION_TYPE` | 의미 | 대응 |
| :--- | :--- | :--- |
| `SYNC_ACTIVE_USER` | 재직자 계정 생성·갱신 | — |
| `DISABLE_USER_OFFBOARDING` | 상태 변경(RESIGNED/SUSPENDED) 차단 | — |
| `DISABLE_USER_HARD_DELETE` | 원장에서 행이 삭제되어 차단 | 의도한 오프보딩인지 확인 |
| `SKIPPED_UNKNOWN_STATUS` | 정의되지 않은 `EMPLOYMENT_STATUS` | 🟡 **상태값이 늘었다.** 프로시저 분기를 확장하십시오 |
| `REJECTED_UNSAFE_IDENTIFIER` | 사번·역할명이 허용 패턴을 벗어남 | 🔴 원장 데이터 오염 조사 |
| `ERROR` | 예외 발생 | 🔴 `ERROR_MESSAGE` 확인 |

```sql
-- 실패 상세
SELECT EMP_ID, ACTION_TYPE, ERROR_MESSAGE, EXECUTED_AT
FROM KSM_ENTERPRISE_DB.SILVER.HR_SYNC_AUDIT_LOG
WHERE STATUS = 'FAILED' ORDER BY LOG_ID DESC LIMIT 50;
```

> 🔴 **예외로 실패한 배치는 스트림에서 다시 읽을 수 없습니다.** 이미 소비되었기
> 때문입니다. `HR_STREAM_BUFFER` 에서 해당 `BATCH_ID` 로 재처리해야 합니다.
> 운영에 올릴 때는 이 재처리 경로를 반드시 준비하십시오.

## 6. 서버리스 크레딧 측정

```sql
SELECT
    DATE_TRUNC('day', START_TIME) AS 일자,
    NAME,
    COUNT(*)                      AS 실행_수,
    SUM(CREDITS_USED)             AS 크레딧
FROM SNOWFLAKE.ACCOUNT_USAGE.SERVERLESS_TASK_HISTORY
WHERE START_TIME >= DATEADD('day', -14, CURRENT_TIMESTAMP())
GROUP BY 1, 2 ORDER BY 1 DESC, 2;
```

| 측정 항목 | 내 환경의 값 |
| :--- | :--- |
| 일일 크레딧 (동기화 태스크) | |
| 일일 크레딧 (자정 감사 태스크) | |
| 측정 기간 | |

> ⚠️ `ACCOUNT_USAGE` 뷰는 **지연 반영**됩니다(수 시간). 실습 직후에는 0행일 수
> 있으며 이는 정상입니다. 뷰가 계정에 없으면 `SHOW TASKS` 와
> `TASK_HISTORY` 의 실행 횟수로 대체 추정하십시오.
>
> 🔴 **`SKIPPED` 실행은 컴퓨트를 쓰지 않습니다.** 따라서 스트림 소비가
> 정상 동작하면 크레딧은 "5분마다 실행" 이 아니라 "변경이 있을 때만" 발생합니다.
> 4절의 결함이 있으면 크레딧이 상시 발생합니다 — 비용 지표가 결함의 신호가 됩니다.

## 7. 감사 커버리지 — 자정 감사가 실제로 동작했는가

```sql
SELECT DATE_TRUNC('day', REPORTED_AT) AS 일자,
       AUDIT_TYPE, ACTION_TAKEN, COUNT(*) AS 건수
FROM KSM_ENTERPRISE_DB.SILVER.HR_SECURITY_AUDIT_REPORT
GROUP BY 1, 2, 3 ORDER BY 1 DESC;
```

> 🔴 **"태스크가 성공했다" 와 "감사가 수행되었다" 는 다릅니다.**
> 이 자료에서 실제로 발생한 결함이 그것입니다. 프로시저의 `EXCEPTION` 핸들러가
> 오류를 삼켜 정상 반환처럼 보였고, 태스크 이력은 `SUCCEEDED` 였지만
> **보고서는 0행**이었습니다.
>
> 따라서 태스크 성공률(3절)만 보지 말고 **보고서에 행이 늘고 있는지**를 함께
> 확인해야 합니다. 아래가 조기 경보 쿼리입니다.

```sql
-- 자정 감사가 최근 실행되었는데 보고서가 비어 있으면 조용한 실패다
SELECT
    (SELECT COUNT(*) FROM TABLE(KSM_ENTERPRISE_DB.INFORMATION_SCHEMA.TASK_HISTORY(
        SCHEDULED_TIME_RANGE_START => DATEADD('day', -2, CURRENT_TIMESTAMP())))
     WHERE NAME = 'TASK_DAILY_MIDNIGHT_HR_AUDIT' AND STATE = 'SUCCEEDED') AS 태스크_성공_수,
    (SELECT COUNT(*) FROM KSM_ENTERPRISE_DB.SILVER.HR_SECURITY_AUDIT_REPORT
     WHERE REPORTED_AT >= DATEADD('day', -2, CURRENT_TIMESTAMP()))         AS 보고서_행수;
--   태스크_성공_수 > 0 인데 보고서_행수 = 0 이면 🔴 조용한 실패를 의심하십시오
--   (단, 퇴사자가 실제로 0명이면 정상입니다 — 원장을 함께 확인하십시오)
```

## 8. 운영에 올리기 전 보완 항목

이 실습 구성은 학습용이며, 운영에는 아래가 추가로 필요합니다.

| 항목 | 이유 |
| :--- | :--- |
| 실패 알림 (이메일·웹훅) | `EXCEPTION` 핸들러가 오류를 삼키므로 감사 로그만으로는 아무도 모릅니다 |
| 실패 배치 재처리 경로 | 스트림은 이미 소비되었습니다. `BATCH_ID` 기반 재처리가 필요합니다 |
| `EXTERNAL_OAUTH_ANY_ROLE_MODE` 재검토 | 실습은 `'ENABLE'` 입니다. 최소 권한과 상충합니다 |
| 계정 레벨 권한 위임 축소 | `MANAGE GRANTS ON ACCOUNT` 은 과도합니다. 필요한 역할에 한정하십시오 |
| 프로시저 소유권·`EXECUTE AS` 검토 | 실습은 `EXECUTE AS CALLER` 입니다 |
| 동적 SQL 식별자 검증 강화 | 현재는 `RLIKE` 패턴 검사입니다. 원장 데이터 신뢰 경계를 정의하십시오 |
| 상태값 사전(Dictionary) 관리 | `SKIPPED_UNKNOWN_STATUS` 가 쌓이면 원장 상태값이 늘어난 것입니다 |

> **이 문서는 배포 가능 여부를 판정하지 않습니다.** 위 항목의 충족 여부는
> 각 조직의 보안 기준에 따라 판단하십시오.
