## 3. 🔴 실행으로 재현한 결함 3건

> 이 3건은 **컴파일 검증이나 문서 대조로는 잡히지 않는다.** 실제로 실행해야 드러난다.
> 원본 문서는 "1~7단계 전체 실행 및 엔드투엔드 검증 완료" 라고 서술하고 있었다.

### [결함 1] 스트림이 소비되지 않아 무한 재처리 — `SP_SYNC_HR_EMPLOYEES`

**원인.** 프로시저가 스트림을 **커서 `SELECT`** 로만 읽는다. Snowflake Stream 의
offset 은 **그 Stream 을 소비하는 DML** 안에서만 전진한다. 조회만으로는 움직이지 않는다.

**재현 근거.**

| 관측 | 값 |
| :--- | :--- |
| `CALL` 1회 반환 | `인사 DB 동기화 완료: 총 4건 처리됨` |
| `CALL` 2회 반환 | `인사 DB 동기화 완료: 총 4건 처리됨` (동일) |
| 2회 후 `SYSTEM$STREAM_HAS_DATA` | `TRUE` (전진하지 않음) |
| `HR_SYNC_AUDIT_LOG` 행 수 | 4행 → **8행** |
| `EMP_F002` 감사 로그 행 수 | **2행** (중복) |

**영향.** 5분 주기 `TASK_SYNC_HR_TO_SNOWFLAKE_USERS` 가 동일 4건을 영구 재처리한다.
→ 서버리스 크레딧 지속 소모 + `CREATE USER`/`ALTER USER`/`GRANT` 반복 발행 + 감사 로그 오염.

**검증된 수정 패턴.** 스트림을 먼저 스테이징 테이블로 소비한 뒤 그 결과를 처리한다.

```sql
INSERT INTO <버퍼>
SELECT ..., METADATA$ACTION, METADATA$ISUPDATE
FROM KSM_ENTERPRISE_DB.BRONZE.HR_EMPLOYEE_STREAM;
```

실행 결과: 버퍼 2행 적재, `SYSTEM$STREAM_HAS_DATA` → **`FALSE`** (offset 전진 확인).

> 부수 관측: `CREATE TABLE AS SELECT ... FROM <stream>` 도 스트림을 소비한다.
> 스키마만 복제할 의도로 `WHERE 1=0` CTAS 를 쓰면 **행은 0개인데 스트림이 비워진다.**

### [결함 2] 자정 감사 프로시저가 항상 실패 — `SP_AUDIT_DORMANT_AND_RESIGNED_USERS`

**원인.** `INSERT ... VALUES` 안에서 커서 루프 레코드 필드를 직접 참조했다.

```sql
-- 구 (실패)
VALUES ('RESIGNED_VERIFICATION', :v_user_name,
        '... (' || r.EMP_NAME || ')', 'AUTO_DISABLED');
```

**실제 오류.**

```
SQL compilation error: error line 2 at position 86
invalid identifier 'R.EMP_NAME'
```

커서 레코드 필드는 SQL 문 안에서 쓸 수 없다. 지역 변수에 담아 `:변수` 로 바인드해야 한다.

**왜 아무도 몰랐는가.** `EXCEPTION WHEN OTHER THEN RETURN '...오류 발생: ' || SQLERRM`
핸들러가 오류를 삼켜 **프로시저가 정상 반환한 것처럼 보인다.**
`HR_SECURITY_AUDIT_REPORT` 는 조용히 0행으로 남았다.
매일 자정 태스크가 계속 "실행 성공" 으로 기록되면서 실제로는 아무 감사도 하지 않는다.

**검증된 수정.** `v_emp_name` / `v_details` 지역 변수 바인드 → 재실행 시
`자정 계정 보안 감사 완료: 총 1명 검증 및 조치 완료`, 보고서 1행 적재 확인.

### [결함 3] 인사 원장에서 `DELETE` 된 직원의 계정이 차단되지 않는다

**원인.** 프로시저 커서가 `WHERE METADATA$ACTION = 'INSERT'` 로 필터한다.
순수 `DELETE` 는 스트림에 `DELETE` 액션 1행만 남기므로 무시된다.

**재현 근거.**

| 단계 | 관측 |
| :--- | :--- |
| `DELETE FROM HR_EMPLOYEE_MASTER WHERE EMP_ID='EMP_F003'` | 스트림: `EMP_F003 / DELETE / ISUPDATE=FALSE` 1행 |
| `CALL SP_SYNC_HR_EMPLOYEES()` 후 `SHOW USERS LIKE 'EMP_F003'` | **`disabled = false`** (활성 잔존) |

**영향.** 오프보딩 누락. 인사 시스템에서 레코드를 삭제하는 방식으로 퇴사를 처리하는
조직에서는 **계정이 영구히 살아남는다.** 보안 실습의 핵심 목표가 달성되지 않는다.

**참고 — 스트림 액션 실측 정리.**

| 원장 변경 | 스트림 결과 |
| :--- | :--- |
| `INSERT` | `INSERT` 1행 (`ISUPDATE=FALSE`) |
| `UPDATE` | `DELETE` + `INSERT` 2행 (`ISUPDATE=TRUE`) |
| `DELETE` | `DELETE` 1행 (`ISUPDATE=FALSE`) |

### [결함 4 · 🟡] 시나리오 검증이 결정적이지 않다 — 태스크와 수동 `CALL` 의 경합

Step 5 가 5분 주기 태스크를 `RESUME` 한 상태에서 Step 7 이 같은 스트림을 수동 `CALL`
한다. 결함 1로 offset 이 전진하지 않으므로 양쪽이 같은 건을 중복 처리한다.
시나리오를 결정적으로 검증하려면 **Step 7 전에 태스크를 `SUSPEND`** 해야 한다.

## 5. 🔴 비용과 무관한 계정 영향 — 실행 전 반드시 인지할 것

| 항목 | 영향 | 원복 |
| :--- | :--- | :--- |
| `ENTRA_ID_SAML_INTEGRATION` (`ENABLED=TRUE`, SP-initiated) | 계정 **로그인 페이지에 SSO 버튼 추가**. 비밀번호 로그인은 유지됨 | `DROP SECURITY INTEGRATION` 로 완전 제거 |
| `SSO_LOGIN_ONLY = TRUE` (2.4, 주석 상태) | 🔴 **해제하지 말 것.** 더미 IdP 상태에서 켜면 해당 사용자가 로그인 불가(잠금) | 주석을 유지하는 것이 안전 |
| `SYSTEM$GENERATE_SCIM_ACCESS_TOKEN` | `CREATE USER`/`CREATE ROLE`/`MANAGE GRANTS` 권한의 **실제 베어러 토큰** 발급. `SELECT` 하면 **쿼리 이력에 잔존** | `AAD_SCIM_INTEGRATION` `DROP` 시 무효화 |
| `GRANT CREATE USER` / `MANAGE GRANTS ON ACCOUNT` (2개 역할) | 계정 사용자·권한을 임의 조작 가능한 권한 위임 | 역할 `DROP` 시 함께 소멸 |
| 태스크 2개 `RESUME` | 계정을 **자동으로 `DISABLED`** 시키는 태스크가 상시 동작 | `SUSPEND` → `DROP` |
| `EXTERNAL_OAUTH_ANY_ROLE_MODE = 'ENABLE'` | 토큰이 임의 역할로 전환 가능. 최소 권한 원칙과 상충 | 운영에서는 `DISABLE` 검토 |

검증 시 토큰 값은 `LENGTH()` 만 확인해 **출력하지 않았다.**

## 9. 정정 내용

### 9.1 [결함 1] 스트림 미소비 → 소비 후 배치 처리

`5.1` 프로시저를 재작성했다. 신설 객체 `OPS.HR_STREAM_BUFFER` 를 두고
`INSERT ... SELECT ... FROM <stream>` 로 **먼저 소비**한 뒤 버퍼를 처리한다.
소비를 처리보다 앞에 두는 것이 요점이다. EDU-02 `07_` 의 검증된 패턴과 같다.

버퍼는 `BATCH_ID`(UUID) 로 회차를 구분하므로 소비 이력 자체가 감사 근거가 되고,
예외로 실패한 배치를 `BATCH_ID` 로 재처리할 수 있다.
**스트림에서는 다시 읽을 수 없다** — 이미 소비되었기 때문이다.
이 점을 예외 핸들러 주석에 명시했다.

### 9.2 [결함 3] `DELETE` 오프보딩 → INSERT 행 부재로 하드 삭제 판별

`WHERE METADATA$ACTION = 'INSERT'` 필터를 제거하고, 버퍼를 `EMP_ID` 로 집계해
**INSERT 행이 하나도 없는 사번**을 하드 삭제로 판정한다.

이 판별이 성립하는 근거는 Step 4 에서 실측한 스트림 액션 표다.
`UPDATE` 는 `DELETE` + `INSERT` 쌍을 만들므로 INSERT 행이 존재해
하드 삭제로 오판되지 않는다. 순수 `DELETE` 만 INSERT 행이 없다.

집계는 INSERT 행의 값을 우선 채택하고(변경 후 최종 상태), 없으면 DELETE 행의
값으로 사번·성명을 확보한다 (`COALESCE(MAX(IFF(...)), MAX(...))`).

### 9.3 정정 과정에서 추가로 발견해 함께 고친 것

| 항목 | 내용 |
| :--- | :--- |
| 부서이동이 계정에 반영되지 않음 | `CREATE USER IF NOT EXISTS` 는 기존 계정을 갱신하지 않는다. 뒤따르는 `ALTER USER` 가 `DISABLED`·`DEFAULT_ROLE` 만 설정해 `DISPLAY_NAME` 이 옛 부서에 고정되었다. 문서가 "부서이동" 을 목표로 명시하는데 실제로는 반영되지 않았다. `ALTER` 에 `DISPLAY_NAME` 을 추가했다 |
| 미정의 상태가 조용히 누락됨 | `EMPLOYMENT_STATUS` 가 `ACTIVE`/`RESIGNED`/`SUSPENDED` 가 아니면 `IF` 어느 분기에도 걸리지 않아 아무 기록 없이 사라졌다. `SKIPPED_UNKNOWN_STATUS` 분기를 추가해 감사 로그에 남기고 보류한다 |
| 동적 SQL 식별자 주입 | 사번·역할명이 `EXECUTE IMMEDIATE` 의 **식별자 자리**에 문자열 결합으로 들어간다. 식별자는 바인드할 수 없으므로 `RLIKE` 패턴 검사를 넣고, 벗어나면 `REJECTED_UNSAFE_IDENTIFIER` 로 거부한다. 표시 문자열의 홑따옴표도 이스케이프했다 |
| `CREATE PROCEDURE` 절 순서 | `COMMENT` 를 `EXECUTE AS` 앞으로 두었다 (EDU-02 `06_` 결함 A 와 동일 사안) |
