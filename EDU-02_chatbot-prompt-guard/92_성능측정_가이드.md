# 92. 성능·비용 측정 가이드

이 문서는 **실습 단계가 아닙니다.** 파이프라인의 성능과 비용을 **직접 측정**하는
방법을 제공합니다.

> 🔴 **이 문서는 성능 수치를 제시하지 않습니다.** 의도된 것입니다.
>
> 이전 판(`93.성능검증_및_성과보고서.md`)에는 `0.38초 P95`, `100+ QPS 지원`,
> `운영 공수 85% 절감`, `프롬프트 공격 방어율 100%`, 토큰 단위까지 특정한 표가
> 실려 있었으나 **측정 절차와 표본이 없었습니다.** 이런 수치는 독자가 실측치로
> 오해해 의사결정 근거로 쓰기 때문에 위험합니다. 따라서 값을 삭제하고
> **측정 방법과 빈 기록 서식**으로 대체했습니다.
>
> 값을 채운 뒤에는 반드시 **측정 조건(웨어하우스 크기, 표본 수, 데이터 규모,
> 측정일)** 을 함께 기록하십시오. 조건 없는 수치는 재현할 수 없습니다.

## 1. 단계별 소요 시간 — 쿼리 이력 기반

Snowflake 가 기록한 실제 실행 시간을 씁니다. 스톱워치로 재지 마십시오.

```sql
ALTER SESSION SET USE_CACHED_RESULT = FALSE;

-- 측정하려는 작업을 실행한 뒤:
SELECT
    LEFT(QUERY_TEXT, 80)            AS QUERY_PREVIEW,
    TOTAL_ELAPSED_TIME / 1000.0     AS ELAPSED_SEC,
    EXECUTION_TIME    / 1000.0      AS EXEC_SEC,
    COMPILATION_TIME  / 1000.0      AS COMPILE_SEC,
    BYTES_SCANNED,
    START_TIME
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY_BY_SESSION(RESULT_LIMIT => 100))
ORDER BY START_TIME DESC;

ALTER SESSION UNSET USE_CACHED_RESULT;
```

기록 서식 — 각 항목을 여러 번 측정해 최소/중앙/최대를 적으십시오.

| 측정 대상 | 실행 방법 | 표본 수 | 최소(초) | 중앙(초) | 최대(초) |
|-----------|-----------|---------|----------|----------|----------|
| PII 마스킹 (단건) | `05_ [3]` | | | | |
| 문서 파싱 + 청킹 (문서 1건) | `06_ [3]` `CALL SP_PROCESS_NEW_DOCUMENTS()` | | | | |
| 검색 (`SEARCH_PREVIEW`) | `08_ [4.1]` | | | | |
| RAG 서빙 — 가드 ON | `09_ [4.1]` 시나리오 A | | | | |
| RAG 서빙 — 가드 OFF | `09_ [4.2]` | | | | |
| 가드 토글 (`UPDATE`) | `09_ [1.3]` | | | | |

> ⚠️ 문서 파싱 시간은 **페이지 수와 레이아웃 복잡도에 비례**합니다.
> 문서 1건 기준값을 다른 문서에 그대로 적용하지 마십시오.

### 1.1 대량 처리 측정 (선택)

마스킹 함수의 배치 처리량을 보려면 실제 청크 테이블에 적용하십시오.

```sql
ALTER SESSION SET USE_CACHED_RESULT = FALSE;

SELECT COUNT(KSM_CHATBOT_DB.SECURITY.MASK_PII_TEXT(CHUNK_TEXT)) AS MASKED_ROWS

ORDER BY START_TIME DESC LIMIT 1;
```

## 2. LLM 토큰 사용량

> 🔴 **`show_details` 로 토큰을 읽는 방법은 이 자료에서 제거했습니다.**
> 2026-09-17 계정 LJ20513 실측 결과, `AI_COMPLETE` 에 `{'show_details': TRUE}` 를
> 넘기면 이 실습이 쓰는 모델이 이를 **거부**했습니다.
>
> ```
> invalid options: model "claude-haiku-4-5" does not accept additional
> parameters, got: [show_details]
> ```
>
> `llama3.1-8b` 에서도 같은 오류가 났고, `AI_COUNT_TOKENS('claude-haiku-4-5', …)` 는
> `NULL` 을 반환했습니다. 즉 **모델에 따라 지원 여부가 다릅니다.**
> 쓰려면 본인이 쓰는 모델에서 직접 확인하십시오.
>
> 참고: 구 함수 `SNOWFLAKE.CORTEX.COMPLETE` 는 옵션을 주면 `OBJECT` 를 반환하며
> 거기에 `usage` 가 포함됩니다. 다만 이 함수는 공식 문서상
> *"will be deprecated by the end of 2026"* 이므로 측정 목적으로도 권하지 않습니다.

아래 ACCOUNT_USAGE 뷰가 토큰 사용량의 **확실한 확인 경로**입니다.
단, 최대 2~3시간 지연되므로 실습 직후에는 0행일 수 있습니다.

```sql
SELECT FUNCTION_NAME, MODEL_NAME, TOKENS, TOKEN_CREDITS, START_TIME
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_FUNCTIONS_USAGE_HISTORY
ORDER BY START_TIME DESC
LIMIT 20;
```

| :--- | :--- |
| 측정한 모델명 | |
| prompt 토큰 | |
| completion 토큰 | |
| 표본 수 (호출 횟수) | |
| 측정일 | |

기록 서식:

| 시나리오 | 가드 | prompt_tokens | completion_tokens | total_tokens |
|----------|------|---------------|-------------------|--------------|
| 정상 업무 질문 | ON | | | |

## 3. 크레딧 소비

### 3.1 웨어하우스 크레딧

```sql
SELECT
    WAREHOUSE_NAME,
    DATE_TRUNC('hour', START_TIME) AS USAGE_HOUR,
    SUM(CREDITS_USED)              AS CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE WAREHOUSE_NAME = 'KSM_CHATBOT_WH'
  AND START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY 2 DESC;
```

### 3.2 Cortex 함수 크레딧 (파싱·LLM·임베딩)

```sql
SELECT
    FUNCTION_NAME,
    MODEL_NAME,
    SUM(TOKENS)        AS TOKENS,
    SUM(TOKEN_CREDITS) AS CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_FUNCTIONS_USAGE_HISTORY
WHERE START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY CREDITS DESC;
```

### 3.3 Serverless Task 크레딧

```sql
SELECT
    NAME,
    DATE_TRUNC('day', START_TIME) AS USAGE_DAY,
    SUM(CREDITS_USED)             AS CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.SERVERLESS_TASK_HISTORY
WHERE NAME ILIKE 'TASK_INGEST_NEW_DOCUMENTS'
  AND START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY 2 DESC;
```

### 3.4 Cortex Search 서빙 비용

```sql
SELECT
    SERVICE_NAME,
    DATE_TRUNC('day', USAGE_DATE) AS USAGE_DAY,
    SUM(CREDITS)                  AS CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_SEARCH_DAILY_USAGE_HISTORY
WHERE USAGE_DATE >= DATEADD('day', -7, CURRENT_DATE())
GROUP BY 1, 2
ORDER BY 2 DESC;
```

> 🔴 **`ACCOUNT_USAGE` 뷰 사용 시 두 가지 주의사항**
>
> 1. **최대 2~3시간 지연됩니다.** 방금 실행한 작업은 보이지 않습니다.
>    실습 직후에 0이 나오는 것은 정상이며, "비용이 0이다"라는 뜻이 아닙니다.
> 2. **계정 에디션·버전에 따라 뷰나 컬럼이 없을 수 있습니다.** 오류가 나면
>    아래로 존재 여부를 먼저 확인하십시오.
>
> ```sql
> SELECT TABLE_NAME FROM SNOWFLAKE.INFORMATION_SCHEMA.TABLES
> WHERE TABLE_SCHEMA = 'ACCOUNT_USAGE' AND TABLE_NAME ILIKE '%CORTEX%';
>
> SELECT COLUMN_NAME FROM SNOWFLAKE.INFORMATION_SCHEMA.COLUMNS
> WHERE TABLE_SCHEMA = 'ACCOUNT_USAGE' AND TABLE_NAME = '<뷰 이름>';
> ```

크레딧 기록 서식:

|------|------|--------|------|
| 웨어하우스 | | | |
| Cortex 함수 (파싱) | | | |
| Cortex 함수 (LLM) | | | |
| Cortex 함수 (임베딩) | | | |
| Serverless Task | | | |

## 4. 검색 품질 — 정량화하려면

검색 관련성은 **정답 집합 없이는 측정할 수 없습니다.** 유사도 점수 하나를
"정확도"라고 부르지 마십시오.

최소한의 평가 방법:

1. 질문 10~20개와 각 질문의 **기대 문서/청크**를 사람이 미리 정합니다
2. 각 질문으로 `SEARCH_PREVIEW` 를 실행합니다
3. 상위 K개 결과에 기대 청크가 포함되는 비율을 셉니다 (Recall@K)

| # | 질문 | 기대 청크 | 상위 3에 포함 | 상위 5에 포함 |
|---|------|-----------|---------------|---------------|
| 1 | | | ☐ | ☐ |
| 2 | | | ☐ | ☐ |
| 3 | | | ☐ | ☐ |

- 표본 수: `______` 개 / Recall@3: `______` / Recall@5: `______`

> ⚠️ 표본 3~5건으로 얻은 비율을 백분율로 제시하면 과대 해석됩니다.
> 표본 수를 반드시 병기하십시오.

## 5. 보안 차단 — 측정 가능한 것과 불가능한 것

| 항목 | 측정 가능? | 방법 |
|------|-----------|------|
| PII 마스킹 누락 건수 | ✅ 가능 | `06_ [4.3]` 정규식 점검 쿼리 — 결정적 |
| 인덱스에 원본 PII 존재 여부 | ✅ 가능 | `08_ [4.4]` 검색 점검 |
| 금칙 주제 거부 여부 | ⚠️ 관찰만 | `09_ [4]` — LLM 출력은 비결정적 |
| 인젝션 차단율 | ❌ **주장 불가** | 시스템 지침 의존이며 공격 공간이 무한 |

> 🔴 **"방어율 100%" 는 쓸 수 없습니다.** 이유가 두 가지입니다.
>
> 1. 이 구성에서 인젝션 방어는 **시스템 지침(모델의 자율 판단)에만 의존**합니다.
>    `{'guardrails': TRUE}` 는 Cortex Guard 이며 **응답 유해성 필터**입니다.
>    플랫폼 레벨 인젝션 탐지(Cortex AI Guardrails)는 CoCo / Snowflake CoWork /
>    Cortex Agents 경로에만 적용되며, SQL `COMPLETE` 호출에는 적용되지 않습니다.
> 2. 몇 건의 시나리오 통과는 방어율의 근거가 되지 못합니다.
>
> 쓸 수 있는 서술: "테스트한 N개 시나리오 중 M건에서 표준 거부 문구가 반환되었다."

- 인덱스 PII 노출: ☐ 없음 ☐ 있음
- 거부 문구가 반환된 시나리오: `______` / 테스트한 시나리오: `______`

## 6. 정성적 이점 — 수치 없이 서술하기

측정할 수 없는 이점은 **비교 구조로** 서술하고 절감률을 붙이지 마십시오.

| 항목 | 별도 스택 구성 | Snowflake 네이티브 구성 |
|------|----------------|-------------------------|
| 구성 요소 | OCR 서버 + 벡터 DB + 파이프라인 오케스트레이터 + 서빙 API | Stage + Cortex 함수 + Task + Cortex Search |
| 운영 주체 | 컴포넌트별 개별 운영 | 단일 플랫폼 |
| 데이터 이동 | 시스템 간 복제 필요 | 계정 내에서 처리 |
| 접근 제어 | 시스템별 별도 관리 | 단일 RBAC |
| 유휴 시 컴퓨트 비용 | 상시 구동 서버 필요 | 발생하지 않음 (서버리스 + AUTO_SUSPEND) |

> 위 표에는 절감률이 없습니다. **"85% 절감" 같은 수치는 조직의 기존 비용 구조를
> 실제로 조사해야 산출할 수 있습니다.** 조사했다면 산출 근거를 함께 남기십시오.
