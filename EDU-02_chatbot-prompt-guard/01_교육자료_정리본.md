# 교육자료 정리본 — Snowflake Cortex 챗봇 보안 가드 실습

- **주제 슬러그:** `chatbot-prompt-guard`
- **객체 접두사:** `KSM_CHATBOT_` / **COMMENT 태그:** `[chatbot-prompt-guard]`
- **작성 기준일:** 2026-09-16

> 이 문서는 실습의 지도다. **실행은 `02_` 부터 순서대로** 진행한다.
> 검증 상태는 각 문서 상단 주석에 항목 단위로 표기되어 있다. 이 자료 전체가
> 검증되었다는 선언은 하지 않는다 — §7 검토 이력의 미검증 항목표를 반드시 확인할 것.

## 1. 학습 목표

Snowflake 네이티브 기능만으로 **사내 문서 기반 RAG 챗봇**을 만들고,
그 위에 **어떤 보안 계층이 실제로 무엇을 막는지** 구분해 검증한다.

완료 시 다음을 할 수 있다.

| # | 달성 상태 | 검증 지점 |
| :--- | :--- | :--- |
| 1 | 비정형 문서(PDF)를 스테이지에 올려 청크 테이블에 **적재된 행을 눈으로 확인** | `06_` 적재 검증 쿼리 |
| 2 | 파싱 전 단계에서 PII가 마스킹되어 인덱스에 **평문 PII가 들어가지 않음**을 확인 | `05_` 단위 테스트, `06_` 청크 샘플 |
| 3 | 스테이지에 파일을 추가하면 Stream·Task가 **자동으로 증분 처리**함을 확인 | `07_` 실행 이력·이벤트 로그 |
| 4 | 하이브리드 검색으로 질문에 맞는 청크가 상위로 반환됨을 확인 | `08_` `SEARCH_PREVIEW` |
| 5 | **SQL 한 줄로 보안 가드를 On/Off** 전환하고 응답 차이를 관찰 | `09_` 토글 시나리오 |
| 6 | **Cortex Guard / System Instruction / Cortex AI Guardrails 세 기능의 적용 범위를 구분** | `09_` [0], `10_` |
| 7 | 실습 전 상태로 **완전히 되돌리고 그것을 대조로 증명** | `98_` → `96_` |

### 이 실습이 다루지 않는 것

- Cortex Agents / Snowflake CoWork 상에서의 에이전트 구축 — `10_` 에서 경로만 안내한다
- 사내 포털 UI·백엔드 연동 구현 — 요구사항 정의만 `91_` 에 있다
- 프로덕션 배포 판단 — 이 자료는 배포 적합성을 판정하지 않는다

## 2. 다층 방어의 실제 구조 — 이 실습의 핵심 개념

> 🔴 **가장 자주 오해되는 지점이다.** 이름이 비슷한 두 제품 기능이 서로 다른 것을
> 검사하며, 적용 대상 클라이언트도 다르다.

| 계층 | 기능 | 무엇을 검사하나 | 어디에 적용되나 | 이 실습의 `COMPLETE` 호출에 적용? |
| :---: | :--- | :--- | :--- | :---: |
| 1 | **Cortex Guard** (`{'guardrails': TRUE}`) | 모델이 생성한 **응답(출력)** 의 유해성. Meta Llama Guard 3 기반 | `AI_COMPLETE` / `SNOWFLAKE.CORTEX.COMPLETE` | ✅ 예 |
| 2 | **System Instruction** | 입력 의도. 모델의 **자율 판단**에 의존 | 프롬프트로 주입 | ✅ 예 |
| 3 | **Cortex AI Guardrails** (계정 파라미터 `AI_SETTINGS`) | **입력** 프롬프트 인젝션·탈옥 | **CoCo / Snowflake CoWork / Cortex Agents 전용** | ❌ 아니오 |
| 4 | **RAG 데이터 계층** (PII 마스킹, 최소 권한, Owner's Rights) | 인덱스에 들어가는 **데이터** | 파이프라인 전처리 | ✅ 예 |

두 가지 결론이 따라온다.

1. **Cortex Guard 는 입력 인젝션 차단 기능이 아니다.** 출력 필터다.
   "LLM 도달 전에 인젝션을 선제 차단해 토큰을 절감한다"는 설명은 사실이 아니다.
2. **이 실습의 SQL 챗봇에서 인젝션 방어는 계층 2(시스템 지침)에만 의존한다.**
   시스템 지침은 모델의 자율 판단이므로 우회될 수 있다. 플랫폼 레벨 인젝션 방어가
   필요하면 Cortex Agents 로 구현해야 한다(`10_` 참고).

개념 배경과 위협 유형은 `90_학습용_참고자료.md` 에 있다.

### 데이터 흐름

```
[문서 업로드]  04_
      │  @BRONZE.DOC_STAGE  (Directory Table)
      ▼
[변경 감지]   07_  BRONZE.STAGE_DOC_STREAM
      │            └─ OPS.TASK_INGEST_NEW_DOCUMENTS (Serverless, WHEN STREAM_HAS_DATA)
      ▼
[파싱→마스킹→청킹] 06_  SILVER.SP_PROCESS_NEW_DOCUMENTS  (EXECUTE AS OWNER)
      │  AI_PARSE_DOCUMENT(TO_FILE(...), {'mode':'LAYOUT'})
      │  → SECURITY.MASK_PII_TEXT → SPLIT_TEXT_RECURSIVE_CHARACTER
      ▼
[청크 저장]   SILVER.DOCUMENT_CHUNKS      ← 평문 PII 없음
      ▼
[검색 인덱스] 08_  SERVING.KSM_HQ_SEARCH_SERVICE
      ▼
[서빙]        09_  SERVING.SP_EXECUTE_GUARDED_CHAT
                   └─ SECURITY.PROMPT_GUARD_CONFIG 로 On/Off 분기
```

> `GRANT EXECUTE TASK ON ACCOUNT`)은 **Role 삭제와 함께 사라진다.** 별도 `REVOKE` 는 필요 없다.

### (b) 기존 객체의 속성 변경 — **`DROP` 이 아니라 원복 대상**

> 🔴 이 두 항목은 계정 전체에 영향을 준다. `DROP` 으로 되돌아가지 않는다.
> 실습 전 값을 기록하지 않으면 **원복이 불가능하다.**

| 대상 | 변경 내용 | 변경 문서 | 사전 값 기록 | 원복 |
| :--- | :--- | :---: | :--- | :--- |
| 계정 파라미터 `AI_SETTINGS` | `guardrails.advanced_prompt_injection` 활성화 | `10_` [2] | `02_` [0] / `95_` | `98_` [7.1] — 실습 전 값에 따라 분기 |
| 계정 파라미터 `CORTEX_ENABLED_CROSS_REGION` | `DISABLED` → 허용 리전 | `10_` [1] | `02_` [0] / `95_` | `98_` [7.2] — **변경했을 때만** |

원복은 실습 전 값에 따라 세 갈래로 갈린다.

| 실습 전 값 | 원복 |
| :--- | :--- |
| 이미 원하는 값이었다 | **변경 자체가 불필요.** 할 일 없음 |
| 비어 있음 / 미설정 | `ALTER ACCOUNT UNSET <파라미터>` |
| 다른 값이 명시되어 있었다 | `ALTER ACCOUNT SET <파라미터> = <기록한 원래 값>` |

> 💡 `CORTEX_ENABLED_CROSS_REGION` 이 이미 `DISABLED` 가 아니면 `10_` [1] 을 **건너뛴다.**
> 불필요한 변경을 만들지 않는 것이 원복보다 낫다.

### (c) 외부 리소스

| 항목 | 위치 | 정리 |
| :--- | :--- | :--- |
| 업로드한 원본 문서 파일 | `@BRONZE.DOC_STAGE` | `DROP STAGE` / `DROP DATABASE` 시 함께 삭제 |

Snowflake 외부에 지속적으로 누적되는 리소스(복제 슬롯, 웹훅, IAM 역할, 방화벽 규칙)는
**이 실습이 만들지 않는다.** `91_사내연계_요청서.md` 의 방화벽·서비스 계정 항목은
실무 도입 시의 요청 사항이며 실습이 생성하는 것이 아니다.

### 대조 결과

(a) 22행 · (b) 2행 · (c) 1행 → `98_리소스정리.sql` 의 삭제·원복 대상과 **1:1 일치**함을

## 6. 트러블슈팅 — 증상 기준

| 증상 | 원인 | 조치 |
