# 교육자료 스킬 패키징 규격

> **목적**: `교육자료 생성 프롬프트.md`(= 무엇을 만들 것인가)를 **스킬로 어떻게 포장할 것인가**를 기록한다.
> 다른 세션에서 아래 **4개 파일**(문서 2 + 스크립트 2)로 동일한 스킬을 재현할 수 있어야 한다.
>
> **범위 밖**: 스킬 제작 일반론(분할 기준, 500줄 한도, 라우터 패턴, frontmatter 작성법)은
> 여기에 쓰지 않는다. `/skill-development` 스킬이 담당한다. 중복 기술은 그 스킬이 개정될 때 낡는다.

---

## 이 문서를 읽는 방법

이 문서는 **명세를 스킬로 포장하는 방법**만 다룬다. 교육자료를 **무엇을** 만들지는
`교육자료 생성 프롬프트.md` 가 담당한다. 스킬 제작 일반론은 `/skill-development` 에 있다.

| 하려는 일 | 읽을 장 |
|-----------|---------|
| 다른 세션에서 스킬을 **처음 재현** | **1장**만 읽으면 된다 (스크립트가 나머지를 한다) |
| 명세를 고쳤는데 스킬에 **반영이 안 됨** | **3.1** 참조 주입 + **7.3** 단방향 동기화 |
| 스킬 파일을 **직접 고치려는 충동** | **7.3** — 하지 마라. 명세를 고치고 재빌드한다 |
| **문서가 커져서** 한도에 걸렸다 | **3.0** 조각 규칙 — 이어 쓰지 말고 이음매를 찾아 분할 |
| 왜 산문 절차가 아니라 **스크립트**인가 | **4장** (4회 재현 실패 기록) |
| 왜 이렇게 **나눴는가** | **5장** (초기 로드 실측) |
| `frontmatter` / 필수 절 작성 | **6장**, **6.1** |
| 파일을 편집했는데 **반영이 안 된 것 같다** | **7.5** 스테이지 FS — `>>` 는 조용히 실패한다 |
| **무엇이 자동으로 막히나** / 사람이 볼 것은 | **8.1** 자동 가드 목록 |
| 스킬을 실제로 써 보고 **명세 내용을 고치는** 절차 | **9장** 개선 피드백 루프 |
| **구조·빌드 도구**를 고치는 절차 | **10장** 변경 절차 (기본 루프·치환 키·가드 검증) |
| 가드를 **추가**했다 | **10.4** 실패를 주입해 작동을 증명한다 |

### 참조 표기 규약

| 표기 | 뜻 |
|------|-----|
| **명세 N장** | `교육자료 생성 프롬프트.md` 의 장 |
| **N장** / **N.M** | 이 문서의 장·절 |
| `SKILL.md` `create/` `references/` | 빌드 산출물(스킬) 파일 |

> ⚠️ 두 문서 모두 `## N.` 형식의 장을 쓰므로 혼동하기 쉽다.
> 명세를 가리킬 때는 **반드시 "명세" 를 앞에 붙인다.**

### 필요한 파일 4개 — 모두 `/workspace/edu-doc-generator-ihcho/`

| 파일 | 역할 |
|------|------|
| `교육자료 생성 프롬프트.md` | **워크플로 명세** — 스킬 내용의 원천 |

| `verify_skill.py` | 도달성·좌표·필수 절·로드 지시 전수 검증 |

> ⚠️ **스크립트를 스킬 폴더(`.snowflake/cortex/skills/...`) 안에 두지 않는다.**
> 스킬을 처음 만들 때는 스킬 폴더가 존재하지 않으므로 부트스트랩이 불가능해진다.

정본 4개는 소스 폴더에, 산출물은 스킬 폴더에 둔다. 둘은 별개 위치다.

```
/workspace/
├── edu-doc-generator-ihcho/                          ← 정본 (소스)
│   ├── 교육자료 생성 프롬프트.md
│   ├── 교육자료 스킬 패키징.md
│   ├── build_skill.py
│   └── verify_skill.py
└── .snowflake/cortex/skills/edu-doc-generator-ihcho/  ← 산출물 (설치 스킬)
    ├── SKILL.md
    ├── create/SKILL.md
    ├── improve/SKILL.md
    └── references/{output-contract,teardown,quality-bar}.md
```

스크립트는 `__file__` 기준으로 명세를 찾으므로, 폴더째 옮겨도 동작한다.

### 절차

```bash
cd /workspace/edu-doc-generator-ihcho

# ① 차이 확인 (기존 스킬이 있을 때 — 덮어쓰기 전 필수)
python3 build_skill.py --check

# ② 빌드
python3 build_skill.py

# ③ 검증 — 22개 항목 전부 통과해야 한다
python3 verify_skill.py
```

경로가 다르면 인자로 지정한다.

```bash
python3 build_skill.py --spec <명세.md> --out <스킬폴더>
python3 verify_skill.py --skill <스킬폴더> --spec <명세.md>
```

### 스크립트가 담당하는 것 / 담당하지 않는 것

| 성격 | 담당 | 내용 |
|------|------|------|

### 3.0 조각 규칙 (Sharding) — 커질 때 어떻게 나누는가

문서는 계속 자란다. 한도를 올리는 것은 지는 싸움이므로 **나누는 규칙**을 둔다.

| 규칙 | 내용 |
|---|---|
| **경계는 의미** | 조각은 **관심사 이음매**로만 나눈다 |
| **한도는 트리거** | 조각 `<= 400줄`. 넘으면 "여기서 자르라"가 아니라 **"관심사가 둘 이상 섞였다"는 신호** |
| **허브는 얇게** | `SKILL.md < 200줄`. 호출마다 읽히므로 여기에 실행 시점 규칙을 두지 않는다 |
| **이름은 번호+의미** | `NN_<slug>.md`. 번호는 안정 주소, slug 는 로드 판단 근거 |
| **포인터는 생성** | 허브의 조각 표는 `pointer_table()` 이 `REFERENCES` 에서 만든다 |

> 🔴 **바이트 경계로 다음 조각에 이어 쓰지 않는다.**
> `0001` 이 꽉 차서 `0002` 로 이어 쓰면 규칙 하나가 무의미한 지점에서 쪼개진다.
> 모델이 앞 조각만 로드하면 **규칙의 절반만 읽고 판단한다.** 읽어야 할 총량은
> 그대로인데 로드 횟수와 반쪽만 읽을 위험만 늘어난다.
> 한도의 목적은 파일 크기 절약이 아니라 **"모델이 온전히 붙들고 쓸 수 있는가"** 다.

> 💡 **번호만 쓰지 않는다.** `0003.md` 만 보면 모델은 무엇을 로드해야 할지
> 판단할 수 없다. 이 스킬이 교육자료에 요구하는 `02_사전준비_및_권한구성.sql`
> 명명 규칙과 같은 이유다 — 자기 규칙을 자기에게 적용한다.

**조각이 한도에 닿았을 때의 절차**

1. 그 조각에 **서로 다른 시점에 필요한** 내용이 섞여 있는지 본다
2. 있으면 그 지점이 이음매다. 새 조각으로 떼어내고 `REFERENCES` 에 등록한다
3. `LOADS` 에서 **필요한 STEP 에만** 새 조각을 로드하도록 지정한다
4. `SUB_LEAF` 의 참조를 **절 제목**으로 가리킨다 (숫자 좌표는 재번호에 깨진다)
5. 빌드 → `verify_skill.py` 로 한도·포인터 표·죽은 좌표를 확인한다

실측 사례: 4장은 `객체 대장·스냅샷`(작성 시점)과 `98_ 9요소`(정리 시점)가 섞여
462줄이었다. `STEP C2` 가 필요하지도 않은 167줄을 함께 읽고 있었다.
두 조각으로 나누자 `C2` 는 `20_`(210줄)만, `C5` 는 `21_`(257줄)만 읽는다.

### 3.1 참조 주입 — 명세의 이름 기반 참조 → 스킬 파일 경로

> **분할은 단순 복사가 아니라 좌표계 변환이다.**
> 명세는 한 문서이므로 다른 장을 자유롭게 가리킬 수 있다. 스킬은 6개 파일로
> 쪼개지므로, 그 참조가 **어느 파일에 있는지** 말해 주지 않으면 가리킬 대상이 없다.
>
> 변환하지 않으면 `references/` 3개 파일을 아무도 로드하지 않아 **고아 파일**이 된다.
> 객체 대장·정리 8요소·품질 기준이 실제 작업에 반영되지 않는다.
> `/skill-development` 의 CYOA 분석에서 **도달 불가(reachability)** 결함으로 잡힌다.

#### 규약: 명세는 장 번호로 참조하지 않는다

과거에는 명세가 `"7장 품질 기준으로 검토한다"`, `"3.5의 8개 요소"` 처럼 **번호**로
다른 장을 가리켰다. 이 방식은 두 번 실패했다.

- 분할하면 번호가 가리킬 대상이 없어져 **죽은 좌표**가 된다
- 명세의 장 순서를 바꾸면 번호가 전부 어긋난다

그래서 **이름으로 참조하는 규약**으로 바꿨다.

| 구 방식 (금지) | 현 방식 |
|---|---|
| `7장 품질 기준으로 검토한다` | `품질 기준으로 초안을 스스로 검토한다` |
| `3.5의 8개 필수 구성 요소` | `정리 문서의 8개 필수 구성 요소` |
| `미검증 항목은 4.3에 따라 표기한다` | `미검증 항목은 미검증 표기 의무에 따라 표기한다` |
| `(6.9 참고)` | `(위 "문서 추가·삭제·번호 변경 규칙")` |

이름은 장이 어디로 옮겨가도 유효하다. **새 하위 절에 번호를 붙이지 않는 이유도 같다**(9.3).

#### 주입은 `build_skill.py` 가 한다

명세는 제품 중립이라 `references/teardown.md` 같은 스킬 파일명을 모른다.
그 경로를 붙이는 것이 빌드의 일이다. 세 가지 장치가 있다.

| 장치 | 대상 | 하는 일 |
|------|------|---------|
| `SUB_ROUTER` | 라우터(명세 0·1·8장) | `references/<파일>.md` 주입 — `../` **없음** |
| `SUB_LEAF` | 서브스킬(명세 6·7·8장) | `../references/<파일>.md` 주입 |
| `LOADS` | 서브스킬 STEP 헤딩 | `**Load**` 지시를 **삽입**(치환이 아니다) |

> ⚠️ **치환과 삽입은 다른 동작이다.** 4차 재현 실패의 원인이 이것이었다.
> 산문 절차가 "치환한다"고만 써서 로드 지시가 하나도 만들어지지 않았다.
> 그래서 두 동작을 `apply_subs()` / `insert_loads()` 로 코드에서 분리했다.

#### 스테일 키 가드 — `check_subs()`

`str.replace` 는 키가 없으면 **조용히 아무 일도 하지 않는다.** 명세 문구를 손보면
치환 키가 소리 없이 무효화되고, 미변환 문구가 스킬로 새어 나간다.
`verify_skill.py` 는 숫자 좌표만 검사하므로 이것을 잡지 못한다.

> 실측: 스테일 키 **14개**가 `22/22 통과` 상태에서 누적되어 있었다.
> 그중 하나(`| teardown | 3장 정리 요구사항 준수만 |`)는 라우터에 파일 경로를
> 넣지 못하게 만들고 있었다.

그래서 `build()` 첫 줄에서 전수 검사하고, 하나라도 어긋나면 **빌드를 실패시킨다.**

```
[오류] 명세에 없는 치환 키 1개 — 명세가 바뀌었다면 키도 고쳐야 한다.
  [SUB_LEAF] - 안전장치 적용
```

**명세 문구를 고쳤으면 같은 커밋에서 치환 키도 고친다.** 이것이 유일한 규율이다.

#### 로드 지시 배치 규칙

1. **그 참조가 처음 필요한 STEP 맨 앞에 둔다.** 문서 중간이 아니다.
2. **로드 이유를 한 구절 덧붙인다.** 왜 필요한지 알면 모델이 판단할 수 있다.
   ```
   **Load** `../references/teardown.md` — 객체 대장과 명명 규칙 작성에 필요하다.
   ```
3. **같은 참조를 두 번째로 지시할 때는 조건을 붙인다.**
   ```
   **Load** `../references/output-contract.md` (아직 로드하지 않았다면) — 분리 규칙, 메타 주석
   ```
4. **참조 파일 내부의 절 번호는 남겨도 된다.** 파일이 로드된 뒤에는 유효하다.
   ```
   `../references/teardown.md` 5장의 8개 필수 구성 요소를 모두 포함한다
   ```
   참조 파일의 절 번호는 `assemble_reference()` 가 **연번으로 다시 매긴다**.
   명세의 `4.5` 가 `teardown.md` 에서는 `5장` 이 되는 식이다. 그래서 명세 번호를
   그대로 쓰면 안 되고, 치환 값에 **재부여된 번호**를 적어야 한다.
5. 라우터에는 로드 지시를 두지 않는다 (7.2 참고).

현재 적용된 배치:

| 파일 | STEP | 로드 대상 |
|------|------|-----------|
| `create/` | C2 초안 작성 | `teardown.md` |
| `create/` | C3 비판적 검토 | `quality-bar.md`, `output-contract.md` |
| `create/` | C4 실습 문서 | `output-contract.md` (조건부) |
| `improve/` | I1 전체 읽기 | `output-contract.md` |
| `improve/` | I2 갭 분석 | `quality-bar.md`, `teardown.md`(범위 조건부) |

#### 검증

```bash
# (1) 서브스킬에 로드 지시가 있는가 (0이면 결함)
grep -c 'Load.*\.\./references' create/SKILL.md improve/SKILL.md

# (2) 죽은 좌표 참조가 남았는가 — 결과가 없어야 정상
#     파일을 먼저 지목한 뒤의 절 번호(정상 표기)는 제외한다
grep -nE '(^|[^`/[:alnum:]])[0-9](장|\.[0-9])' SKILL.md create/SKILL.md improve/SKILL.md \
  | grep -v 'references/[a-z-]*\.md` *[0-9~]*장'
```

두 검사 모두 `verify_skill.py` 에 들어 있다. 손으로 돌릴 필요는 없다.

**판별 기준 — 같은 줄에 참조 파일 경로가 선행하는가**

```
`../references/teardown.md` 5장의 8개 필수 구성 요소를 모두 포함한다   ← 정상
`../references/output-contract.md` 의 검증 규율에 따라                ← 정상
검증 규율에 따라 다시 검증한다                                        ← 결함 (파일 지목 없음)
```

> ⚠️ **경로 없는 이름 참조는 이 검사를 통과한다.** 숫자가 없으니 걸리지 않는다.
> 라우터로 들어가는 본문이 참조 문서의 절을 이름으로 가리키면 사람이 판별해야 한다.
> 판별 기준표는 9.3에 있다.

## 4. 왜 스크립트인가 — 산문 절차의 한계

재현 실험을 4회 수행했다. 매 회차 **다른 지점**에서 누락이 발생했다.

| 회차 | 결함 | 문제가 이동한 방향 |
|------|------|-------------------|
| 1차 | 변환 규칙 자체가 없음 → 참조 3개가 고아 파일 | 무엇을 |
| 2차 | `4장` 표기 1건을 눈으로 못 찾음 | 어떻게 찾을지 |
| 3차 | 절차 장만 검사해 금지 사항 장의 `(6.9)` 누락 | 어디까지 |
| 4차 | 치환만 하고 `**Load**` **삽입**을 누락 | 어떤 동작인지 |

산문 절차를 고칠 때마다 새 구멍이 생겼다. 이는 산문의 한계다.

`/skill-development` 의 `SKILL_BEST_PRACTICES.md` 가 이 상황을 정확히 지시한다.

> *"Look for repeated code: Did the agent write similar scripts multiple times? **Bundle these in `scripts/`.**"*

같은 빌드 스크립트를 4번 썼다는 것이 곧 그 신호였다.

**멱등성은 스크립트만 보장한다.** 같은 입력에 바이트 단위로 같은 출력을 낸다.
산문 절차는 LLM 해석을 거치므로 매번 달라진다.

### 검증 스크립트의 실측 성과

`verify_skill.py` 는 **수작업 검토 4회가 놓친 손작업 스킬의 실제 결함 2줄**을 찾아냈다.

```
SKILL.md:56        구조 결함(품질 기준 1장)      ← 파일 지목 없는 죽은 좌표
create/SKILL.md:108  6장 안전장치를 적용한다.      ← 같음
```

기계적 검사가 사람 눈보다 이 부류에 강하다.

## 5. 분할 근거 — 왜 이렇게 나눴는가

`/skill-development` 의 일반 기준(500줄 초과, 3+ 분기)에 더해, 이 스킬에는 다음 사정이 있다.

| 결정 | 근거 |
|------|------|
| 라우터 + 서브스킬 2개 | CREATE와 IMPROVE는 **단계 구성이 완전히 다르다**. 한쪽 작업에 다른 쪽 워크플로가 들어갈 이유가 없다 |
| 참조 3분할 | 로드 시점이 서로 다르다 — `output-contract` 는 문서 작업 직전, `teardown` 은 객체 대장/`98_` 작업 시, `quality-bar` 는 검토·갭 분석 시 |
| 참조를 라우터에서 로드하지 않음 | 모드 판별만 하고 끝나는 대화가 있다. 그때 참조 515줄은 낭비다 |

### 초기 로드 실측 (단일 파일 → 분할)

| 시점 | 단일 파일 | 분할 후 |
|------|-----------|---------|
| 라우터 진입 | 398줄 | **150줄** |
| CREATE 착수 | 797줄 | **336줄** |
| 모드 판별만 하고 종료 | 797줄 | **150줄** |

> 분할은 *총* 토큰을 줄이는 것이 아니라 **쓰지 않을 내용의 로드를 없애는 것**이다.
> 절감은 (a) 반대 모드, (b) 아직 필요 없는 참조에서 나온다.

### 6.1 서브스킬 필수 절 (누락 빈발)

서브스킬(`create/`, `improve/`)은 아래 6개 절을 **모두** 갖는다.
명세 6·7장(CREATE/IMPROVE)에는 **STEP 본문만** 있다. 나머지는 **옮길 때 새로 써야 한다.**
이 사실을 모르면 조용히 빠진다.

| 절 | 원본에 있나 | 내용 |
|----|-------------|------|
| `## When to Load` | ❌ **새로 작성** | 라우터의 어느 판정에서 진입하는가 |
| `## Prerequisites` | ❌ **새로 작성** | 진입 시점에 확보되어 있어야 하는 것 (`GOAL` / `TARGET_FOLDER` 등) |
| 참조 경로 안내 | ❌ **새로 작성** | `../references/` 표기 이유 한 줄 (7.1) |
| `## Workflow` | ❌ **헤딩을 새로 작성** | 명세 6·7장은 `### STEP C0` 부터 바로 시작하고 `## Workflow` 헤딩이 없다. STEP 본문을 이 헤딩 아래에 넣는다 |
| `## Stopping Points` | ❌ **새로 작성** | 본문의 `⚠️ STOP` 을 **요약 목록으로 재수집** |
| `## 금지 사항` | ✅ 8장 모드별 절 | 해당 모드 전용만. 공통은 라우터에 |
| `## Output` | ❌ **새로 작성** | 원본에는 없다. 이 모드가 만들어내는 산출물을 명시한다 (CREATE: `00_`~`99_` 파일 목록 / IMPROVE: 변경·신규 파일과 누적 이력) |

> 실측: 2차 재현에서 `## Workflow` 와 `## Output` 이 "원본에 있음"으로 오기되어 둘 다 누락되었다.
> **원본에 헤딩이 없는 것과, 내용이 없는 것을 구분한다.** `Workflow` 는 내용은 있고 헤딩만 없다.
> `Output` 은 둘 다 없다.

#### `## Stopping Points` 를 반드시 별도 절로 두는 이유

명세는 중단점을 본문에 `⚠️ STOP` 으로 **흩어 놓기만** 한다.
본문만 옮기면 요약 절이 없어 모델이 전체 중단 지점을 한눈에 파악하지 못한다.
실측: 이 절을 빼면 중단점 인식이 22개 → 13개로 줄었다.

작성 방법 — 본문의 `⚠️ STOP` 을 스캔해 STEP 번호와 함께 나열한다.

```markdown
## Stopping Points

- ✋ C0: `GOAL` / `TOPIC_SLUG` / 문서 구성 승인
- ✋ C0: 대상 폴더에 이미 파일이 있을 때
- ✋ C1: 계정 제약으로 실습 불가 항목 발견 시
- ✋ C8: 최종 리뷰
```

IMPROVE 의 `✋ I3` (개선 계획 승인)은 **가장 중요한 중단점**이다. 반드시 포함하고 강조한다.

#### 검증

```bash
for f in create/SKILL.md improve/SKILL.md; do
  echo "== $f"
  for s in "When to Load" "Prerequisites" "Workflow" "Stopping Points" "금지 사항" "Output"; do
    grep -q "^## .*$s" "$f" && echo "  ✅ $s" || echo "  ❌ $s 누락"
  done
done
```

## 7. 주의 사항 — 실제로 겪은 문제

### 7.1 서브스킬의 참조 경로 (반드시 확인)

서브스킬은 하위 폴더(`create/`, `improve/`)에 있다.
여기서 `references/20_teardown-registry.md` 로 쓰면
`create/references/20_teardown-registry.md` 로 해석될 수 있다.
**도달 불가 참조가 되는 실제 버그다.**

- 서브스킬에서는 `../references/<조각>.md` 로 표기한다
- 각 서브스킬 상단에 경로 안내 한 줄을 둔다
- 라우터(`SKILL.md`)는 루트에 있으므로 `references/<조각>.md` 가 맞다

검증: `verify_skill.py` 의 `[6.1]` 항목이 자동으로 본다. 수동 확인은 아래.
```bash
grep -n '`references/' create/SKILL.md improve/SKILL.md   # 결과 없어야 정상
```

### 7.2 라우터에서 참조를 로드하지 않는다

라우터의 참조 표는 **로드 시점 안내**일 뿐이다. "항상 로드"로 지시하면 5장(분할 근거)의 절감이 사라진다.
실제 로드 지시(`**Load**`)는 서브스킬의 해당 STEP에만 둔다.

### 7.3 동기화는 단방향이다 — 명세 → 스킬

**스킬 파일을 직접 고치지 않는다.** 명세(`교육자료 생성 프롬프트.md`)를 고치고
`build_skill.py` 를 다시 돌린다. 스킬은 산출물이므로 직접 수정하면 다음 빌드에 덮어써진다.

빌드 결과가 의도와 다르면, 원인은 셋 중 하나다.
1. 명세 본문 — 명세를 고친다
2. 참조 주입 누락 — `build_skill.py` 의 `SUB_ROUTER` / `SUB_LEAF` 에 추가한다 (3.1)
3. 골격(frontmatter·필수 절·템플릿) — `build_skill.py` 의 해당 부분을 고친다

### 7.5 워크스페이스 스테이지 파일시스템 — 조용히 실패한다

`/workspace` 는 Snowflake 스테이지 마운트이며 완전한 POSIX 파일시스템이 아니다.
**명세·스크립트를 편집할 때 실제로 문서를 손상시킬 수 있는 함정**이므로 여기 남긴다.
(교육자료 작성자용 같은 내용은 명세 2.2 에 있다. 이 절은 **스킬 정본 편집자용**이다.)

| 동작 | 결과 | 회피 |
|------|------|------|
| **`>> 파일` 추가 리다이렉트** | ❌ `Operation not supported`. **조용히 실패한다** — 종료 코드 0, `wc -l` 도 정상처럼 보인다 | `/tmp` 에서 전체를 만든 뒤 `cp` 로 덮어쓴다 |
| **쓰기 직후 읽기** | ⚠️ 잘린 내용이 보일 수 있다 | 잠깐 대기 후 재시도. **디코드 실패를 손상으로 단정하지 않는다** |
| 디렉터리 `mv` | ❌ `Input/output error` | 복사 → 재귀 `diff` → 원본 제거 |
| `rm -rf <중첩 디렉터리>` | ❌ `Directory not empty` 부분 실패 | `find -type f -exec rm -f` → `find -depth -type d -exec rmdir` |
| `$(find ...)` 워드 분할 | 공백 포함 파일명이 깨진다 | `-print0` + `while IFS= read -r -d ''` |

> 🔴 **실측 사고.** 명세를 쓴 직후 읽기가 `UnicodeDecodeError`(문자 중간 절단)로
> 실패해 **파일이 손상된 것으로 판단하고 복구를 준비했다.** 잠시 뒤 다시 읽으니
> 온전했다 (89,872 → 91,756 바이트). 즉 **쓰기가 아직 반영 중인 상태를 읽은 것**이다.
>
> 온전한 파일을 "복구"하려다 실제로 망칠 수 있었다. 그래서 규칙은 이렇다 —
> **파일 크기와 디코드 가능 여부를 함께 확인하고, 복구를 시작하기 전에 두 번 확인한다.**

편집 후에는 **반드시 내용으로 확인한다.** 종료 코드나 줄 수는 근거가 아니다.

```bash
grep -c "<새로 넣은 문구>" "<파일>"    # 0 이면 반영되지 않았다
```

이것은 명세 5장의 `"성공 응답" 은 검증 근거가 아니다` 와 같은 원칙이다.
스킬을 고치는 작업 자체에도 그 원칙이 적용된다.

### 7.4 (참고) 과거 양방향 동기화 이력

스킬을 고치면서 워크플로가 바뀌면 **`교육자료 생성 프롬프트.md` 에 역반영한다.**
반영하지 않으면 다음 재현 때 그 개선이 사라진다.

실제 사례: 리팩터링 중 CREATE에 `STEP C1 계정 적합성 사전 확인`을 신설했으나 명세에
반영하지 않아, 같은 md로 재생성하면 그 단계가 없는 스킬이 나오는 상태가 되었다.

동기화 대상:
- 단계 추가·삭제·순서 변경
- 중단점(`⚠️ STOP`) 변경
- 금지 사항 추가
- 품질 기준·심각도 변경

동기화 대상이 아닌 것(이 문서에만 기록):
- 파일 분할 방식, 참조 경로, frontmatter, 트리거

## 8. 재현 검증

### 8.1 자동 가드 — `build_skill.py` / `verify_skill.py` 가 막아 주는 것

**사람이 기억할 필요가 없는 항목**이다. 아래는 전부 실패하면 빌드나 verify 가 멈춘다.
가드를 새로 넣을 때는 **반드시 실패를 주입해 작동을 확인한다** (9.6).

| 가드 | 위치 | 막는 것 |
|------|------|---------|
| `check_subs()` | build | 치환 키가 명세에 없으면 빌드 중단. **조용한 무효화 방지** |
| `load_chapters()` | build | 명세 `## 0`~`## 8` 장 누락 |
| 3단 절번호 차단 | build | `### N.M.K` 는 재번호되지 않아 죽은 좌표가 된다 |
| `chapter_sections()` 범위 검사 | build | `sections` 에 없는 절을 지정 |
| `tidy()` | build | 연속 구분선·과다 빈 줄 |
| 허브 `< 200줄` | verify | 코디네이터가 비대해지는 것 (호출마다 읽힌다) |
| 조각 `<= 400줄` | verify | 한 조각에 관심사가 둘 이상 섞이는 것 |
| 허브 포인터 표 ↔ 실제 조각 일치 | verify | 조각이 늘거나 이름이 바뀔 때의 표 드리프트 |
| 죽은 좌표 (허브·리프) | verify | `7장`, `3.5` 같은 존재하지 않는 좌표 |
| 죽은 좌표 (`references/`) | verify | 조각 안의 `N.M` 절 좌표 |
| 고아 조각 | verify | 어느 서브스킬도 `**Load**` 하지 않는 조각 |
| 리프 필수 6개 절 | verify | `When to Load` / `Prerequisites` / … 누락 |
| 참조 경로 `../references/` | verify | 서브스킬의 도달 불가 참조 (7.1) |

> - **파일명 없는 절 이름 참조**가 라우터에서 도달 가능한지 (9.4)
> - 조각 분할이 **의미 이음매**를 따랐는지 (3.0 — 한도만 자동으로 본다)

## 9. 개선 피드백 루프 — 스킬을 실제로 써서 명세를 고친다

### 9.1 왜 이 절이 필요한가

`build_skill.py` / `verify_skill.py` 는 **명세와 스킬이 일치하는지**만 보장한다.
**명세 자체가 틀렸거나 비어 있는 것**은 잡아내지 못한다.
22/22 통과가 "명세가 완전하다"는 뜻은 아니다.

명세의 구멍은 스킬을 **실제 교육자료에 적용했을 때만** 드러난다.
따라서 다음 루프를 돈다.

```
명세 → build → 스킬 → 실제 자료에 CREATE/IMPROVE 적용
                              ↓
                    명세에 없던 결함 유형 발견
                              ↓
                    명세에 역반영 → 재빌드 → verify
```

### 9.2 실제 사례 (2026-09-16, openflow-cdc 자료)

스킬을 `openflow-cdc/` 에 IMPROVE 모드로 적용해 🔴 4건을 찾았는데,
그중 **2건은 명세에도 없던 구멍**이었다.

| 발견 | 명세의 구멍 | 역반영 |
|------|-------------|--------|
| 실습이 `ALTER USER … SET DEFAULT_SECONDARY_ROLES` 로 **기존 사용자 객체를 영구 변경**하는데 대장·정리 어디에도 없었다 | 3장 대장이 "실습에서 **생성하는** 모든 것"만 다루고 **피할 수 없는 속성 변경**의 원복 범주가 없었다. 8장 금지 사항은 "기존 객체를 변경하지 않는다"고만 해서 불가피한 경우의 처리 지침이 없었다 | 3장에 "속성 변경(Mutation)" 절 신설 (대장 3부 구조 + 필수 3단계), 3.7 자체 검증에 `ALTER … SET` grep 추가, 7.4 품질 기준에 6항목 추가, 8장 금지 사항을 "등재 없이 변경 금지"로 수정 |

교훈: **정리 검증 쿼리는 실습 리소스가 없어도 실행할 수 있는 유일한 부분**이므로
반드시 실행해 본다. 이것을 건너뛰면 "정리 문서가 있다"는 사실만 남고
"정리 문서가 동작한다"는 보장은 없다.

(번호 체계·메타 주석·인덱스 없음)였고, `.md` 설명 문서 비중이 컸다.

| 발견 | 명세의 구멍 | 역반영 |

| `AI_PARSE_DOCUMENT('@stage', file, {...})` — 구버전 `PARSE_DOCUMENT` 시그니처를 신규 함수명에 적용해 **컴파일 실패** | "모델 기억 금지"는 있었으나 **구·신 함수 공존**이라는 구체적 함정이 결함 유형에 없었다 | 결함 유형 표에 "구·신 함수 혼용" 행 추가 + 전용 절 신설 (신규 이름으로 재확인, 반환 타입 확인, 컴파일 필수) |
| 개념 심화 자료·부서 핸드오프 요청서가 **번호 없이** 폴더에 흩어져 있었다. 금지 사항의 "계획·분석 문서 금지"와 구분이 모호 | 문서 번호 규칙이 `02_`~`97_` 를 실습 단계로만 정의해 **부수 문서의 자리**가 없었다. 원본의 실습 전/후 환경 대조 문서도 둘 곳이 없었다 | 번호 규칙을 `02_`~`89_` 실습 / `90_`~`94_` 부수 문서 / `95_`·`96_` 왕복 검증으로 재편. "허용되는 부수 문서" 표와 "왕복 검증 문서" 절 신설, 금지 사항에 예외 명시 |

교훈 3가지:

1. **컴파일·실행 검증은 "동작하는 거짓"을 잡지 못한다.** 기능 성격 오인, 미측정 수치,
   총괄 합격 선언은 모두 SQL이 정상 동작하는 상태에서 성립한다. 이 부류는
   **공식 문서 대조와 서술 규칙**으로만 막을 수 있다.
2. **`.md` 는 설명 문서가 아니라 실행 경로다.** 실습자는 코드블록을 복사해 실행한다.
   추출·정리·대장 대조에서 `.md` 를 제외하는 순간 왕복 가능성이 깨진다.
3. **"통과하는 체크리스트 항목"을 의심한다.** `멱등성 확보` 항목은 `OR REPLACE` 로도
   통과했다. 항목이 **무엇을 근거로 통과했는지**까지 규정하지 않으면 기준은 무력하다.

### 9.4 역반영 시 주의 — 좌표를 새로 만들지 않는다

명세에 하위 절을 추가할 때 `### 3.1.1` 처럼 **번호를 붙이면 안 된다.**

- `build_skill.py` 의 `assemble_reference()` 는 `### N.M` 을 `## M'.` 로 재번호한다
- 3단(`### N.M.K`)은 **재번호 대상이 아니어서 그대로 남는다** → 죽은 좌표
- 본문에서 `(3.1.1 참고)` 로 참조해도 마찬가지다

번호 없는 제목(`#### <제목>`)을 쓰고, 본문에서는 `"<절 제목>" 절` 로 참조한다.
좌표가 없으면 재번호에 영향받지 않는다.

> ✅ **이제 이 규칙은 자동으로 막힌다.** 3단 절번호를 쓰면 빌드가 중단된다
> (8.1). 과거에는 사람이 기억해야 했고, 실제로 `### 3.1.1` 로 작성했다가
> verify 가 떨어진 이력이 있다.
>
> 🔴 **그럼에도 숫자 좌표 자체를 만들지 않는 것이 낫다.** 2단 절번호(`3.2`)를
> **본문에서 참조**하면 조각 재번호 뒤 죽은 좌표가 된다. 실측: `위 3.2 표의` 가
> `## 7` 과 `## 8` 사이에 남아 있었고, verify 가 `references/` 를 훑지 않아
> 22/22 로 통과하고 있었다. **본문 참조는 항상 절 제목으로 한다.**

**번호를 없애도 끝이 아니다.** 절 이름으로 참조하면 죽은 좌표 검사는 통과하지만,
**라우터에서는 그 절이 어느 파일에 있는지 알 수 없다.** 라우터는 설계상
`references/` 를 로드하지 않기 때문이다(6.2).

따라서 8장 금지 사항처럼 **라우터로 들어가는 본문**이 참조 문서의 절을 가리키면
`build_skill.py` 의 `SUB_ROUTER` 에 파일명을 붙이는 변환을 추가해야 한다.

```python
# 8장 공통 금지 사항 — 라우터는 조각을 로드하지 않으므로 파일명을 명시한다
('그것을 **대장 (b) 속성 변경 행으로 등재하고 "속성 변경(Mutation)" 절의 3단계',
 f'그것을 **대장 (b) 속성 변경 행으로 등재하고 {tdr} 의 "속성 변경(Mutation)" 절 3단계'),
```

> 조각 상수는 `OC` / `VD` / `TDR` / `TDX` / `QB` (서브스킬용, `../` 포함) 와
> 소문자 `oc` / `vd` / `tdr` / `tdx` / `qb` (라우터용, `../` 없음) 두 벌이다.

판별 기준:

| 본문이 들어가는 곳 | 참조 표기 |
|---------------------|-----------|
| 라우터 (0·1·8장 공통) | `SUB_ROUTER` 에 `references/<파일>.md` 를 붙인다 (`../` 없음) |
| 서브스킬 (5·6·8장 모드별) | `SUB_LEAF` 에 `../references/<파일>.md` 를 붙인다 |
| 참조 문서 내부 (2·3·4·7장) | 같은 파일 안이므로 절 이름만으로 충분하다 |

`verify_skill.py` 는 **숫자 좌표만** 검사한다. 파일명 없는 절 이름 참조는
잡아내지 못하므로 이 판별은 사람이 해야 한다.

### 9.5 루프 실행 체크리스트

- [ ] 스킬을 실제 자료에 적용했다 (CREATE 또는 IMPROVE)
- [ ] 발견한 결함마다 "명세가 이걸 막았는가?" 를 물었다
- [ ] 막지 못한 결함 유형을 명세에 역반영했다 (스킬을 직접 고치지 않는다 — 7.3)
- [ ] 역반영이 8장 금지 사항과 모순되지 않는지 확인했다
- [ ] 새 하위 절에 번호를 붙이지 않았다 (9.4)
- [ ] 본문 참조를 **절 제목**으로 했다 (숫자 좌표 금지 — 9.4)
- [ ] `build_skill.py` 재실행 → `verify_skill.py` **전 항목 통과**
- [ ] `build_skill.py --check` 차이 0건, 연속 2회 빌드 바이트 동일

## 10. 변경 절차 — 구조·도구를 고칠 때

### 10.1 9장과 무엇이 다른가

| | 9장 개선 피드백 루프 | 10장 변경 절차 |
|---|---|---|
| 고치는 대상 | 명세의 **내용** (규칙이 빠졌다) | 명세의 **구조**와 **빌드·검증 도구** |
| 계기 | 스킬을 실제 자료에 적용해 결함 발견 | 문서가 커짐, 가드 사각지대, 가독성 |
| 위험 | 규칙이 서로 모순될 수 있다 | **빌드가 깨지거나 조용히 잘못 나온다** |

9장은 "무엇을 쓸까", 10장은 "**어떻게 손대야 안 깨지나**" 다.

### 10.2 기본 루프 — 한 번에 하나씩

```
① 기준선 확인:  build → verify 전 항목 통과   ← 초록에서 출발한다
② 변경 1건 적용 (명세 또는 스크립트)
③ 내용 확인:   grep -c "<넣은 문구>" <파일>    ← 7.5, 종료 코드는 근거가 아니다
④ build → verify
⑤ 실패하면 즉시 고친다. 다음 변경으로 넘어가지 않는다
→ ② 로 돌아간다
```

> 🔴 **①을 건너뛰지 않는다.** 이미 깨진 상태에서 출발하면, 내가 깨뜨린 것인지
> 원래 깨져 있던 것인지 구분할 수 없다.
>
> 🔴 **여러 변경을 몰아서 빌드하지 않는다.** `check_subs` 가 실패하면 어느 변경이
> 원인인지 좁히는 데 더 오래 걸린다.

### 10.3 치환 키와 함께 고쳐야 하는 것

`build_skill.py` 는 **명세의 문장을 정확히 일치하는 문자열로** 찾아 치환한다(3.1).
따라서 **명세의 그 문장을 바꾸면 키도 함께 바꿔야 한다.**

| 명세에서 바꾼 것 | 함께 고칠 곳 |
|---|---|
| 치환 키가 된 문장·불릿 | `SUB_ROUTER` / `SUB_LEAF` 의 해당 키 |
| `## 0.` / `## 1.` 장 제목 | `SUB_ROUTER` (장 제목이 키다) |
| `### 공통` / `### CREATE 모드 전용` / `### IMPROVE 모드 전용` | `prohibition()` 이 찾는 제목 |
| `**A. …**` 금지 그룹 라벨 | `proh_groups()` 의 `keep` / `drop` |
| `### STEP …` 제목 | `LOADS` 의 삽입 대상 헤딩, `stopping_points()` |
| 장·절 순서·번호 | `REFERENCES` 의 `chapters` / `sections` |

> ✅ **키가 어긋나면 빌드가 멈춘다** (`check_subs`). 조용히 무효화되지 않는다.
> 오류 메시지가 어긋난 키를 그대로 보여 주므로 그것을 명세와 맞추면 된다.

**실측 사례.** `98_` 필수 구성을 `8개 → 9개` 로 늘릴 때, 명세의 문장 2곳과
`build_skill.py` 의 치환 키 1개 + 참조 설명 1개를 **같이** 고쳐야 했다.
명세만 고치면 빌드가 중단되고, 키만 고치면 산출물에 옛 숫자가 남는다.

### 10.4 가드를 추가하면 실패를 주입해 증명한다

**검사를 넣고 작동을 안 믿는 상태로 두지 않는다.** 통과하는 것은 근거가 아니다 —
검사가 애초에 아무것도 보지 않아도 통과한다.

```
① 가드 추가
② 백업:      cp <파일> /tmp/<파일>.bak
③ 결함 주입:  가드가 잡아야 할 것을 일부러 넣는다
④ 실행:      실패하는지, 메시지가 위치를 지목하는지 확인
⑤ 복원:      cp /tmp/<파일>.bak <파일>
⑥ 재확인:    build → verify 전 항목 통과, 주입 흔적 0건
```

이 세션에서 추가한 가드 4개를 모두 이 방식으로 확인했다.

| 가드 | 주입한 결함 | 나온 메시지 |
|---|---|---|
| 3단 절번호 차단 | `### 3.3` → `### 3.2.1` | `3단 절번호 헤딩은 재번호되지 않아 죽은 좌표가 된다: 3.2.1` |
| `references/` 죽은 좌표 | 본문에 `위 3.2 표의` | `references/10_output-contract.md:330: 3.2 — …` |
| 조각 한도 | 조각에 120줄 채움 | `초과: 30_quality-bar.md 543줄 → 의미 이음매를 찾아 분할하라` |
| 포인터 표 드리프트 | 고아 조각 파일 생성 | `어긋남: ['99_orphan-test.md']` |

> 💡 **이 검증이 곧바로 값을 했다.** `references/` 죽은 좌표 가드를 넣은 직후,
> 5.3 절을 분할하면서 내가 새로 만든 `(5.3)` 좌표를 그 가드가 잡아냈다.
> 사람이 놓칠 자리였다.

### 10.5 가드의 사각지대를 의심한다

**"전 항목 통과" 는 "결함이 없다" 가 아니다.** 검사가 그 파일을 보지 않았을 수 있다.

실측: 죽은 좌표 검사가 `SKILL.md` 와 리프 2개만 훑고 **`references/` 를 보지 않았다.**
그래서 조각 안의 죽은 좌표 2건이 **22/22 통과 상태로 누적**되어 있었다.
`build_skill.py` 주석에 남아 있던 "스테일 키 14개가 22/22 통과 상태였다" 와 같은 유형이다.

| 규칙 | 내용 |
|---|---|
| **파일 종류를 늘리면 검사 범위도 늘린다** | 조각 폴더를 만들었으면 조각도 훑는다 |
| **목록을 손으로 나열하지 않는다** | `shards()` 처럼 **파일시스템에서 읽는다.** 하드코딩하면 새 파일이 조용히 빠진다 |
| **생성물은 생성한다** | 허브 포인터 표는 `pointer_table()` 이 만든다. 손으로 쓰면 반드시 어긋난다 |

> 실측: 조각을 5개로 나눈 뒤에도 손으로 쓴 포인터 표에는 **옛 파일명 3개**가
> 남아 있었다. 예측했던 드리프트가 그대로 발생했다.

### 10.6 산출물을 직접 고치지 않는다 — 예외 하나

원칙은 7.3(단방향 동기화)이다. **예외는 조각 이름이 바뀌거나 줄어들 때다.**
빌드는 파일을 **덮어쓰지만 지우지는 않는다.** 옛 이름의 조각이 남아 고아가 된다.

```bash
# 조각 이름을 바꾼 뒤 옛 파일을 지운다
cd /workspace/.snowflake/cortex/skills/edu-doc-generator-ihcho/references
rm -f <옛-조각>.md
```

지우지 않으면 `verify_skill.py` 의 **포인터 표 일치 검사**가 잡아낸다(8.1).
실측: 조각 5개로 재편한 뒤 옛 파일 3개가 남아 있었다.
