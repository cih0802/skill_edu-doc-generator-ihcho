# 교육자료 생성·개선 프롬프트

> **목적**: 사용자가 입력한 **학습 목표(GOAL)** 로부터, Snowflake 환경에서 **SQL 기반으로 직접 실습하고 데이터 적재 검증까지 완료할 수 있는 교육자료 세트**를 생성한다.
> 또한 **이미 만들어진 교육자료를 읽어 같은 기준으로 개선**한다.
>
> 이 문서는 스킬(`edu-doc-generator-ihcho`)의 **워크플로 명세서**다.
> LLM이 그대로 실행 가능한 절차서 형태로 기술한다.
> 문서 규격·검증 규율·정리 요구사항·품질 기준은 **두 모드가 공유하는 단일 기준**이다.

## 관련 문서

| 문서 | 담당 |
|------|------|
| **이 문서** | 교육자료를 **무엇을 어떻게** 만들 것인가 — 워크플로, 규격, 품질 기준 |
| `교육자료 스킬 패키징.md` | 이 명세를 **스킬로 어떻게 포장**할 것인가 — 이름, 파일 분할, 트리거, 설치 위치 |
| `/skill-development` 스킬 | 스킬 제작 **일반론** — 분할 기준, 500줄 한도, 라우터 패턴, frontmatter 작성법 |

**스킬을 재현하려면 이 문서만으로는 부족하다.** `교육자료 스킬 패키징.md` 를 함께 본다.

> ⚠️ **동기화 의무**: 스킬 쪽에서 워크플로를 고쳤다면 이 문서에 역반영한다.
> 반영하지 않으면 다음 재현 때 그 개선이 사라진다.
> 대상: 단계 추가·삭제·순서 변경, 중단점 변경, 금지 사항 추가, 품질 기준 변경.

## 이 문서를 읽는 방법

**전부 읽지 않아도 된다.** 아래 순서로 필요한 장만 읽는다.

1. **0장**으로 모드(CREATE / IMPROVE)를 판정한다 — 항상 먼저.
2. **1장**에서 입력 변수를 확보한다.
3. 모드에 해당하는 **절차 장**(6장 또는 7장)으로 간다.
4. 절차가 지시하는 시점에만 **기준 장**(2~5장)을 펼친다.
5. **8장**은 전 과정에서 항상 유효하다.

### 장 지도

| 장 | 역할 | 성격 | 언제 읽는가 |
|----|------|------|-------------|
| **0** 모드 판별 | CREATE / IMPROVE 판정 | 라우팅 | 항상 가장 먼저 |
| **1** 입력 | `GOAL` / `TARGET_FOLDER` 등 변수 | 라우팅 | 모드 판정 직후 |
| **2** 산출물 규격 | 폴더·번호·분리·메타 주석·SQL 원칙 | **기준** | 문서를 쓰거나 읽기 직전 |
| **3** 검증 규율 | 근거 우선순위, 실행 vs 컴파일, 미검증 표기 | **기준** | 정확성을 주장하기 직전 |
| **4** 정리 요구사항 | 객체 대장, 사전 스냅샷, `98_` 구성 | **기준** | 대장 작성 / `98_` 작업 시 |
| **5** 품질 기준 | 구조·내용·정확성·정리 체크리스트 + 심각도 | **기준** | 자체 검토 / 갭 분석 시 |
| **6** CREATE 절차 | STEP C0 ~ C8 | **절차** | CREATE 모드일 때만 |
| **7** IMPROVE 절차 | STEP I0 ~ I8 | **절차** | IMPROVE 모드일 때만 |
| **8** 금지 사항 | 공통 + 모드별 | **제약** | 항상 |

> **2~5장이 기준이고 6~7장이 절차다.** 기준은 두 모드가 공유하며,
> 절차는 모드마다 다르다. 이 분리가 이 문서의 골격이다.

### 표기 규약

| 표기 | 뜻 |
|------|-----|
| **⚠️ STOP** | 사용자 승인 없이 다음으로 넘어가지 않는다 |
| **생략 금지** | 시간이 부족해도 건너뛸 수 없는 단계 |
| 🔴 / 🟡 / 🟢 | 품질 결함 심각도 — 치명 / 중요 / 개선 |
| `01_` `98_` | 산출물 문서의 번호 접두사 |
| `<대문자>` | 치환할 변수 (`<TOPIC_SLUG>`, `<N>`) |

> **장 사이 참조는 번호가 아니라 이름으로 한다** (예: "검증 규율에 따라").
> 장 순서가 바뀌어도 참조가 깨지지 않도록 하기 위한 규약이다.
> 새 하위 절에 번호를 붙이지 않는 이유도 같다.

### 가장 자주 위반되는 제약 — 먼저 읽는다

세부 근거는 각 기준 장에 있다. 아래는 실제 산출물에서 반복 발견된 것만 모았다.

| # | 제약 | 위반하면 |
|---|------|----------|
| 1 | 측정 절차 없이 **성능·절감률·방어율 수치**를 쓰지 않는다 | 독자가 거짓 수치를 의사결정에 쓴다 |
| 2 | **"검증 완료" 총괄 선언**을 쓰지 않는다. 검증은 항목 단위로만 주장한다 | 항목별 미검증 표기가 무력화된다 |
| 3 | 이름이 비슷한 **두 제품 기능을 확인 없이 동일시**하지 않는다 | 아키텍처 설명 전체가 거짓이 된다 |
| 4 | 객체 추출은 `.sql` 이 아니라 **폴더 전체**(`.md` 코드블록 포함)에서 한다 | 계정 변경이 정리 대상에서 빠진다 |
| 5 | **`CREATE OR REPLACE` 는 멱등성이 아니다.** 계정 레벨 객체에 쓰지 않는다 | 동명 사용자 자산을 파괴한다 |
| 6 | 스냅샷 **실측값을 전사하지 않는다.** 쿼리와 빈 서식만 둔다 | 대조 기준이 즉시 낡아 무의미해진다 |

## 0. 모드 판별 (MODE) — 항상 가장 먼저 수행

### 발화 신호

| 신호 | 모드 |
|------|------|
| "…실습 교육자료 만들어줘", "목표: …" | CREATE |
| "개선", "보완", "업데이트", "최신화", "검토해줘", "빠진 것 채워줘", "고쳐줘" | IMPROVE |
| 기존 폴더명·문서명·경로를 언급 | IMPROVE |

### 작업 공간 스캔 — 발화가 모호할 때의 근거

```bash
cat "/workspace/00_교육자료_카탈로그.md" 2>/dev/null      # 등록된 교육자료 목록 — 가장 먼저 본다
ls -d /workspace/EDU-*/ 2>/dev/null
```

`01_*.md` 또는 `00_index.md` 를 포함한 폴더는 이 스킬의 산출물로 간주한다.
카탈로그에 등록되어 있으면 그 자체가 산출물이라는 근거다.

> ⚠️ 카탈로그에 없는데 `EDU-` 접두사 없이 존재하는 폴더는 **구 규칙 산출물**일 수 있다.
> IMPROVE 대상이 될 수 있으므로 무시하지 않는다.

### 판정 및 라우팅

| 상황 | 조치 |
|------|------|
| 관련 폴더 없음 + 목표 있음 | **CREATE** 로 진행 |
| 관련 폴더 있음 + 개선 의도 명확 | **IMPROVE** 로 진행 |
| 폴더 있음 + 목표만 주어짐 | **⚠️ STOP.** 아래 ⓐ 질문 |
| 폴더 후보가 여러 개 | **⚠️ STOP.** 목록 제시 후 선택받고 재판정 |
| 개선 의도인데 폴더 없음 | **⚠️ STOP.** "개선할 기존 자료를 찾지 못했습니다. 경로를 알려주시거나, 새로 만들까요?" |
| 폴더가 이 스킬 산출물이 아님 | **⚠️ STOP.** 아래 ⓑ 질문 |
| 폴더 없음 + 목표 없음 | **⚠️ STOP.** 목표를 먼저 질문 |

**ⓐ 개선 vs 신규 확인**

> "`<TOPIC_SLUG>` 폴더에 이미 교육자료가 있습니다(문서 N개). 기존 자료를 **개선**할까요, **새로 만들까요**? 새로 만들면 기존 폴더는 그대로 두고 다른 이름으로 생성합니다."

**ⓑ 규격 외 폴더**

> "`<경로>` 는 이 스킬의 문서 규격(번호 체계·메타 주석·인덱스)을 따르지 않습니다. ① 규격에 맞게 **재구성**하면서 개선할까요? ② 규격은 유지하지 않고 **내용만** 개선할까요?"

①이면 IMPROVE 모드의 규격 정렬을 전면 적용한다.
②면 IMPROVE 모드로 진입하되 구조 결함(품질 기준의 구조 항목)을 갭 분석에서 제외한다.

**모드를 추측해 진행하지 않는다.** 판정이 모호하면 멈추고 질문한다.
**기존 폴더를 확인 없이 덮어쓰지 않는다.**

## 1. 입력 (INPUT)

### CREATE 모드

| 변수 | 필수 | 설명 | 예시 |
|------|------|------|------|
| `GOAL` | 필수 | 학습 목표/주제 | `Openflow로 CDC 기능을 구현하는 실습` |
| `TOPIC_SLUG` | 자동 | 폴더명 (영문 소문자 + 하이픈) | `openflow-cdc` |
| `SOURCE_SYSTEM` | 선택 | 소스 시스템이 명시된 경우 | `PostgreSQL`, `MySQL` |

`GOAL` 이 없으면 **작업을 시작하지 않고** 목표를 먼저 질문한다.

### IMPROVE 모드

| 변수 | 필수 | 설명 |
|------|------|------|
| `TARGET_FOLDER` | 필수 | 개선 대상 폴더 경로 |
| `IMPROVE_SCOPE` | 선택 | 미지정 시 `full` |
| `IMPROVE_REQUEST` | 선택 | 사용자가 지목한 구체적 요청 |

| `IMPROVE_SCOPE` | 범위 |
|----|------|
| `full` | 전체 감사 — 규격 + 정확성 + 정리 + 완결성 (기본값) |
| `accuracy` | 문법·최신 문서 대조·계정 적합성만 |
| `teardown` | 정리 요구사항 준수만 |
| `structure` | 문서 번호·분리 규칙·메타 주석·인덱스만 |
| `extend` | **학습 범위 확장** — 기존 목표에 없던 내용 추가 |
| `specific` | `IMPROVE_REQUEST` 에 지목된 부분만 |

**개선인가 확장인가 — 반드시 구분한다**

| 요청 예시 | 성격 | `IMPROVE_SCOPE` |
|-----------|------|------|
| "잘못된 문법 고쳐줘", "검증해줘", "정리 절차 빠졌어" | 개선 | `full` 등 |
| "MySQL도 실습할 수 있게 추가해줘", "모니터링 단계도 넣어줘" | **확장** | `extend` |

사용자가 "개선"이라 말했어도 실제로는 확장인 경우, 그 사실을 알리고 승인받는다.
확장의 추가 의무는 IMPROVE 모드에 있다.

## 2. 산출물 규격 (OUTPUT CONTRACT) — 두 모드 공통

> **이 장이 정하는 것** — 무엇을 어떤 이름·번호·형식으로 쓰는가.
> 폴더 구조 · 파일 조작 제약 · 문서 번호 · 분리 규칙 · 메타 주석 · SQL 작성 원칙.

---

### 2.1 폴더 구조

교육 주제 전용 폴더를 쓰고, 모든 문서와 스크립트는 **그 폴더 하위에만** 둔다.

폴더명은 **`EDU-<NN>_<TOPIC_SLUG>`** 형식이다.

| 요소 | 규칙 |
|------|------|
| `EDU-` | 교육자료 폴더 식별 접두사. 폴더 **내부** 번호(`00_`~`99_`)와 시각적으로 구분한다 |
| `<NN>` | **생성 순번.** 두 자리(100번째부터 세 자리). **배정 후 절대 변경하지 않는다** |
| `<TOPIC_SLUG>` | 영문 소문자 + 하이픈 |

> 🔴 **번호에 분류를 넣지 않는다.** 번호는 불변 식별자이며 분야·난이도·수강 순서를
> 뜻하지 않는다. 한 자료가 여러 분야에 걸치는 것이 정상이므로(파이프라인 + 보안 +
> AI 등) 대표 분야를 번호에 넣으면 임의적이고, 분야가 바뀌면 재번호가 필요해져
> 외부 참조를 깨뜨린다. **분야는 카탈로그의 다중 태그로 관리한다.**

번호 배정과 분야 태그는 **워크스페이스 카탈로그**가 정본이다: `/workspace/00_교육자료_카탈로그.md`

```
/workspace/EDU-<NN>_<TOPIC_SLUG>/
├── 00_index.md              # 스크립트로 자동 생성되는 인덱스 문서
├── 01_교육자료_정리본.md      # 교육 문서 정리본 (개념 + 전체 흐름 + 객체 대장)
├── 02_*.sql | 02_*.md       # 프로세스 1단계 작업 문서
├── 03_*.sql | 03_*.md       # 프로세스 2단계 작업 문서
├── ...                      # 필요한 만큼 (실습 단계는 89_* 까지)
├── 90_*.md ~ 94_*.md        # 부수 문서 (선택) — 개념 심화, 실무 핸드오프
├── 95_실습전_기준선.md        # 왕복 검증 전반 (선택)
├── 96_실습후_대조.md          # 왕복 검증 후반 (선택)
├── 97_*.md                  # 외부 리소스 정리 (분량이 클 때만 분리)
├── 98_리소스정리.sql          # 전체 정리(Teardown) 문서 — 필수, 예약 번호
└── 99_generate_index.py     # 00_index.md 재생성 스크립트
```

### 2.2 🔴 워크스페이스 파일 조작 제약 — 실측

`/workspace` 는 Snowflake 스테이지 마운트이며 **완전한 POSIX 파일시스템이 아니다.**
아래는 실측된 제약이다. 모르고 작업하면 **문서를 조용히 손상시킨다.**

| 동작 | 결과 | 회피책 |
|------|------|--------|
| **셸 추가 리다이렉트 `>> 파일`** | ❌ `Operation not supported`. **조용히 실패한다** — 종료 코드와 `wc -l` 이 정상처럼 보일 수 있다 | `/tmp` 에서 전체 내용을 만든 뒤 `cp` 로 덮어쓴다 |
| 디렉터리 `mv` | ❌ `Input/output error`. 폴더 이동·이름 변경 불가 | 복사 → 재귀 `diff` 로 무결성 확인 → 원본 제거 |
| 파일 단위 `mv` / `cp` | ✅ 동작 | — |
| `rm -rf <중첩 디렉터리>` | ❌ `Directory not empty` 로 부분 실패 | `find -type f -exec rm -f` → `find -depth -type d -exec rmdir` |
| `find` 의 심볼릭 링크 | `/workspace` 가 심링크라 시작 경로를 따라가지 않는다 | `find -L /workspace` 또는 `/workspace/` (끝에 슬래시) |
| `grep --include` | BusyBox 라 미지원 | `find` 로 대상을 좁힌 뒤 `grep` |
| **쓰기 직후 읽기** | ⚠️ **일시적으로 잘린 내용이 보일 수 있다.** 실측: 쓰기 직후 읽기가 `UnicodeDecodeError`(문자 중간 절단)로 실패했고, 잠시 뒤 다시 읽으니 온전했다 (89,872 → 91,756 바이트) | 쓰기와 후속 읽기 사이에 잠깐 대기하고, **디코드 실패를 손상으로 단정하기 전에 재시도**한다 |

**필수 규율.**

1. **파일에 내용을 덧붙일 때 `>>` 를 쓰지 않는다.** 반드시 전체를 다시 쓴다
2. **쓰기 후에는 내용으로 확인한다.** 종료 코드나 줄 수만 보지 않는다
   ```bash
   grep -c "<새로 넣은 문구>" "<파일>"    # 0 이면 반영되지 않았다
   ```
3. **읽기가 깨졌다고 곧바로 손상으로 판단하지 않는다.** 잠시 뒤 재시도해 본다.
   파일 크기와 디코드 가능 여부를 함께 확인하고, **복구 작업을 시작하기 전에
   두 번 확인**한다 — 온전한 파일을 "복구" 하려다 실제로 망칠 수 있다
4. **공백이 든 파일명은 널 안전 처리**한다. `$(find ...)` 는 워드 분할로 깨진다
   ```bash
   while IFS= read -r -d '' f; do ...; done < <(find -L . -type f -print0)
   ```
5. **폴더를 지우기 전에 대체본 존재를 확인**한다. 이동으로 격리할 수 없으므로
   되돌릴 수 없다 (정리 요구사항의 아카이브 규칙 참고)

#### 허용되는 부수 문서 (`90_` ~ `94_`)

실습 단계가 아니면서 교육자료의 일부로 남길 가치가 있는 문서다. **선택 사항이며,
주제가 요구하지 않으면 만들지 않는다.**

| 유형 | 내용 | 왜 분리하는가 |
|------|------|---------------|
| 개념 심화 참고자료 | 배경 이론, 위협 모델, 제품 기능 비교 | `01_` 이 비대해지는 것을 막는다 |
| 실무 핸드오프 문서 | 유관 부서 연계 요청서, 운영 인수인계 항목 | 실습 결과를 조직에 넘기는 산출물 |
| 운영 런북 | 장애·경보 대응 절차 | 실습 단계가 아니라 운영 절차다 |

> ⚠️ **계획·분석·진행 상황 문서는 여기에 해당하지 않는다.** 그것은 만들지 않는다
> (금지 사항). 부수 문서는 **교육 대상자가 읽을 산출물**만 허용한다.

#### 왕복 검증 문서 (`95_` / `96_`)

정리(Teardown) 결과를 증명하려면 실습 전 상태와 실습 후 상태를 **대조**해야 한다.
사전 스냅샷은 `02_` 안의 한 절이지만, 기록 분량이 크거나 교육 대상자가
증빙으로 제출해야 하면 별도 문서로 분리한다.

- `95_실습전_기준선.md` — 스냅샷 **쿼리와 빈 기록 서식**을 담는다
- `96_실습후_대조.md` — 정리 후 같은 쿼리를 재실행해 `95_` 와 차이가 없음을 확인한다

> 🔴 **스냅샷 결과값을 문서에 손으로 전사하지 않는다.** 전사한 값은 계정이 바뀌면
> 즉시 거짓이 된다. 쿼리와 빈 서식을 제공하고, 값은 실습자가 채운다.
> 자세한 근거는 정리 요구사항의 "사전 스냅샷" 절 참고.

### 2.4 문서 분리 규칙 (중요)

실습이 **SQL 한 문서로 끊김 없이 진행되지 않으면 반드시 문서를 분리**한다.
분리 기준점은 **Snowflake 내부 작업 ↔ 외부 작업이 전환되는 지점**이다.

예시 (Openflow CDC):

```
02_openflow_환경구성.sql        # Snowflake 내 SQL 작업
03_소스DB_CDC_설정.md           # Snowflake 외부 작업 (수동 안내)
04_커넥터_배포_및_기동.sql       # Snowflake로 복귀, SQL 작업 계속
05_적재결과_검증.sql            # 데이터 적재 확인
97_외부리소스_정리.md            # 외부 정리 (분량이 클 때만 분리)
98_리소스정리.sql               # 전체 Snowflake 객체 정리 (필수)
```

- `.sql` 문서: Snowflake에서 실행 가능한 쿼리만 포함
- `.md` 문서: Snowflake 외부에서 수행하는 작업
  (소스 DB 설정, 네트워크, 외부 콘솔, 계정 승인, 로컬 파일 편집 등)

#### 흔한 분리 지점

| 전환 | 예시 |
|------|------|
| SQL → 외부 | 소스 시스템 설정값을 얻어와야 다음 SQL을 쓸 수 있다 |
| 외부 → SQL | 외부 설정이 끝나 Snowflake 작업을 재개한다 |
| SQL → 로컬 | 파일 다운로드·편집·업로드가 필요하다 (드라이버 JAR, 설정 JSON) |

### 2.5 파일 최상단 주석 규칙 (인덱스 생성용 필수)

`99_generate_index.py` 가 각 파일의 최상단 주석을 파싱해 인덱스를 만든다.
따라서 **모든 문서는 파일 첫 줄부터 아래 형식의 메타 주석 블록으로 시작**해야 한다.

**`.sql` 파일**
```sql
/*
title: Openflow 환경 구성
step: 02
type: sql
summary: Openflow Deployment / Runtime / Secret / 대상 DB 및 권한을 SQL로 생성한다.
requires: 없음
next: 03_소스DB_CDC_설정.md
*/
```

**`.md` 파일**
```markdown
<!--
title: 소스 DB CDC 설정
step: 03
type: md
summary: PostgreSQL의 wal_level, 논리 복제 슬롯, 퍼블리케이션을 설정한다. Snowflake 외부 작업.
requires: 02_openflow_환경구성.sql
next: 04_커넥터_배포_및_기동.sql
-->
```

**`.py` 파일**
```python
"""
title: 인덱스 생성 스크립트
step: 99
type: python
summary: 폴더 내 문서를 스캔해 00_index.md를 재생성한다.
"""
```

#### 필드 규칙

| 필드 | 규칙 |
|------|------|
| `title` | 사람이 읽는 제목 |
| `step` | 파일명 접두 번호와 일치 |
| `type` | `sql` / `md` / `python` |
| `summary` | 한두 문장. 이 문서가 무엇을 하는지 |
| `requires` | **실제 존재하는 파일명** 또는 `없음` |
| `next` | **실제 존재하는 파일명** 또는 `없음` |

`requires` / `next` 체인은 실제 파일과 일치해야 한다.
문서를 추가·삭제·번호 변경할 때 이 체인을 함께 갱신한다.

### 2.6 SQL 문서 작성 원칙

- 실행 순서대로 배치한다
- 각 블록 앞에 목적 주석을 둔다
- 하드코딩 값은 문서 상단 `-- ⚙️ 설정값` 섹션에 집약한다
- **모든 신규 객체에 공통 접두사와 `COMMENT = '... [<TOPIC_SLUG>]'` 태그를 부여한다**
- `CREATE ... IF NOT EXISTS` 로 재실행 안전성(멱등성)을 확보한다
  - 지원하지 않는 객체는 그 사실과 재실행 시 대처법을 주석으로 남긴다
  - **`CREATE OR REPLACE` 는 멱등성이 아니다** — 아래 절 참고
- 문서 상단에 **검증 상태 주석**을 둔다 (미검증 항목 표기 의무)
- 문서 말미에 `-- 🧹 리소스 정리` 섹션을 둔다
  (주석 처리 상태, 그 문서에서 만든 객체만, `98_` 참조 안내)
- **시크릿을 평문으로 남기지 않는다.** `CREATE SECRET` 등은 별도 워크시트에서
  실행하는 템플릿으로 분리하고, 그 이유를 명시한다
- **동적 SQL 의 식별자 자리를 검증 없이 문자열 결합하지 않는다** — 아래 절 참고

#### 🔴 동적 SQL — 식별자는 바인드할 수 없다

`EXECUTE IMMEDIATE` 로 DDL 을 조립하는 실습(자동 프로비저닝, 동적 마스킹 등)에서
자주 나온다. **식별자(객체명·역할명) 자리에는 바인드 변수를 쓸 수 없다.**
따라서 문자열 결합이 불가피하고, 그 값이 **데이터에서 온다면 주입 경로가 된다.**

```sql
-- 🔴 위험: v_emp_id 는 인사 원장 테이블에서 온 값이다
v_sql := 'CREATE USER ' || v_emp_id || ' DEFAULT_ROLE = ' || v_role;
EXECUTE IMMEDIATE :v_sql;
```

원장에 `FOO DEFAULT_ROLE=ACCOUNTADMIN --` 같은 값이 들어오면
의도하지 않은 DDL 이 실행된다. 실습 자료가 "인사 시스템에서 온 데이터" 를
신뢰 경계 안으로 그냥 들여보내는 구조를 가르치게 된다.

**교육자료에 넣을 최소 방어.**

1. **식별자 패턴을 검사하고, 벗어나면 거부한다** (통과시키지 않고 기록한다)
   ```sql
   IF (NOT RLIKE(v_emp_id, '[A-Za-z0-9_]{1,50}')) THEN
       INSERT INTO <감사로그> (..., ACTION_TYPE, STATUS, ERROR_MESSAGE)
       VALUES (..., 'REJECTED_UNSAFE_IDENTIFIER', 'FAILED',
               '식별자가 허용 패턴을 벗어나 동적 SQL 생성을 거부했습니다.');
       CONTINUE;
   END IF;
   ```
2. **문자열 리터럴 자리는 홑따옴표를 이스케이프한다** (`REPLACE(v, '''', '''''')`)
3. **값 자리는 가능하면 바인드**한다. 식별자만 결합으로 남긴다
4. 그 자리에 **"왜 바인드가 불가능한가" 를 주석으로 설명**한다 — 학습 포인트다

> 이것은 보안 실습이 아닌 자료에서도 적용된다. 교육자료는 실무에 복사되므로
> **주입 가능한 패턴을 예시로 남기지 않는다.**

#### 🔴 `CREATE OR REPLACE` 는 멱등성이 아니다

재실행해도 오류가 나지 않는다는 점 때문에 멱등성으로 착각하기 쉽다. 실제로는
**기존 객체를 파괴하고 새로 만든다.** 두 가지 손실이 발생한다.

| 손실 | 예시 |
|------|------|
| 실습자가 쌓은 데이터 | 적재한 청크·로그 테이블 내용, 설정 테이블에 넣은 값 |
| **동명 기존 객체** | 같은 이름의 사용자 자산을 통째로 덮어쓴다. `DROP` 으로 되돌아가지 않는다 |

규칙:

| 상황 | 조치 |
|------|------|
| 기본 | `CREATE ... IF NOT EXISTS` |
| `OR REPLACE` 가 불가피하다 | **파괴 범위를 그 자리 주석에 명시한다** |
| `DATABASE` / `WAREHOUSE` / `ROLE` 등 계정 레벨 객체 | **`OR REPLACE` 를 쓰지 않는다.** 사전 스냅샷의 접두사 충돌 검사를 게이트로 앞단에 배치 |
| "재실행 안전"이라고 서술할 때 | `OR REPLACE` 를 근거로 삼지 않는다 |

```sql
-- ⚠️ OR REPLACE: 재실행 시 이 테이블의 기존 행이 모두 사라집니다
CREATE OR REPLACE TABLE ...
```

## 3. 검증 규율 (VERIFICATION DISCIPLINE) — 두 모드 공통

> **이 장이 정하는 것** — 무엇을 근거로 "맞다"고 말할 수 있는가.
> 근거 우선순위 · 실행 vs 컴파일 · 실행 승인 범위 · 미검증 표기 의무.

정확성 주장은 근거가 있어야 한다. 두 모드 모두 아래를 따른다.

### 3.1 검증 규율 — 근거의 우선순위

정확성 주장은 근거가 있어야 한다.

1. **실제 실행 결과** — `snowflake_sql_execute` 로 실행해 확인
2. **컴파일 검증** — `only_compile=true` 로 문법 확인
3. **공식 문서** — `cortex search docs "<주제>"` 로 대조
4. ❌ **모델 기억** — 근거로 삼지 않는다. 내장 지식은 낡았을 수 있다

---

### 3.2 실행 vs 컴파일 판단

| 구문 성격 | 방법 |
|-----------|------|
| 조회·메타데이터 (`SHOW`, `DESCRIBE`, `SELECT CURRENT_*`) | **실제 실행** |
| 부작용 있음 (비용 발생, 외부 리소스 생성, 되돌리기 어려움) | `only_compile=true` |
| 선행 객체가 없어 컴파일조차 불가 | 공식 문서 대조 + **미검증 표기** |
| 검증 도구가 지원하지 않는 구문 (예: 일부 `GRANT`) | 공식 문서 대조 + **도구 한계 명시** |
| **`98_` 의 `DROP` / `TERMINATE` 문** | ❌ 실행하지 않는다. 대상 객체가 없으면 컴파일도 불가하므로 **공식 문서 대조**로 검증하고 미검증 표기 |

> `98_` 정리 문서는 원리상 사전 검증이 가장 어렵다. 그래서 정리 요구사항에서
> "삭제 워크플로를 공식 문서로 확인"을 요구한다. 실습을 실제로 수행한 뒤에만
> 정리 절차를 실행 검증할 수 있으므로, 그 사실을 문서에 밝힌다.

#### 컴파일 검증의 함정

- 참조하는 객체가 없으면 컴파일 단계에서 실패한다. 이는 **문법 오류가 아니다.**
  이 경우 "미검증"으로 분류하고 공식 문서로 문법을 대조한다.
- 일부 DDL/DCL은 컴파일 전용 검사가 지원되지 않는다. 도구 한계이지 문법 오류가 아니다.
  오류 메시지를 그대로 문법 문제로 해석하지 않는다.

---

### 3.3 🟢 실행 승인 — 비용 발생을 사전 허가한다

> **사용자 승인 완료 (2026-09-16).** 교육자료를 실제로 수행해 검증할 때 발생하는
> **컴퓨트·서버리스·토큰·스토리지 비용은 사전 허가되었다.** 비용을 이유로
> 실행 검증을 건너뛰지 않는다.

따라서 앞 "실행 vs 컴파일 판단" 절 표의 "부작용 있음(비용 발생)" 항목은 아래와 같이 읽는다.

| 구문 성격 | 방법 |
|-----------|------|
| 비용만 발생하는 구문 (Warehouse, Task, LLM 호출, 인덱싱, 스토리지) | ✅ **실제 실행** — 별도 승인 불필요 |
| 되돌릴 수 없거나 계정 정체성·자격증명에 영향 | ⚠️ **아래 예외 목록 참고** — 여전히 확인받는다 |

**실행 후에는 반드시 `98_` 정리를 수행하고 사전 스냅샷과 대조한다.**
비용 허가는 잔여물을 남길 허가가 아니다. 실행했다면 왕복 검증까지 완결한다.

#### 🔴 비용 허가로 대체되지 않는 것 — 여전히 사전 확인이 필요하다

**"비용이 괜찮다"는 "무엇이든 해도 된다"가 아니다.** 아래는 성격이 다른 위험이므로
비용 허가와 별개로 사용자에게 알리고 확인받는다.

| 유형 | 예시 | 왜 다른가 |
|------|------|-----------|
| **로그인 경로 변경** | `SSO_LOGIN_ONLY = TRUE`, `ALTER ACCOUNT SET SAML_IDENTITY_PROVIDER`, MFA·네트워크 정책 강제 | 계정에서 잠길 수 있다. 비용 문제가 아니다 |
| **자격증명 발급** | `SYSTEM$GENERATE_SCIM_ACCESS_TOKEN`, PAT, Key-Pair, `CREATE SECRET` | 실제로 쓰이는 크리덴셜이 생긴다 |
| **기존 사용자·역할 변경** | 실습이 만들지 않은 `USER`/`ROLE` 에 대한 `ALTER`/`DROP`/`REVOKE` | 사용자 자산이다 |
| **계정 파라미터 변경** | `ALTER ACCOUNT SET …` | 계정 전체에 영향. 대장 (b) + 3단계 원복 대상 |
| **외부 시스템 변경** | 소스 DB 설정, 방화벽, IAM, 웹훅 | Snowflake 정리로 되돌아가지 않는다 |
| **되돌릴 수 없는 데이터 손실** | 실습이 만들지 않은 객체에 대한 `DROP`/`TRUNCATE`/`OR REPLACE` | 복구 불가 |

#### 자격증명을 발급했을 때

- **값을 대화·문서·인덱스에 출력하지 않는다.** 필요하면 `LENGTH()` 등 메타데이터만 반환한다
- 발급 사실과 **무엇으로 무효화되는지**를 그 자리에 적는다
- `98_` 에서 무효화(상위 객체 `DROP` 등)를 확인한다
- 교육자료가 "토큰을 `SELECT` 해서 복사하라"고 안내한다면, **쿼리 이력에 남는다는 경고**를
  함께 넣도록 개선 대상으로 지적한다

---

### 3.4 미검증 항목 표기 의무

검증하지 못한 것을 검증된 것처럼 쓰지 않는다. **두 곳에** 표기한다.

**(1) 해당 문서 상단 주석**
```
-- 검증 상태 :
--   ✅ <구문> — 컴파일 검증 완료
--   ✅ <구문> — 실제 실행 검증 완료
--   ⚠️ <구문> — <이유>로 미검증. 문법은 공식 문서로 대조 확인
```

`.md` 문서에서는 해당 위치에 다음 형식으로 표기한다.
```
> ⚠️ 이 단계는 <이유>로 현재 계정에서 검증되지 않았습니다.
```

**(2) `01_` 문서의 검토 이력** — 미검증 항목과 이유를 표로 정리

| 항목 | 미검증 이유 |
|------|-------------|
| `CREATE X` 실제 실행 | 프로비저닝 시간 + 크레딧 발생. 사용자 승인 없이 실행하지 않음 |
| `Y` 컴파일 검증 | 검증 도구가 해당 구문의 컴파일 전용 검사를 지원하지 않음(도구 한계) |

#### 🔴 총괄 합격 선언 금지

**검증은 항목 단위로만 주장한다.** 문서 전체·자료 전체가 검증되었다는 선언은
항목별 표기 의무를 실질적으로 무력화한다. 독자는 총괄 선언을 먼저 읽고
개별 ⚠️ 표기를 신뢰하지 않게 된다.

| 금지 | 대체 |
|------|------|
| 제목에 `(검증 완료)`, `(최종)`, `(운영 배포 가능)` | 제목에 검증 상태를 넣지 않는다 |
| "실제 환경에서 문법 검증이 완료되었습니다" | "아래 표의 ✅ 항목은 <방법>으로 확인했고, ⚠️ 항목은 미검증입니다" |
| "모든 스크립트가 상호 호환되며 정상 동작함을 검증" | 실행한 구문만 나열한다 |
| "즉시 실무 운영 환경에 배포 가능" | 배포 판단은 서술하지 않는다 |

> 총괄 선언을 쓰고 싶어지는 시점이 바로 **검증 범위를 과장하고 있는 시점**이다.
> 무엇을 어떤 방법으로 확인했는지만 쓰면 총괄 선언은 필요하지 않다.

## 4. 정리(Teardown) 요구사항 — 실습 전후 상태 동일성

> **이 장이 정하는 것** — 실습이 만든 것을 빠짐없이 되돌리는 방법.
> 객체 대장(정리의 계약서) · 사전 스냅샷 · `98_` 9개 필수 구성 · 재실행 안전성.

> **원칙: 실습은 계정에 흔적을 남기지 않는다.**
> 실습 전 상태와 정리 후 상태가 동일해야 한다. 이를 **왕복 가능성(round-trip)** 이라 부른다.
> 정리 절차는 부가 기능이 아니라 **산출물의 필수 구성 요소**다.

---

### 4.1 객체 대장(Object Registry) — `01_` 문서에 필수 포함

실습에서 **생성하는 모든 것**을 표로 명시한다.
여기에 없는 객체를 만들면 안 되고, 여기 있는 모든 객체는 `98_` 에서 삭제되어야 한다.
**이 표가 정리 절차의 계약서다.**

| 종류 | 이름 | 스코프 | 생성 문서 | 정리 방법 | 비용 발생 |
|------|------|--------|-----------|-----------|-----------|
| Role | `LAB_ADMIN_RL` | 계정 | `02_` | `DROP ROLE` | 없음 |
| Database | `LAB_DB` | 계정 | `02_` | `DROP DATABASE` | 스토리지 |
| Warehouse | `LAB_WH` | 계정 | `02_` | `DROP WAREHOUSE` | **컴퓨트** |
| Integration | `LAB_EAI` | 계정 | `04_` | `DROP INTEGRATION` | 없음 |
| Secret | `LAB_DB.SCH.LAB_SECRET` | 스키마 | `04_` | `DROP SECRET` | 없음 |
| (외부) | 복제 슬롯 `lab_slot` | 소스 DB | `03_` | `pg_drop_replication_slot()` | **소스 디스크** |

#### 스코프 열이 중요한 이유

**계정 레벨 객체**(Role, Database, Warehouse, Integration, Compute Pool, Share,
Network Policy, Openflow Deployment 등)는 삭제를 놓치면 계정에 영구히 남는다.
**스키마 레벨 객체**는 상위 DB를 지우면 함께 사라지므로 위험이 낮다.

#### 외부 리소스도 대장에 포함한다

Snowflake 밖에서 만든 것(복제 슬롯, 웹훅, IAM 역할, 방화벽 규칙, 소스 DB 설정 변경)도
같은 표에 넣는다. 누락되면 사용자 환경에 문제가 남는다.

#### 대장은 세 부분으로 나눈다

대장을 하나의 표로 만들면 성격이 다른 항목이 섞여 정리가 누락된다.
다음 세 부분으로 나눠 작성한다.

| 부분 | 대상 | 정리 동작 |
|------|------|-----------|
| **(a) 신규 생성 Snowflake 객체** | 실습이 만든 것 | `DROP` |
| **(b) 기존 객체의 속성 변경** | 실습이 **바꾼** 것 | **원복** (아래 "속성 변경(Mutation)" 절) |
| **(c) 외부 리소스** | Snowflake 밖 | 삭제 또는 설정 원복 |

---

#### 🔴 간접 생성 객체 — `grep` 으로는 절대 찾을 수 없다

**대장 누락의 가장 위험한 유형이다.** 지금까지의 객체 추출은 문서에 적힌
`CREATE` 구문을 찾는 방식이다. 그런데 **프로시저·태스크·UDF 가 실행 중에 만드는
객체**는 문서에 `CREATE` 구문으로 존재하지 않는다. 동적 SQL 문자열 안에 있거나
런타임에 조립되므로 정적 검색으로 보이지 않는다.

| 유형 | 예시 | 왜 위험한가 |
|------|------|-------------|
| 프로시저가 만드는 사용자 | `EXECUTE IMMEDIATE 'CREATE USER ' \|\| :v_id` | **계정 레벨**이라 `DROP DATABASE` 로 사라지지 않는다 |
| 프로시저가 만드는 Role·Grant | 동적 `GRANT ROLE` | 권한이 계정에 잔존한다 |
| 태스크가 적재하는 대상 테이블 | 파이프라인이 자동 생성하는 대상 | 상위 DB 안이면 위험은 낮다 |
| 외부 시스템이 역방향 생성 | SCIM 프로비저닝이 만드는 사용자 | Snowflake 밖 트리거로 생성된다 |

> 실측 사례: 인사 동기화 프로시저가 사번당 `CREATE USER` 를 발행해 계정에
> 사용자 5명을 만들었다. 문서의 `CREATE` 구문에는 없으므로 대장에서 빠졌고,
> `DROP DATABASE` 로도 사라지지 않아 **계정 레벨 잔여물**이 되었다.

**필수 조치.**

1. 대장 (a) 에 **`(간접)` 표시와 "생성 문서" 대신 "누가 만드는가"** 를 적는다
   ```
   | **User (간접)** | `EMP_F***` | 계정 | `06_` 프로시저가 실행 중 생성 | `DROP USER` |
   ```
2. **이름이 가변적이면 패턴으로 등재**하고, `98_` 에 **패턴 검색 + 개별 삭제** 절차를 둔다
   ```sql
   -- 프로시저가 만든 사용자를 먼저 찾는다 (입력 데이터에 따라 개수가 다르다)
   SHOW USERS LIKE 'EMP_F%';
   --   남은 사용자: ______  (없어야 합니다)
   ```
3. 알려진 이름은 개별 `DROP` 을 넣고, **"입력을 바꿨다면 더 있을 수 있다"** 를 경고한다

**찾는 방법.** 정적 검색으로는 안 되므로 아래를 병행한다.

```bash
# 동적 SQL 조립 지점을 찾는다 — 여기서 만들어지는 객체를 사람이 읽어 판단한다
grep -rnE "EXECUTE IMMEDIATE|IDENTIFIER\(|\|\| *'" "$F"
```

그리고 **실습을 완주한 뒤 계정을 접두사로 훑는다.** 이것이 가장 확실하다
(품질 기준의 "완주 검증" 절).

---

#### 속성 변경(Mutation) — 삭제가 아니라 **원복** 대상

> **가장 놓치기 쉬운 결함이다.** 사전 스냅샷 절의 "기존 객체를 재사용하지 않는다" 원칙에도
> 불가피한 예외가 생긴다. 제품이 요구하는 계정·사용자·파라미터 설정 변경은
> 새 객체를 만들 수 없으므로 **기존 객체를 바꿔야만** 한다.
> 이런 항목은 `DROP` 으로 되돌아가지 않으므로 별도로 관리한다.

전형적인 예:

| 유형 | 예시 | 왜 불가피한가 |
|------|------|---------------|
| 사용자 속성 | `ALTER USER … SET DEFAULT_SECONDARY_ROLES`, `SET DEFAULT_ROLE` | 제품이 특정 Role 평가 방식을 요구 |
| 계정 파라미터 | `ALTER ACCOUNT SET …` | 기능 활성화에 필요 |
| 기존 객체 연결 | `ALTER <상위객체> SET EVENT_TABLE / EXTERNAL_ACCESS_INTEGRATIONS` | 상위 객체가 실습 대상이면 원복 필요 |
| 외부 시스템 설정 | `wal_level`, `binlog_format`, 방화벽 규칙 | 소스 시스템 재설정 |

**필수 3단계.** 하나라도 빠지면 왕복 가능성이 깨진다.

1. **`02_` 사전 스냅샷에서 실습 전 값을 기록한다** — 기록 서식을 함께 제공한다.
   무엇으로 되돌릴지 모르면 원복이 불가능하다.
   ```sql
   -- 🔴 실습 전 값 기록 — 이 값 없이는 원복할 수 없습니다
   DESCRIBE USER IDENTIFIER($my_user);
   -- 실습 전 DEFAULT_SECONDARY_ROLES = ______________
   ```
2. **변경 지점에 🔴 경고를 붙인다** — "이것은 신규 생성이 아니라 기존 객체 변경이며
   `DROP` 으로 되돌아가지 않는다"는 사실을 그 자리에서 알린다.
3. **`98_` 에 원복 절을 둔다** — 실습 전 값에 따라 **분기**한다.
   원복 구문은 `UNSET`(기본값 복귀)과 `SET <원래 값>`이 다르므로 공식 문서로 확인한다.

```sql
-- 경우 1) 실습 전에도 이미 그 값이었다 → 할 일 없음
-- 경우 2) 실습 전이 미설정/NULL 이었다  → ALTER USER … UNSET <속성>;
-- 경우 3) 실습 전이 명시적 다른 값이었다 → ALTER USER … SET <속성> = <원래 값>;
```

> 💡 **제품 기본값이 이미 그 값이면 변경 자체가 불필요하다.** 변경 구문을 넣기 전에
> 해당 속성의 현재 기본값을 확인하고, 기본값과 같다면 "건너뛰어도 된다"고 명시한다.
> 불필요한 변경을 만들지 않는 것이 원복보다 낫다.

---

### 4.2 명명 규칙 — 식별 가능하게 만든다

정리 누락을 막는 가장 효과적인 수단은 **일관된 접두사**다.

- 모든 신규 객체에 공통 접두사를 붙인다: `LAB_`, `<TOPIC>_EDU_` 등
- 모든 객체의 `COMMENT` 에 공통 태그를 넣는다: `[<TOPIC_SLUG>]`
- 이렇게 하면 정리 시 `SHOW ... LIKE '<PREFIX>%'` 로 잔여물을 한 번에 찾을 수 있다

```sql
CREATE DATABASE LAB_DB COMMENT = '실습용. [openflow-cdc]';
```

---

### 4.3 사전 스냅샷 — `02_` 문서 시작부에 필수

실습 **전** 상태를 기록해 둔다. 정리 후 이것과 대조해 원상복구를 증명한다.
기록 자체가 계정을 변경하지 않도록 **조회 전용**으로 구성한다.

```sql
-- 실습 전 상태 스냅샷 (결과를 별도로 저장하거나 캡처해 둘 것)
SHOW DATABASES;
SHOW WAREHOUSES;
SHOW ROLES;
SHOW INTEGRATIONS;
SHOW COMPUTE POOLS;
-- 주제에 따라 추가: SHOW TASKS / STREAMS / PIPES / SECRETS / NETWORK RULES ...
```

접두사 방식을 쓴다면 더 간단하게 **충돌 검사**로 대체할 수 있다.

```sql
-- 접두사가 이미 쓰이고 있지 않은지 확인 (기존 객체를 덮어쓰지 않기 위해)
SHOW DATABASES  LIKE 'LAB_%';
SHOW WAREHOUSES LIKE 'LAB_%';
SHOW ROLES      LIKE 'LAB_%';
-- 결과가 있으면 접두사를 바꾸거나 사용자에게 확인한다
```

> ⚠️ **기존 객체를 재사용하지 않는다.** 사용자가 명시적으로 지정한 경우를 제외하고,
> 실습은 항상 새 객체를 만든다. 기존 객체를 건드리면 정리로 되돌릴 수 없다.

#### 🔴 스냅샷 결과값을 문서에 전사하지 않는다

가장 흔한 실수는 스냅샷을 한 번 실행하고 **그 결과를 문서 표에 옮겨 적는 것**이다.
전사한 값은 즉시 낡는다. 실습자의 계정은 작성자의 계정이 아니다.

| 전사가 만드는 결함 | 예시 |
|-------------------|------|
| 값이 틀린다 | `AUTO_SUSPEND = 600초` 로 적었지만 실제 계정은 `300초` |
| 목록이 빠진다 | 웨어하우스 3개 중 1개만 적어 대조 기준이 무의미해진다 |
| 대조가 불가능해진다 | 실습자의 실제 상태와 문서의 값이 달라 차이의 원인을 알 수 없다 |

따라서 스냅샷 절(또는 `95_실습전_기준선.md`)은 다음 두 가지만 담는다.

1. **실행할 쿼리**
2. **빈 기록 서식** — 값은 실습자가 채운다

```sql
-- 실습 전 상태 스냅샷 — 결과를 아래 서식에 직접 기록하세요
SHOW WAREHOUSES;
--   실습 전 웨어하우스 목록: ______________________________
--   COMPUTE_WH AUTO_SUSPEND = ______ 초
```

> 작성자가 확인한 값을 남기고 싶다면 **"작성 시점의 참고값(계정마다 다름)"** 으로
> 명시하고, 대조 기준으로 쓰지 않는다.

### 4.5 `98_리소스정리.sql` 필수 구성 — 9개 요소

#### (1) 비용 경고 — 문서 최상단
지속적으로 비용이 발생하는 객체를 먼저 명시한다.
사용자가 문서를 다 읽지 않아도 가장 급한 것을 알 수 있어야 한다.

#### (2) 일시 중단 vs 완전 삭제 선택지
실습을 이어서 할 수 있으므로 두 경로를 제공한다.

- **일시 중단**: `SUSPEND`, `AUTO_SUSPEND`, 태스크 `SUSPEND` 등 — 삭제 없이 비용만 멈춤
- **완전 삭제**: 전체 teardown

일시 중단으로도 남는 부작용이 있으면 반드시 경고한다.
예: 소스 DB의 복제 슬롯이 살아 있어 WAL 이 계속 축적된다.

#### (3) 역순 삭제 순서 — 의존 관계 명시
생성 순서의 역순으로 삭제한다. 순서를 지키지 않으면 실패하는 지점을 표시한다.

```
① 실행 중인 것 정지 (커넥터/태스크/서비스)
② 자식 객체 삭제
③ 부모 객체 삭제
④ 계정 레벨 객체 삭제 (Integration, Compute Pool 등)
⑤ Database / Warehouse 삭제
⑥ Role 삭제 (가장 마지막 — 앞 단계 실행 권한이 필요하므로)
⑦ 외부 시스템 정리
```

#### (4) 상태 전이가 필요한 객체의 정확한 절차
`DROP` 만으로 삭제되지 않는 객체가 있다.
각 객체의 실제 삭제 워크플로를 **공식 문서로 확인**해 기술한다. **추측하지 않는다.**

예시:
- Openflow Runtime: `SUSPEND` → `TERMINATE` → `DROP`
- Openflow Connector: `STOP` → `TERMINATE` → `DROP`
- 일부 객체는 상위 객체의 `TERMINATE CASCADE` 로 자식까지 처리 가능

또한 **어떤 상태에서 `ALTER`/`DROP` 이 거부되는지**도 확인해 명시한다
(전이 상태에서는 명령이 거부되는 경우가 많다).

#### (5) 삭제 전 데이터 보존 선택지
실습 결과 데이터를 남기고 싶을 수 있다.
어떤 객체를 보존해도 되는지, 보존 시 비용이 발생하는지 명시한다.

#### (6) 외부 리소스 정리 — 별도 절 또는 `.md` 문서
Snowflake 외부 작업이 있었다면 그 정리도 반드시 포함한다.
특히 **계속 누적되는 것**을 우선한다.

| 유형 | 예시 | 방치 시 결과 |
|------|------|-------------|
| 누적형 | PostgreSQL 복제 슬롯 | WAL 축적 → 소스 디스크 고갈 |
| 누적형 | 로그·이벤트 스트림 | 스토리지 증가 |
| 권한형 | 외부 IAM 역할, 방화벽 규칙 | 불필요한 접근 경로 잔존 |
| 설정 변경 | `wal_level`, `binlog_format` 등 | 소스 시스템 성능·동작 변화 |
| 계정형 | 웹훅, 서비스 계정 | 미사용 자격증명 잔존 |

설정 변경은 **원복 방법과 재시작 필요 여부**를 함께 기술한다.

#### (7) 정리 완료 검증 쿼리
"삭제했다"가 아니라 **"없음을 확인했다"** 로 끝나야 한다.

```sql
SHOW DATABASES  LIKE 'LAB_%';   -- 결과 없음
SHOW WAREHOUSES LIKE 'LAB_%';   -- 결과 없음
SHOW ROLES      LIKE 'LAB_%';   -- 결과 없음
SHOW INTEGRATIONS;              -- 실습 객체 없음
```

앞의 "사전 스냅샷"과 대조해 **차이가 없음**을 확인하는 절차로 마무리한다.
외부 리소스 검증 쿼리도 함께 제공한다.
"속성 변경(Mutation)" 절의 항목이 있다면 **원복 확인 쿼리**도 넣는다
(예: `DESCRIBE USER` 로 실습 전 값과 같아졌는지 확인).

**검증 쿼리 자체를 반드시 실행해 본다.**
정리 검증 쿼리는 **실습 없이도 지금 실행할 수 있는 유일한 부분**이다.
잔여물이 없는 상태에서 0행이 나오는 것이 정상이므로, 실습 리소스가 없어도
쿼리의 정당성을 확인할 수 있다. **반드시 실행한다.**

> ⚠️ **`ACCOUNT_USAGE` / `INFORMATION_SCHEMA` 뷰의 존재를 가정하지 않는다.**
> 계정 에디션과 버전에 따라 일부 뷰가 없다. 실제로
> `SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSES` 가 없는 계정이 있다.
> 뷰가 없으면 `SHOW <객체>` + `TABLE(RESULT_SCAN(LAST_QUERY_ID()))` 로 대체한다.
> `RESULT_SCAN` 은 컬럼명을 큰따옴표로 인용해야 한다.
>
> ```sql
> SHOW WAREHOUSES;
> SELECT "name", "comment"
> FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))
> WHERE "comment" ILIKE '%[<TOPIC_SLUG>]%';
> ```
>
> 또한 `ACCOUNT_USAGE` 뷰는 **최대 2~3시간 지연**되므로 정리 직후 확인에는
> 부적합하다. 즉시 확인은 `SHOW` 로, 태그 기반 광역 검색은 `ACCOUNT_USAGE` 로
> 나누고 그 차이를 주석에 명시한다.

#### (8) 정리 체크리스트
비용 발생 객체 항목을 **굵게** 표시한다.

#### 🔴 (9) 재실행 안전성 — 정리 문서는 두 번 실행된다

**정리 문서가 한 번만 실행된다고 가정하지 않는다.** 실제 사용 양상은 다음과 같다.

- 중간에 한 구문이 실패해 **처음부터 다시 실행**한다
- 일부만 정리하고 며칠 뒤 **나머지를 정리**한다
- 이미 정리된 계정에서 **확인 삼아 다시 실행**한다

##### `IF EXISTS` 는 상위 컨테이너 부재를 막아주지 않는다

가장 흔한 함정이다. `IF EXISTS` 는 **그 객체 자체**의 부재만 처리한다.
정규화된 이름의 **상위 컨테이너**(데이터베이스·스키마)가 없으면
객체 존재 여부를 보기 전에 **이름 해석 단계에서 실패**한다.

```sql
-- KSM_DB 가 이미 삭제된 상태에서 실행하면 IF EXISTS 에도 불구하고 실패한다
ALTER TASK IF EXISTS KSM_DB.OPS.MY_TASK SUSPEND;
--   Database 'KSM_DB' does not exist or not authorized.
```

> 실측 사례: `DROP DATABASE` 뒤에 오는 태스크 `SUSPEND`/`DROP` 구문이 2회차
> 실행에서 첫 줄부터 실패했다. 1회차 실행에서는 전혀 드러나지 않았다.

**따라서 정리 순서상 `DROP DATABASE`(또는 `DROP SCHEMA`) 보다 앞에 있는 모든
스키마 레벨 구문은 재실행 시 실패한다.** 그 구문들을 방어한다.

```sql
-- 상위 DB 존재를 먼저 확인하는 방어 블록
EXECUTE IMMEDIATE $$
DECLARE
    v_db_count INTEGER;
    rs RESULTSET;
BEGIN
    -- ACCOUNT_USAGE / INFORMATION_SCHEMA 뷰 존재를 가정하지 않고 SHOW 로 확인한다
    rs := (SHOW DATABASES LIKE '<DB>');
    SELECT COUNT(*) INTO v_db_count FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()));

    IF (v_db_count = 0) THEN
        RETURN '<DB> 가 이미 없습니다. 이 절을 건너뜁니다.';
    END IF;

    ALTER TASK IF EXISTS <DB>.OPS.MY_TASK SUSPEND;
    DROP  TASK IF EXISTS <DB>.OPS.MY_TASK;
    RETURN '정리 완료';
END;
$$;
```

방어 블록을 넣기 어렵다면, 최소한 **그 지점에 "상위 DB 가 이미 없으면 이 절을
건너뛰라"는 주석**을 남긴다. 조용히 실패하게 두지 않는다.

##### 검증 방법 — 반드시 두 번 실행한다

**`98_` 을 1회 실행해 성공한 것은 재실행 안전성의 근거가 아니다.**
실습을 완주해 정리를 실행했다면, **곧바로 한 번 더 실행**해 다음을 확인한다.

| 확인 | 기대 |
|------|------|
| 2회차 실행이 오류 없이 끝나는가 | ✅ 전 구문 통과 (방어 블록은 "건너뜁니다" 반환) |
| 2회차가 무엇도 추가로 지우지 않는가 | ✅ 이미 0행이므로 변화 없음 |
| 2회차에서 새 오류가 나는가 | 🔴 나오면 그 구문이 재실행 안전하지 않다 |

이 검증은 **실습을 완주한 직후에만 가능**하다. 그 시점을 놓치면
다음 회차까지 확인할 수 없으므로, 정리 실행 직후에 바로 수행한다.

### 4.6 안전장치

- `98_` 의 `DROP` 문은 **주석 처리 상태로 제공**하고, 상단에 주석 해제가 필요함을 명시한다
- `DROP ... IF EXISTS` 를 사용해 부분 실행 후 재실행이 안전하도록 한다
- `DROP DATABASE` 등 광범위 삭제 앞에는 **대상 확인 쿼리**를 배치한다
- **계정 기본 객체를 삭제하는 구문을 절대 생성하지 않는다**
  (`COMPUTE_WH`, `SNOWFLAKE` DB, 시스템 Role, `PUBLIC` 등)
- `DROP ... CASCADE` 는 영향 범위를 주석으로 명시한 경우에만 사용한다
- 삭제 순서상 실패할 수 있는 지점에는 **실패 시 확인할 것**을 주석으로 남긴다

### 4.7 자체 검증 — 1:1 대조

`98_` 작성을 마치면 반드시 확인한다.

1. `01_` 객체 대장의 항목을 센다 — **(a) 생성 / (b) 속성 변경 / (c) 외부** 세 부분 모두
2. `98_` 의 삭제 대상과 **원복 대상**을 센다
3. **두 수가 일치하는지** 확인한다
4. 불일치하면 어느 쪽이 누락인지 판단해 수정한다
   - 대장에 없는데 SQL에서 생성됨 → **대장에 추가** (더 위험한 경우)
   - 대장에 있는데 `98_` 에 없음 → **`98_` 에 추가**

**(b) 속성 변경 행은 3중 대조가 필요하다.** 하나라도 빠지면 왕복 불가다.

| 확인 | 위치 |
|------|------|
| 실습 전 값 기록 절차가 있는가 | `02_` 사전 스냅샷 |
| 변경 지점에 🔴 경고가 있는가 | 변경을 수행하는 문서 |
| 원복 절이 있는가 | `98_` |

객체 추출은 `grep` 으로 보조한다. `CREATE` 문만 찾으면 **속성 변경을 놓친다.**
`ALTER … SET` 도 함께 검색한다.

#### 🔴 추출 범위는 `.sql` 이 아니라 **폴더 전체**다

가장 놓치기 쉬운 구멍이다. 실습자가 실행하는 구문은 `.sql` 파일에만 있지 않다.
**`.md` 설명 문서의 코드블록도 실습자는 복사해서 실행한다.** `.sql` 만 훑으면
그 구문이 만든 객체와 바꾼 속성이 대장에도, `98_` 에도 들어가지 않는다.

전형적인 사고 경로:

```
아키텍처 설명 .md 안 코드블록에 ALTER ACCOUNT SET <파라미터>
  → .sql 만 grep  →  대장 (b) 미등재
  → 98_ 에 원복 절 없음  →  실습 후 계정 파라미터가 영구히 바뀐 상태로 남는다
```

따라서 grep 은 **확장자를 제한하지 않고 폴더 전체**에 수행한다.

```bash
# .sql / .md / .py 를 모두 포함해 폴더 전체를 훑는다
grep -rnE "CREATE (OR REPLACE )?(IF NOT EXISTS )?(DATABASE|SCHEMA|WAREHOUSE|ROLE|TABLE|VIEW|STAGE|SECRET|NETWORK RULE|EXTERNAL ACCESS INTEGRATION|EVENT TABLE|TASK|STREAM|PIPE|COMPUTE POOL|FUNCTION|PROCEDURE|CORTEX SEARCH SERVICE)" <폴더>/
grep -rnE "ALTER (USER|ACCOUNT|SESSION|DATABASE|WAREHOUSE|TASK|STAGE) .*(SET|UNSET) " <폴더>/   # ← 속성 변경 탐지
grep -rn  "GRANT " <폴더>/                                                                      # ← 계정 레벨 권한 부여 탐지
```

`.md` 코드블록에서 걸린 구문은 둘 중 하나로 처리한다.

| 판정 | 조치 |
|------|------|
| 실습자가 **실행하는** 구문이다 | 대장에 등재하고 `98_` 에 정리·원복 절을 둔다. 가능하면 `.sql` 단계 문서로 옮긴다 |
| 순수 **설명용 예시**다 | 그 코드블록에 "설명용 예시 — 실행하지 않습니다" 를 명시한다 |

> 판정이 모호하면 **실행되는 것으로 간주한다.** 등재 누락이 과잉 등재보다 위험하다.

IMPROVE 모드에서는 대장을 믿지 말고 **폴더 전체에서 직접 객체를 추출해** 대조한다.

## 5. 품질 기준 (QUALITY BAR) — 두 모드 공통

> **이 장이 정하는 것** — 완성으로 볼 수 있는 최저선.
> 구조 · 내용 · 정확성(완주 검증 포함) · 정리 4개 영역과 심각도 매핑.

- **CREATE 모드**: 완료 전 자체 확인 체크리스트
- **IMPROVE 모드**: 갭 분석 기준

### 5.3 정확성 — 사실 확인

근거 판정은 `output-contract.md` 의 검증 규율을 따른다.

- 🔴 **모든 SQL이 컴파일 검증을 통과했다** (선행 객체 부재로 컴파일 불가한 것은 미검증 표기)
- 🔴 **실습을 최소 1회 완주하고 정리·대조까지 실행했다** (아래 절)
- 🔴 문법을 공식 문서로 대조했다 (**모델 기억에 의존하지 않았다**)
- 🟡 계정 적합성(Edition, Region, Trial, 기능 활성화)을 실제 SQL로 확인했다
- 🔴 **미검증 항목이 문서와 검토 이력 두 곳에 명시되었다**
- 🟡 검증 도구의 한계로 확인 못 한 것을 그렇게 밝혔다
- 🔴 객체의 삭제·상태 전이 워크플로를 추측하지 않고 공식 문서로 확인했다
- 🔴 **측정하지 않은 정량 수치를 제시하지 않았다** (아래 절)
- 🔴 **"검증 완료" 류의 총괄 합격 선언이 없다** (미검증 항목 표기 의무)
- 🔴 **제품 기능의 성격과 적용 범위를 공식 문서로 확인했다** (아래 절)

#### 🔴 측정하지 않은 정량 수치 금지

성능·비용·효과 수치는 그럴듯할수록 위험하다. 독자는 이것을 실측치로 받아들이고
의사결정 근거로 쓴다. **측정 절차 없이 숫자를 쓰지 않는다.**

금지 대상 — 측정 절차가 없다면 하나도 쓰지 않는다.

| 범주 | 예시 표현 |
|------|-----------|
| 레이턴시 | `0.38초`, `P95 1.42초`, `밀리초 단위 처리` |
| 처리량 | `100+ QPS 지원`, `10,000건 0.45초` |
| 절감·개선률 | `운영 공수 85% 절감`, `탐색 시간 90% 단축`, `토큰 75% 절감` |
| 정확도·성공률 | `방어율 100%`, `차단 정확도 100%`, `유출 위험 0%` |
| 비용·ROI | `유휴 비용 0 크레딧`, `TCO N% 개선` |
| 토큰 수 | 단위까지 특정한 `prompt_tokens 105` 표 |

수치를 제시하려면 **세 가지를 함께 둔다.**

1. **측정 쿼리 또는 명령** — 독자가 재현할 수 있어야 한다
2. **표본 수와 측정 조건** — 웨어하우스 크기, 문서 건수, 반복 횟수
3. **측정 시점** — 값은 시간이 지나면 달라진다

그럴 수 없다면 선택지는 둘이다.

| 선택 | 표기 |
|------|------|
| 수치를 **삭제**한다 | 정성 서술로 대체 — "유휴 시 컴퓨트 비용이 발생하지 않는다" |
| 예시임을 **명시**한다 | `예시값(미측정) — 실제 값은 계정·데이터에 따라 다릅니다` |

> ⚠️ **표본 3건으로 `100%` 를 주장하지 않는다.** 관찰 결과는 관찰 결과로 쓴다 —
> "테스트한 3개 시나리오에서 모두 차단되었다".

#### 자주 나오는 정확성 결함 유형

| 유형 | 예시 | 어떻게 잡는가 |
|------|------|---------------|
| 파라미터명 오류 | 실제와 다른 옵션·컬럼 이름 사용 | 컴파일 검증 |
| 필수 권한 누락 | 동작에 필요한 권한을 빠뜨려 런타임에 실패 | 공식 문서 대조 |
| 삭제 워크플로 단순화 | 다단계 절차를 `DROP` 하나로 기술 | 공식 문서 대조 |
| 변경 가능성 오기 | 변경 불가한 속성을 변경 가능하다고, 또는 그 반대로 서술 | 공식 문서 대조 |
| 검증 범위 과장 | 검증 명령이 실제로 확인하지 못하는 것까지 확인한다고 서술 | 자체 점검 |
| **기능 혼동** | 이름이 유사한 두 제품 기능을 동일시하거나, 적용 대상을 확대 해석 | 공식 문서 대조 (아래) |
| **미측정 수치** | 성능·절감률·방어율을 측정 없이 제시 | 위 절 |
| **구·신 함수 혼용** | 신규 함수 이름에 구버전 시그니처를 적용 | 컴파일 검증 (아래) |

#### 🔴 기능 혼동 — 이름이 비슷하면 반드시 문서로 확인한다

Snowflake는 유사한 이름의 기능을 여러 계층에 둔다. **이름이 비슷하다는 이유로
같은 기능이라고 서술하면 아키텍처 설명 전체가 틀린다.** 실습은 동작하는데
설명이 거짓인 상태가 되므로 컴파일·실행 검증으로는 잡히지 않는다.

각 기능에 대해 세 가지를 문서로 확인한다.

| 확인 항목 | 왜 |
|-----------|-----|
| **무엇을 검사·처리하는가** | 입력인가 출력인가. 차단인가 필터인가 |
| **어느 호출 경로에 적용되는가** | SQL 함수 / 특정 클라이언트 / 특정 제품에만 적용될 수 있다 |
| **활성화 방법과 전제 조건** | 함수 인자 / 계정 파라미터 / Edition·Region 요건 |

> 💡 이름이 비슷한 두 기능을 하나의 "다층 방어" 그림으로 합치기 전에, **각 레이어가
> 실제로 그 위치에서 동작하는지** 문서로 확인한다. 다이어그램은 검증 대상이다.

#### 🔴 구·신 함수 혼용 — 시그니처는 이름과 함께 바뀐다

Snowflake는 함수를 새 이름으로 재출시하면서 **인자 형태를 함께 바꾸는** 경우가 많다.
모델 기억은 구버전 시그니처를 신버전 이름에 그대로 붙이는 실수를 반복한다.

- 구·신이 공존하는 함수는 **신규 이름으로 문서를 다시 확인한다**
- 인자 개수·타입·반환 타입을 모두 확인한다 (반환이 문자열인지 OBJECT인지)
- **반드시 컴파일 검증한다.** 이 유형은 컴파일에서 즉시 잡힌다

### 5.4 완주와 검증 태도

> 이 절은 **어떻게 검증하는가**를 정한다. 앞 "정확성 — 사실 확인" 절과 별개로,
> 무엇을 근거로 "확인했다"고 말할 수 있는지의 문제다.

#### 🔴 완주 검증 — 컴파일은 완주를 대신하지 못한다

> **"컴파일을 통과했다"는 "실습이 된다"가 아니다.** 이 두 항목을 `또는` 으로 묶으면
> 컴파일만으로 정확성 기준이 충족되어, **한 번도 돌려보지 않은 자료를 완료로 보고**할 수 있다.
> 그래서 분리한다.

컴파일 검증이 원리상 잡지 못하는 것들이 있다.

| 유형 | 실제 사례 |
|------|-----------|
| **DDL 절 순서 오류** | `CREATE PROCEDURE ... EXECUTE AS OWNER` 뒤에 `COMMENT` → 생성 자체가 실패. 개별 구문을 컴파일해도 드러나지만, 문서를 읽기만 하면 놓친다 |
| **런타임 타입 오류** | `TO_JSON(<VARCHAR>)` → 실행 시점에 실패. 프로시저 본문은 생성 시 컴파일되지 않는다 |
| **프로시저 본문 전체** | 본문은 `CREATE` 시 검증되지 않는다. 커서 필드를 SQL 문에 직접 참조하는 오류 등이 호출 시점에야 드러난다 |
| **조용한 실패** | `EXCEPTION WHEN OTHER THEN RETURN '...'` 가 오류를 삼켜 **정상 반환처럼 보인다.** 결과 테이블이 0행인 것으로만 알 수 있다 |
| **상태·순서에 의존하는 동작** | 스트림 오프셋 전진, Task `WHEN` 조건 평가, 인덱스 동기화, 소유권에 따른 권한 |
| **세션 상태 파괴** | 정리 중 사용 중인 웨어하우스를 `DROP` → 후속 문장이 실패 |
| **정리 절차 전체** | `98_` 의 `DROP` 은 대상이 없으면 컴파일조차 불가하다. 실습을 수행한 뒤에만 검증된다 |

**완주의 정의.** 아래를 모두 실행해야 "완주"다.

1. `02_` 부터 마지막 단계 문서까지 **순서대로 실행**한다
2. 학습 목표의 **데이터 적재·동작 결과를 쿼리로 확인**한다 (생성 성공만으로는 부족하다)
3. `98_` 정리를 **실행**한다
4. 사전 스냅샷과 **대조**해 잔여물 0을 확인한다 (속성 변경 원복 포함)

**완주하지 못했다면** 그 사실과 이유를 `01_` 검토 이력과 각 문서 상단에 쓴다.
비용은 사전 허가되었으므로(검증 규율의 "실행 승인" 절) **비용은 완주하지 못한 이유가 될 수 없다.**
정당한 이유는 다음과 같은 것들이다.

- 외부 시스템·테넌트·자격증명이 필요하다 (Entra ID, 소스 DB, IdP 인증서)
- UI 조작이 필요하다 (드래그앤드롭 업로드)
- 시간 경과가 필요하다 (CRON 자연 발동, `TARGET_LAG` 증분 갱신)
- 사용자가 확인을 보류한 위험 구문이다 (로그인 경로 변경 등)

> 💡 완주에 실습 데이터가 필요하면 **직접 만든다.** 파일이 없다고 건너뛰지 않는다.
> 예: PDF 가 필요하면 생성해 스테이지에 올린 뒤(`COPY FILES` 등) 파싱까지 확인한다.
> 이때 만든 검증용 자산은 완주 후 삭제한다.

#### 🔴 "성공 응답" 은 검증 근거가 아니다 — 결과 상태를 단정한다

구문이 오류 없이 끝난 것과 **의도한 상태가 된 것**은 다르다.
아래는 모두 "성공" 으로 보이면서 실제로는 아무 일도 하지 않은 사례다.

| 겉보기 | 실제 |
|--------|------|
| `CALL` 이 `... 완료: 총 4건 처리됨` 반환 | `EXCEPTION` 핸들러가 오류를 삼켰다. 대상 테이블은 **0행** |
| 태스크 이력 `STATE = SUCCEEDED` | 프로시저 내부에서 실패했으나 핸들러가 정상 반환했다 |
| `CALL` 이 매번 같은 건수를 반환 | 스트림 오프셋이 전진하지 않아 **같은 건을 재처리**하고 있었다 |
| `CREATE USER IF NOT EXISTS` 성공 | 기존 계정이라 **아무 것도 갱신되지 않았다** (부서이동 미반영) |
| `ALTER ... SET` 성공 | 설정은 됐으나 `DESCRIBE` 출력에 그 속성이 없어 **확인 자체가 불가능**했다 |

**규칙.**

1. **반환 메시지·`STATE` 를 근거로 쓰지 않는다.** 결과를 **별도 쿼리로 단정**한다
   ```sql
   CALL MY_PROC();                       -- ← 이것은 근거가 아니다
   SELECT COUNT(*) FROM TARGET_TABLE;    -- ← 이것이 근거다
   SHOW USERS LIKE 'EMP_%';              -- ← disabled 값까지 확인한다
   ```
2. **`EXCEPTION WHEN OTHER THEN RETURN ...` 패턴을 결함으로 지적한다.**
   교육자료가 이 패턴을 쓴다면, 최소한 **실패를 감사 로그·알림으로 남기는지**
   확인하고, 남기지 않으면 조용한 실패 위험을 그 자리에 경고한다
3. **멱등성 주장에는 2회 호출 결과를 붙인다.** 1회 성공은 재실행 안전성의 근거가 아니다
   (정리 요구사항의 "재실행 안전성" 절과 같은 원칙이다)
4. **검증 표에 "관측" 열을 둔다.** "성공" 이 아니라 **무엇을 보았는지**를 적는다

> 이 원칙을 지키지 않으면 검증 상태 주석이 거짓이 된다. 실측 사례에서
> 결함 3건이 모두 "성공 응답" 을 반환하고 있었고, 자료는 그것을 근거로
> "엔드투엔드 검증 완료" 를 선언하고 있었다.

#### 🔴 도달 한계(Hard Blocker)를 실행으로 확정한다

계정 에디션·트라이얼 여부·리전·기능 활성화 상태에 따라 **어떤 실습은 끝까지 갈 수
없다.** 그 사실 자체는 결함이 아니다. **결함은 차단 지점을 추정으로 적는 것이다.**

| 흔한 오류 | 결과 |
|-----------|------|
| 문서로 읽은 제약을 게이트로 삼는다 | 실제로는 통과하는 지점에서 학습자를 멈춘다 |
| 가장 앞선 제약만 경고한다 | **진짜 벽은 뒤에 있는데 예고되지 않는다** |
| "될 것이다" 로 서술한다 | 학습자가 중간까지 진행한 뒤 막힌다 |

> 실측 사례: 자료는 "트라이얼 계정에서 `CREATE OPENFLOW DEPLOYMENT` 가 실패할 수
> 있다" 를 사전 게이트로 두었다. 실제로 실행해 보니 **성공**했고, 진짜 차단 지점은
> 세 문서 뒤의 `CREATE EXTERNAL ACCESS INTEGRATION`
> (`External access is not supported for trial accounts`) 이었다.
> 학습자를 틀린 곳에서 멈추게 하고, 정작 넘을 수 없는 벽은 예고하지 않았다.

**필수 절차.**

1. **가장 이른 하드 블로커를 실행으로 찾는다.** 순서대로 실행하다 처음 막히는 지점이
   그것이다. 문서로 추정하지 않는다
2. 막힌 **오류 원문을 그대로 인용**하고 공식 문서로 원인을 대조한다
3. `01_` 의 사전 준비물과 해당 단계 문서 **양쪽에** 그 지점을 명시한다
4. **해소 방법**을 적는다 (에디션 전환, 담당자 승인, 외부 리소스 준비 등)
5. 카탈로그의 실행 검증 열에 **"부분 완주 (도달 한계 확인)"** 으로 기록한다

**도달 한계까지 간 것은 완주 실패가 아니다.** 어디까지 되고 어디서 왜 막히는지를
실측으로 확정한 것이 산출물이다. 다만 그것을 **"완주" 라고 부르지 않는다.**

### 5.5 정리 / 왕복 가능성

세부 기준은 `teardown.md` 참고.

- 🔴 `01_` 에 **객체 대장**이 있고 스코프·정리 방법·비용 발생 여부가 채워졌다

- 🔴 **객체 추출을 `.sql` 이 아니라 폴더 전체(`.md` 코드블록 포함)에서 수행했다** — 설명 문서의 코드블록도 실습자는 실행한다

- 🟡 제품 기본값이 이미 그 값이면 "변경을 건너뛰어도 된다"고 명시했다
- 🟡 모든 신규 객체에 **공통 접두사**와 `COMMENT` 태그가 있다
- 🟡 `02_` 시작부에 **사전 스냅샷**(또는 접두사 충돌 검사)이 있다
- 🔴 **`98_리소스정리.sql` 이 존재한다**
- 🟡 `98_` 이 9개 필수 구성 요소를 모두 포함한다
- 🔴 **객체 대장의 모든 항목이 `98_` 삭제 대상에 있다 (1:1 대조 완료)**
- 🔴 `DROP` 만으로 삭제되지 않는 객체의 실제 워크플로를 공식 문서로 확인해 반영했다
- 🔴 **외부 리소스 정리가 포함되었다** (특히 계속 누적되는 것)
- 🟡 각 단계 문서 말미에 그 단계까지의 정리 주석이 있다
- 🟡 `98_` 의 `DROP` 문이 주석 처리 상태이고 `IF EXISTS` 를 쓴다
- 🟡 정리 완료 검증 쿼리가 있고 사전 스냅샷과 대조하는 절차로 끝난다
- 🟡 **정리 완료 검증 쿼리를 실제로 실행해 봤다** — 실습 리소스가 없어도 실행 가능한 유일한 부분이다

- 🔴 계정 기본 객체를 삭제하는 구문이 없다
- 🟡 일시 중단 선택지가 제공되었다 (실습을 이어서 할 수 있도록)

## 7. IMPROVE 모드 — 기존 교육자료 개선 절차

#### 분량이 많을 때

문서 수가 많거나 총 분량이 커서 전부 읽으면 이후 작업 여력이 부족해질 것 같으면,
읽기를 다음처럼 나눈다. **읽기를 건너뛰는 것은 허용하지 않는다.**

| 방법 | 언제 |
|------|------|
| 우선순위 정독 + 나머지 대상 축소 | `IMPROVE_SCOPE` 가 `full` 이 아닐 때. 범위에 해당하는 문서만 정독한다 |
| 서브에이전트에 읽기 위임 | `full` 이고 분량이 클 때. 갭 분석에 필요한 사실만 추출해 오게 한다 |
| 회차 분할 | 위 두 방법으로도 부족할 때. 사용자에게 알리고 문서 그룹을 나눠 여러 회차로 진행한다 |

객체 목록 추출은 grep 으로 보조할 수 있다. 단, **grep 결과만으로 판단하지 말고
해당 파일을 읽어 문맥(주석 처리 여부, 조건부 실행, 설명용 예시 여부)을 확인한다.**

**확장자를 제한하지 않는다.** `.md` 설명 문서의 코드블록도 실습자는 실행한다.
`.sql` 만 훑으면 그 구문이 만든 객체와 바꾼 속성이 대장에서 빠진다.
자세한 근거는 정리 요구사항의 "자체 검증 — 1:1 대조" 절 참고.

```bash
F=/workspace/<TARGET_FOLDER>/
grep -rnE "CREATE (OR REPLACE )?(IF NOT EXISTS )?(DATABASE|SCHEMA|WAREHOUSE|ROLE|TABLE|VIEW|STAGE|SECRET|NETWORK RULE|EXTERNAL ACCESS INTEGRATION|EVENT TABLE|TASK|STREAM|PIPE|COMPUTE POOL|FUNCTION|PROCEDURE|CORTEX SEARCH SERVICE)" "$F"
grep -rnE "ALTER (USER|ACCOUNT|SESSION|DATABASE|WAREHOUSE|TASK|STAGE) .*(SET|UNSET) " "$F"   # ← 속성 변경 탐지
grep -rn  "GRANT " "$F"                                                                      # ← 계정 레벨 권한 부여 탐지
```

### STEP I2. 갭 분석 (Gap Analysis)

품질 기준을 체크리스트로 삼아 **현재 상태를 항목별로 판정**한다.
`IMPROVE_SCOPE` 에 해당하는 항목만 본다.

각 결함을 아래 형식으로 정리한다.

| # | 심각도 | 분류 | 위치 | 문제 | 근거 | 조치안 |
|---|--------|------|------|------|------|--------|
| 1 | 🔴 치명 | 정확성 | `03_*.sql:45` | `DROP` 워크플로가 실제와 다름 | 공식 문서 대조 | 3단계 절차로 수정 |
| 2 | 🟡 중요 | 정리 | `01_*.md` | 객체 대장에 Integration 누락 | SQL 직접 추출 결과 | 대장 + `98_` 에 추가 |
| 3 | 🟢 개선 | 가독성 | `07_*.md` | 설정값이 본문에 산재 | — | 상단으로 집약 |

심각도 정의:

| 심각도 | 기준 |
|--------|------|
| 🔴 **치명** | 실습이 실패하거나, 계정에 잔여물이 남거나, 잘못된 정보를 사실로 서술 |
| 🟡 **중요** | 규격 위반, 누락된 필수 요소, 검증 부족 |
| 🟢 **개선** | 가독성, 구성, 보강 |

**정확성 판정은 검증 규율을 따른다.** "틀린 것 같다"로 지적하지 않고, 실행·컴파일·공식 문서로 확인한 뒤 지적한다.

### STEP I4. 개선 적용

승인된 항목만 반영한다. 다음 규율을 지킨다.

#### 최소 변경 원칙
- **부분 편집을 우선한다.** 전체 재작성은 문서가 규격을 근본적으로 위반할 때만 한다.
- 지적하지 않은 부분은 건드리지 않는다.
- 사용자가 직접 손댄 것으로 보이는 내용(주석, 메모, 커스텀 값)은 보존한다.
- 파일 삭제는 **승인받은 경우에만** 한다.

#### 규격 정렬 (Normalization)
기존 자료가 구 규격이면 다음을 보완한다. 없는 것만 추가한다.
- 메타 주석 블록 누락 → 추가
- `01_` 에 객체 대장 없음 → **폴더 전체**(`.md` 코드블록 포함)에서 객체를 추출해 작성
- `02_` 에 사전 스냅샷 없음 → 추가
- `98_리소스정리.sql` 없음 → **신규 생성** (STEP C5와 동일 기준)
- 단계 문서 말미에 정리 주석 없음 → 추가
- `99_generate_index.py` 없음 → 신규 생성
- 검증 상태 주석 없음 → 추가. **총괄 합격 선언이 있으면 제거**한다
- 계정 레벨 객체에 `CREATE OR REPLACE` → `IF NOT EXISTS` + 충돌 검사 게이트로 전환
- 스냅샷 실측값이 전사되어 있음 → 쿼리 + 빈 기록 서식으로 교체
- 부수 문서가 번호 없이 흩어져 있음 → `90_`~`94_` 로 편입 (계획·분석 문서는 제외)

#### 정확성 수정
- 수정 근거를 반드시 확보한 뒤 고친다 (검증 규율)
- 고친 구문은 **재검증**한다
- 검증 못 한 것은 미검증으로 표기한다 (미검증 표기 의무)

### STEP I5. 재검증 및 실습 완주

수정한 SQL을 검증 규율에 따라 다시 검증한다. **수정했다는 사실이 정확성을 보장하지 않는다.**

**🔴 개선 범위가 `full` 또는 `accuracy` 이면 실습을 완주한다.**
품질 기준의 "완주 검증" 절 기준을 따른다. 기존 자료가 "검증 완료"라고 주장하고 있어도 그것을 근거로 삼지 않는다 —
그 주장 자체가 갭 분석 대상이다.

> 실측 사례: 컴파일만 통과한 자료에서 완주 시 `CREATE PROCEDURE` 절 순서 오류로
> 프로시저가 아예 생성되지 않고, 프로시저 본문의 런타임 타입 오류와
> `EXCEPTION` 핸들러에 삼켜진 조용한 실패가 드러났다.

`requires` / `next` 체인이 실제 파일과 일치하는지 확인한다.

### 문서 추가·삭제·번호 변경 규칙 (STEP I4 공통 규칙)

IMPROVE 모드에서 문서 구성이 바뀔 때 적용한다.

| 상황 | 처리 |
|------|------|
| 문서 **추가** — 빈 번호가 있다 | 그 번호를 사용한다. 번호 변경 불필요 — 번호는 연속일 필요가 없다 |
| 문서 **추가** — 빈 번호가 없다 | 뒤쪽 문서를 재번호. `requires`/`next` 체인과 문서 내 상호 참조를 **모두** 갱신 |
| 문서 **분할** — 한 문서가 SQL/외부 작업 혼재 | 문서 분리 규칙에 따라 분리. 원본 번호를 앞쪽에 유지하고 뒤쪽에 새 번호 부여 |
| 문서 **삭제** | **승인 필수.** 번호는 비워 둔다(재번호하지 않는다 — 외부 참조 보호) |
| 문서 **이름 변경** | 다른 문서의 `requires`/`next` 와 본문 참조를 모두 갱신 |

재번호는 외부 참조(사용자 메모, 다른 문서 링크)를 깨뜨린다. **가능하면 피하고,
수행했다면 최종 보고에 명시한다.**

## 8. 금지 사항

### 공통
**A. 시작 전제 — 임의로 출발하지 않는다**
- **모드를 추측해 진행하지 않는다**
- **`GOAL` 또는 `TARGET_FOLDER` 없이 임의로 시작하지 않는다**

**B. 검증 근거 — 이것을 근거로 삼지 않는다**
- **검증 단계를 생략하지 않는다**
- **모델 기억을 근거로 정확성을 주장하지 않는다**
- **검증하지 않은 구문을 검증된 것처럼 서술하지 않는다**
- **프로시저·태스크의 "성공 응답"을 검증 근거로 삼지 않는다** — 반환 메시지와 `STATE = SUCCEEDED` 는 `EXCEPTION` 핸들러에 삼켜진 실패를 가릴 수 있다. **결과 상태를 별도 쿼리로 단정한다**
- **`98_` 을 1회 실행해 성공한 것을 재실행 안전성의 근거로 삼지 않는다** — 정리 문서는 두 번 실행해 검증한다. `IF EXISTS` 는 **상위 데이터베이스·스키마 부재를 막아주지 않는다**
- **컴파일 검증만으로 완료를 보고하지 않는다** — 실습 완주(실행 → 결과 확인 → 정리 → 대조)까지
  수행하고, 못 한 부분은 이유와 함께 밝힌다 (품질 기준의 "완주 검증" 절)
- **실습 데이터가 없다는 이유로 완주를 건너뛰지 않는다** — 필요한 데이터는 직접 만든다
- **비용을 이유로 실행 검증을 생략하지 않는다** — 컴퓨트·서버리스·토큰·스토리지 비용은
  사용자가 사전 허가했다(검증 규율의 "실행 승인" 절). 단 **로그인 경로 변경·자격증명 발급·
  기존 사용자/역할 변경·계정 파라미터 변경·외부 시스템 변경**은 비용 허가와 별개로 확인받는다
- **`DROP` 워크플로를 추측해 기술하지 않는다** — 공식 문서로 확인한다
- **차단 지점(하드 블로커)을 추정으로 기술하지 않는다** — 순서대로 실행해 **처음 막히는 지점**을 실측으로 확정하고 오류 원문을 인용한다. 도달 한계까지 간 것을 "완주" 라고 부르지 않는다

**C. 서술 정직성 — 아는 것보다 크게 말하지 않는다**
- **측정하지 않은 성능·비용·효과 수치를 제시하지 않는다** — 레이턴시, 처리량, 절감률, 방어율, ROI
- **"검증 완료"·"운영 배포 가능" 류의 총괄 합격 선언을 쓰지 않는다** — 검증은 항목 단위로만 주장한다
- **이름이 비슷한 두 제품 기능을 확인 없이 동일시하지 않는다** — 성격·적용 범위를 공식 문서로 확인한다

**D. 정리·왕복 가능성 — 계정에 흔적을 남기지 않는다**
- **정리 문서(`98_`) 없이 완료로 보고하지 않는다**
- **실행 검증을 했다면 `98_` 정리와 스냅샷 대조까지 완결한다** — 비용 허가는 잔여물을 남길 허가가 아니다
- **객체 대장에 없는 객체를 실습에서 생성하지 않는다**
- **객체 추출을 `.sql` 파일로 한정하지 않는다** — `.md` 코드블록의 `CREATE`/`ALTER … SET` 도 대장 대상이다
- **정적 검색 결과만으로 객체 대장을 완성하지 않는다** — 프로시저·태스크가 **실행 중 만드는 객체**는 `grep` 에 걸리지 않는다. 계정 레벨이면 `DROP DATABASE` 로도 사라지지 않으므로 `(간접)` 으로 등재하고 `98_` 에 패턴 검색 절차를 둔다
- **사용자가 명시하지 않은 기존 Snowflake 객체를 재사용하거나 변경하지 않는다.** 제품 요구사항 때문에 불가피하게 변경해야 한다면 그것을 **대장 (b) 속성 변경 행으로 등재하고 "속성 변경(Mutation)" 절의 3단계(사전 값 기록 → 변경 지점 경고 → `98_` 원복)를 모두 수행한다.** 등재 없이 변경하는 것을 금지한다
- **`DROP` 만으로 원복되지 않는 변경을 정리 완료로 보고하지 않는다**
- **계정 기본 객체(`COMPUTE_WH`, `SNOWFLAKE`, 시스템 Role, `PUBLIC` 등)를 삭제하는 구문을 생성하지 않는다**
- **`CREATE OR REPLACE` 를 재실행 안전성의 근거로 삼지 않는다.** 계정 레벨 객체(DB/WH/Role)에는 쓰지 않는다
- **스냅샷·환경 상태의 실측값을 문서에 전사하지 않는다** — 쿼리와 빈 기록 서식을 제공한다

**E. 보안·자격증명**
- **발급한 자격증명 값을 대화·문서에 출력하지 않는다**
- **동적 SQL 의 식별자 자리를 검증 없이 문자열 결합하지 않는다** — 식별자는 바인드할 수 없으므로 패턴 검사로 방어한다. 주입 가능한 패턴을 예시로 남기지 않는다

**F. 문서 구조·번호·카탈로그**
- `00_index.md` 를 손으로 작성하지 않는다
- 폴더 밖에 파일을 흩뿌리지 않는다 (예외: 워크스페이스 카탈로그 `/workspace/00_교육자료_카탈로그.md`)
- `95_`, `96_`, `98_`, `99_` 를 다른 용도로 쓰지 않는다 (예약 번호)
- 계획·분석·진행 상황 문서를 별도 파일로 만들지 않는다 (분석은 대화와 `01_` 검토 이력에 남긴다).
  단 `90_`~`94_` 의 **부수 문서**(개념 심화, 실무 핸드오프, 운영 런북)는 허용한다 — 문서 번호 규칙 참고
- **이미 배정된 `EDU-<NN>` 번호를 바꾸지 않는다.** 폐기된 번호도 재사용하지 않는다
- **번호에 분야·난이도·수강 순서를 인코딩하지 않는다**
- **분야 태그를 하나만 달지 않는다** — 해당하는 것 전부 단다. 한 자료가 여러 분야에 걸치는 것이 정상이다
- **카탈로그에 등록하지 않고 완료로 보고하지 않는다** — 번호·제목·폴더·분야 태그·검증 상태

**G. 작업 환경**
- **`>>` 로 문서에 내용을 덧붙이지 않는다** — 이 스테이지 파일시스템에서 **조용히 실패**한다. 전체를 다시 쓰고, 쓴 뒤 **내용으로** 확인한다

### CREATE 모드 전용

- **기존 폴더를 확인 없이 덮어쓰지 않는다**
- 문서 번호를 중복하지 않는다
- 필수 문서(`01_`, `98_`, `99_`)를 빼놓고 마무리하지 않는다
- **계정 적합성 확인(STEP C1) 없이 문서를 쓰지 않는다** — 불가능한 실습의 문서는 낭비다

### IMPROVE 모드 전용

- **모든 문서를 읽지 않은 상태로 갭 분석하지 않는다** (STEP I1)
- **승인(STEP I3) 없이 파일을 수정하지 않는다**
- **승인 없이 파일을 삭제하지 않는다**
- **기존 검토 이력을 지우거나 덮어쓰지 않는다** — 회차를 누적한다
- **사용자가 직접 작성한 내용을 임의로 제거하지 않는다**
- 지적하지 않은 부분을 함께 고치지 않는다 (최소 변경 원칙)
- 기존 검토 이력에서 이미 "미검증"으로 밝힌 항목을 새로운 결함처럼 보고하지 않는다
- 필요 없는 재번호를 하지 않는다 (위 "문서 추가·삭제·번호 변경 규칙")
- **객체 대장을 그대로 신뢰하지 않는다** — 폴더 전체(`.md` 코드블록 포함)에서 직접 추출해 대조한다 (STEP I1)
